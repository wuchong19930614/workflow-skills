## 1. 为什么要做

连续三天（2026-10-14 至 10-16）快道没出过 go。原因不是找不到新游戏，而是**工具位在开玩前后就被占满**：

- WARDOGS、Aniimo 首页上 7 个专做该游戏的占位站，域名注册或首张证书都比开放游玩日早 6–230 天。
- Castlevania: Belmont's Curse 上线当天，地图首页已有 6 个站（10-01 起有试玩版，做地图的人提前准备）。
- DayZ Badlands 新地图 10-15 上线，10-16 首页第 1、2 名就是 survivalservers.com 与 iZurvive 的新地图。
- Pixel Lineage（Roblox）的梯队首页有 3 个专做本作的小站。

现行规则要求"开玩后、按当前搜索量过线"才判 go，我们永远晚一步。用户 2026-10-16 允许在上线前按预测判 go，让用户有时间在对手之前把站做出来。

## 2. 写方案前的实测

### 2.1 WARDOGS 的倍数

2026-10-16 用 Trends（美国、近 90 天逐日）实测：

- 同一次查询放"wardogs"和"wardogs map"不能用：任务词只有对象名的约 1%，读数全是 0 和 1。
- 改为两个词分别和同一个锚词"map seed"（美国 8,100 次/月，旧词库）比，读数可用。
- **窗口选法对倍数影响极大**：WARDOGS 的开玩日按口径是 08-22（向所有预购者开放的封闭测试），但大批玩家是 09-10 抢先体验才进来的。"wardogs map" 在 08-22 起 14 天只有锚词的 0.012 倍，在 09-10 起 14 天是 0.122 倍，差 10 倍。所以参照的窗口必须写死（5.3）：
  - 对象名：开玩日前第 9 到第 3 天（对应最晚的预判时点）。WARDOGS 08-13 至 08-19 为锚词的 1.065 倍，折合美国约 **8,623 次/月**；
  - 任务词：开玩后 60 天内最高的连续 14 天（对应门槛"上线 90 天内有一个月"）。WARDOGS 是 09-04 至 09-17，为锚词的 0.145 倍，折合美国约 **1,172 次/月**；
  - 倍数 r（任务词 ÷ 对象名）≈ **0.14**。

只有 1 个样本，**未确认**。

### 2.2 这意味着什么

- 门槛（英文区单月 1 万访问）在基准份额 20%、AI 概览系数 0.6 下，需要约 **83,000 次英文区搜索/月**。
- WARDOGS 卖了 200 多万份，地图词最高的两周也才约 1,172 次/月（美国），离门槛差约 70 倍。单个任务词，几乎任何新游戏都到不了门槛。
- 所以预判必须按**一款游戏做一个站、覆盖几项任务**合计测算（5.1）。即便这样，大概率也只有超级大作、或工具本身就是核心玩法的游戏（交易估价、大型开放世界地图）能过线。**预期 go 很少**，这是诚实的先验，不是方案的缺陷。

## 3. 目标、非目标、反目标

**目标**

- 对开玩日已定、还没开放游玩的游戏，在开玩前 3–21 天用预测量判 go，给用户留出建站时间。
- 每次预判都留下可复核的依据；开玩后 7 天用实测量对账，偏差太大就提示止损，并把实测倍数补进参照库，让预测越用越准。

**非目标**

- 不改现行"开玩后按当前量判 go"的路径，两条路并存。
- 不建站、不自动部署、不做定时任务（沿用用户已定的口径）。
- 不接付费数据接口；Trends、Semrush、Google 首页都沿用现有通道。

**反目标**（技术上能跑通也算失败）

- 只凭预告片热度、公布期热度就判 go，开玩后量没起来。
- 测试期就有专做本作的 wiki 或工具站，我们还判 go。
- 为预判把 Trends 配额烧光，导致当天的飙升词、量级换算取不到。

## 4. 预判的适用范围（P1–P6）

六条全过才能预判，和现行 Q1–Q6 一一对应：

- **P1 即将开玩**：对象类型 `game`（含 DLC、资料片），开玩日已确定（发售表、官方或商店页），并且在**今天之后 3–21 天**之内；还没有所有人都能下载的试玩版或公开测试（有的话开玩日已过，按现行路径走）。3 天是最小版本建站要的时间，21 天以外日期容易变、预测也不稳（我的判断）。
- **P2 有人在等**：对象名在 Trends 上开玩前 7 天读得出（美国均值不为 0），并且自动补全已出现任务说法，或者参照库里同类游戏有这类任务。
- **P3 任务会反复发生**：要做的任务类型在参照库里有记录（地图、配装、梯队、计算器、兑换码等），不是一次性的。
- **P4 范围**：同契约第 1 节五条排除。
- **P5 还没人做**：看美国首页"<游戏名> <任务词>"和"<游戏名> wiki"两次；测试期就有专做本作的 wiki 或工具站、或大站已发了完整页，算已占位，不预判。
- **P6 没被答完**：开玩前 AI 概览答不了未上线的内容，记为"开玩前未知"，测算时统一按在场未答完取系数 0.6（保守）。

## 5. 预测模型

### 5.1 测算单位：一款游戏一个站

预判方向 = 给一款游戏做一个站，最小版本覆盖 1–4 项任务（例：交互地图 + 配装 + 梯队）。量级按这几项任务的预测量相加，不再只看一个词。

### 5.2 公式

- **对象名开玩前月搜索量** O：英文区 6 国按现有锚词换算（`trends_volume.py`），窗口取预判当天之前最近 7 天（和参照的"开玩前第 9 到第 3 天"同口径；预判越早，O 往往越小，结果偏保守）。
- **任务 t 的预测月搜索量** F_t = O × r_t，r_t 取参照库里该任务类型的倍数（5.3）。
- **站点预测月搜索量** F = Σ F_t（只算最小版本要做的任务）。
- **预测月访问** = floor(F × 首发份额 × 0.6)，份额沿用 10% / 20% / 30%。
- **预测月收入**：按各国量的比例分，美国 $4、其他英文国家 $2 每千访问（沿用快道假设表）。

### 5.3 参照库与倍数

- **参照记录**：每款已开玩游戏的每项任务一条，记对象名开玩前 7 天的量、任务词开玩后 0–13 天的量、倍数 r、游戏类别、开玩日、取数网址（格式见 7.1）。
- **取数**：都用美国、Trends 近 90 天逐日，两个词分别和同一个锚词比（2.1 的做法），每条参照 2 次 Trends 请求。只取美国：倍数是比例，国家差异在 O 里已经按国家换算（我的判断）。
- **窗口（写死）**：对象名取开玩日前第 9 到第 3 天的均值；任务词取开玩后 60 天内最高的连续 14 天均值；都换算成月量后相除。开玩日按契约 10.4 的口径（第一次让大量普通用户用上）。开玩后不满 60 天的游戏，先用已有天数里最高的 14 天，记"未满 60 天"，满了再更新（我的判断）。
- **游戏类别**（粗分，我的判断）：开放世界或生存、MMO 或抽卡、银河城或冒险解谜、竞速体育派对、Roblox 体验。
- **倍数取法**：同任务类型、同类别的参照至少 3 条才可用；判 go 用**下四分位数**（偏保守），同时报中位数；同类别不足 3 条时退到同任务类型全部类别，仍不足 3 条就不预判，记"参照不足"。
- **冷启动**：先用 10-08 至 10-16 已观察过的游戏补参照：WARDOGS、Aniimo、Castlevania: Belmont's Curse、Hellraiser: Revival、Silver Pines、Planet Zoo 2、Order of the Sinking Star、Star Wars: Galactic Racer、Gears of War: E-Day、Valor Mortis、DayZ Badlands、Pixel Lineage 等。每天的那一轮里补 2–4 条，大约一周补齐。

### 5.4 判定

- **预判 go**：P1–P6 全过，并且按下四分位倍数算出的**基准预测月访问 ≥ 10,000**（英文区合计，和现行门槛同一个数）。
- **预判观察**：P1–P6 全过，下四分位不过线但中位数过线 → 进 watching，开玩后第 7 天按现行"当前量"路径复判。
- **不预判**：其余情况只记观察，不登记方向；对象照常留在"即将开玩"日历里，开玩后按现行路径看。

## 6. 流程接入

### 6.1 每天一轮里加一步"预判"

放在"扫信号"之后、"零成本速判"之前：

1. 从 `quick_pool.py upcoming --days 21` 取开玩日在今天之后 3–21 天的游戏，按日历顺序，**每轮最多预判 2 个**（Trends 配额）。
2. 对象跑 `suggest_snapshot.py --object` 找任务说法，定最小版本要做的 1–4 项任务。
3. 看首页（P5），两次请求间隔 ≥ 60 秒，计入当轮 10 个首页名额。
4. 先只测美国的 O；美国单国算出的基准预测已不到门槛的一半，就不再测其他 5 国、不花 Semrush，直接记"不预判"（我的判断，省配额）。
5. 写一份 `quick_forecast` 观察（7.2）。

### 6.2 登记、结算与跟进

- `ledger.py register-quick` 增加预判登记：`object.first_public` 填未来的开玩日，允许在速判日之后 3–21 天；方向记 `basis: "forecast"`。
- `settle.py --verdict go` 对预判方向照常走四处强推；建议最晚上线日 = **开玩日前 1 天**（现行是判 go 后 7 天）；决策书加"预判依据与风险"一节，写参照条数、倍数、下四分位与中位数两档结果、最大未知。
- 预判观察（watching）的到期日 = 开玩日 + 7 天。

### 6.3 开玩后复核与参照库自校准

- 开玩日 + 7 天，按现行锚词换算实测各任务词的量，写 `quick_volume` 观察，和预测比：
  - 实测 < 预测 × 25%：在跟进记录里标"预判失准，建议停止追加投入"，看板提醒；
  - 不管准不准，都把这次的实测倍数写成一条参照记录，进参照库。
- 预判观察的方向在这一天按现行路径复判（go、继续观察或否决）。

## 7. 数据格式

### 7.1 参照记录 quick_reference

一款游戏的一项任务一份观察，`slug` 为 null：

```json
{
  "kind": "quick_reference",
  "readings": {
    "object": "WARDOGS",                         // 游戏名
    "category": "open_world_survival",           // 游戏类别:open_world_survival | mmo_gacha | metroidvania_adventure | sports_racing_party | roblox
    "task": "map",                               // 任务类型:map | build | tier_list | calculator | codes | 其他(写明)
    "task_term": "wardogs map",                  // 实测的任务词
    "playable_at": "2026-08-22",                 // 开玩日(第一次让大量普通用户用上的日期)
    "anchor_term": "map seed",                   // 两次查询共用的锚词
    "anchor_volume": 8100,                       // 锚词美国月量
    "anchor_source": "lexicon",                  // lexicon | semrush
    "object_window": ["2026-08-13", "2026-08-19"],  // 对象名窗口:开玩日前第 9 到第 3 天
    "object_ratio": 1.065,                       // 对象名窗口均值 ÷ 锚词同期均值
    "task_window": ["2026-09-04", "2026-09-17"], // 任务词窗口:开玩后 60 天内最高的连续 14 天
    "task_ratio": 0.145,                         // 任务词窗口均值 ÷ 锚词同期均值
    "full_60_days": true,                        // 开玩后是否已满 60 天;未满时窗口取已有天数里最高的 14 天
    "object_volume_pre": 8623,                   // 对象名开玩前月量 = 锚词月量 × object_ratio
    "task_volume_post": 1172,                    // 任务词开玩后月量 = 锚词月量 × task_ratio
    "r": 0.136                                   // 倍数 = task_volume_post ÷ object_volume_pre
  }
}
```

### 7.2 预判观察 quick_forecast

一个拟预判方向一份，`slug` 写拟用的方向名：

```json
{
  "kind": "quick_forecast",
  "readings": {
    "object": "Monster Hunter Outlanders",       // 游戏名
    "category": "mmo_gacha",                     // 游戏类别,同 7.1
    "playable_at": "2026-10-29",                 // 开玩日,须在观察日之后 3–21 天
    "date_source": "https://…",                  // 开玩日从哪读的
    "object_volume_pre": {"US": 0, "GB": 0},     // 对象名开玩前月量,6 国各一项;引用对应的 quick_volume 观察
    "object_volume_ref": "证据/…-quick_volume.json",  // 对象名量级观察的路径
    "tasks": [                                   // 最小版本要做的任务
      {
        "task": "map",                           // 任务类型
        "terms": ["… map", "… interactive map"], // 归到这项任务的说法
        "r_p25": 0.05,                           // 参照库下四分位倍数
        "r_median": 0.08,                        // 参照库中位数倍数
        "references": 4,                         // 用到的参照条数(须 ≥ 3)
        "reference_refs": ["证据/_quick/…-quick_reference.json"]  // 参照观察路径
      }
    ],
    "forecast_p25": 0,                           // 下四分位倍数下的站点预测月搜索量(英文区合计)
    "forecast_median": 0,                        // 中位数倍数下的站点预测月搜索量
    "checks": {                                  // P1–P6,格式同 quick_screen 的 checks
      "P1": {"pass": true, "basis": "…"}
    }
  }
}
```

## 8. 假设表新增项

假设表由 `2026-10-14.q3` 升为 `q4`，数值写进 `quick_model.QUICK_ASSUMPTIONS`，和契约由文档一致性测试锁住。以下都是我的判断：

- 预判窗口：开玩日在今天之后 3–21 天。
- 每轮最多预判 2 个对象。
- 参照最少 3 条（同任务类型、同类别；不足退到同任务类型）。
- 判 go 用下四分位倍数，同时报中位数。
- 预判 go 的建议最晚上线日：开玩日前 1 天。
- 复核日：开玩日 + 7 天；复核止损线：实测 < 预测 × 25%。
- 美国单国基准预测不到门槛一半时，不测其他 5 国。

## 9. 成本与限流

- 一条参照：2 次 Trends（美国）。
- 一个预判对象：美国 1–2 次 Trends，过了"一半门槛"才测其他 5 国（再 5 次 Trends，读得出的国家各 1 次 Semrush）；首页 2 次。
- 每轮合计估算：飙升词 6 次 + 预判 2–12 次 + 参照 4–8 次 + 当轮量级换算若干，大约 15–30 次 Trends。10-16 实测，间隔 ≥ 35 秒时 9 次以上没遇到 429；上限多少未确认，遇到 429 就按现行规则停下，没做的写"本次未取"。
- 优先级（同一轮里 Trends 不够时）：当轮飙升词 > 复核到期的预判方向 > 预判 > 补参照。

## 10. 风险与未确认

- **倍数只有 1 个样本**（WARDOGS 地图 0.14），量级、类别差异都未确认，冷启动参照库补齐前预测不可信；参照不足时不预判。

## 14. 2026-10-17 用户拍板的三条

2026-10-16 实施完成后留了三件待拍板的事。2026-10-17 我给了建议，用户回复"ok"，三条都按建议做。下面是实现口径。

### 14.1 判过不预判的游戏什么时候重做

- **每款游戏最多预判 2 次**（按规范化后的游戏名数预判观察的份数）；建议为 `measure_rest` 的那份不算次数（它只测了美国，补测其余 5 国后当天重做的才算一次完整预判）。这个"2"写进假设表 `forecast_max_per_object`，假设表升为 `2026-10-17.q5`。
- 看板"可预判"每行按上次预判观察给出重做状态：

```json
{
  "reforecast": "due",                 // new 没预判过 | due 可以重做 | wait 还不到时候 | no 不再预判
  "reason": "上次量不够,开玩前 9–3 天再做一次"  // 大白话原因,看板原样显示
}
```

- 判法（上次 = 这款游戏最新的一份预判观察）：
  - 没预判过 → `new`。
  - 已做满 2 次，或上次建议是 go / watching（已登记，正常不会再出现在可预判里）→ `no`。
  - 上次 P4（范围）、P5（首页已占位）或 P6 不过 → `no`；开玩后照现行路径看。
  - 上次 P1 不过 → 原料里的开玩日和上次观察的 `playable_at` 不同（改期了）才 `due`，否则 `no`。
  - 上次 P3 不过（参照不足）→ 上次的每项任务在参照库里都取得到倍数（同类别或退到同任务类型够 3 条）才 `due`，否则 `wait`。
  - 上次 P2 不过（美国读不出），或六条都过但建议 `skip`（量不够、美国单国不到截断线）→ 今天离开玩日在参照的对象名窗口里（开玩日前第 9 到第 3 天，即 `reference_object_window`）、而上次不是在这个窗口里做的 → `due`；还没到窗口 → `wait`；上次已经在窗口里做过 → `no`。
  - 上次建议 `measure_rest` → `due`（补测其余 5 国）。
- 排序：`new`、`due` 在前（再按开玩日），然后 `wait`、`no`。SKILL 第 5 步只取 `new` 与 `due`，每轮仍最多 2 个。
- 理由：对象名的量越临近开玩越大，而参照的对象名窗口正是开玩前第 9 到第 3 天，这时预测口径最一致；限 2 次让最坏成本确定（每次约 2 个首页名额、1–6 次 Trends）。

### 14.2 预判方向开玩后判 go 的约束

- **观察中**（预判后进 watching）：维持 2026-10-16 的规则——复核日已到、复查过一次、最新速判与登记说法的量级都在开玩日或之后。
- **搁置**（预判登记后开玩前搁置，`basis: "forecast"`、state parked）→ 按现行路径判 go 时：最新速判的观察日须在开玩日当天到开玩后 `new_days_game`（14）天内（相当于开玩后重新判一次 Q1），登记说法的最新量级观察日须在开玩日当天或之后；开玩日取 `object.first_public`。不要求复核日和复查（搁置没有观察期）。游戏推迟了，搁置的方向同样可以用 `ledger.py update` 改开玩日（须在新开玩日到来前改，见 13 第 10 条），窗口按新开玩日算；过了窗口又没有推迟的，只能否决或继续搁置。
- **否决不限制**：not_new、occupied、answered、scope、volume、oneoff 照现行规则。否决是保守方向，判错只是少一个机会；开玩前就看到专做本作的站，当场否决反而省事。

### 14.3 观察按自己记下的口径校验

- `quick_reference` 与 `quick_forecast` 的读数各加一项 `params`，记下校验要用的假设表数值，并加 `assumptions_version`：

```json
{
  "assumptions_version": "2026-10-17.q5",   // 写入时的假设表版本
  "params": {                               // quick_reference 的口径
    "object_window": [9, 3],                // 对象名窗口:开玩日前第 9 到第 3 天
    "task_days": 14,                        // 任务词窗口长度
    "task_span": 60                         // 任务词窗口须在开玩后多少天内;满多少天算 full_60_days
  }
}
```

```json
{
  "assumptions_version": "2026-10-17.q5",   // 写入时的假设表版本
  "params": {                               // quick_forecast 的口径
    "forecast_days": [3, 21],               // P1 的开玩日窗口
    "min_references": 3,                    // 每项任务至少几条参照

    "share_base": 0.2,                      // 基准首发份额
    "aio_factor": 0.6,                      // 预判一律按的 AI 概览系数
    "us_only_cutoff": 0.5                   // 只测美国时的截断线(门槛的比例)
  }
}
```

- **写入时**（`write_observation.write`、两个生成脚本）`params` 与 `assumptions_version` 须等于当前假设表，不能自己编口径。
- **读回时**（`write_observation.read`）按观察自己的 `params` 校验，不再拿当前假设表比；假设表改了，历史观察照样读得进来。
- **参照库算倍数**只用 `params` 与当前假设表相同的参照；口径不同的不混着算，在看板和 `quick_forecast.py` 的"参照不可用"里写明"口径已变，需重测"。
- **结算重算**（`ledger.forecast_model`）：预判观察与它引用的参照，`params` 都须等于当前假设表，否则拒收"口径已变，重做预判"。
- **复核**（`review-forecast`）、看板读历史预判、重建决策书：按观察自己的口径读，不受假设表变更影响。
- **不在本次范围**：`quick_volume` 的锚词比值区间（0.2–5）读回时仍按当前假设表；账本里模型的重算也按当前假设表（两条道现有做法）。改假设表时现有 go 与观察中方向的模型会重算不一致，到时另议。
