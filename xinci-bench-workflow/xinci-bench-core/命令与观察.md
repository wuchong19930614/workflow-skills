## 2. 运行清单

```bash
python3 $S/run_log.py --plan
python3 $S/run_log.py --skill xinci-bench-scan --run-id run-20261014-a --round 1 --max-rounds 3 \
  --source-kind legacy --seed-value "种子池 legacy 前 16 个" --outcome started --next-step scan
python3 $S/run_log.py --finish --run-id run-20261014-a --outcome completed --semrush-calls 5 \
  --direction-touched example-county --note "16 个初核,2 个登记"
```

- 每阶段先写 started，结束用 `--finish`（completed / blocked / skipped），脚本推导下一步。
- found 已有 ≥ 3 个时 `--plan` 返回 `scan_outcome=skipped`：照样先写 scan started，再 `--finish --outcome skipped`。
- `--semrush-calls` 只填本条新增的调用数。
- `--plan` 还给出今天两条道合计的 Semrush 用量：`semrush_calls_today`、`semrush_daily_limit`（100）、`semrush_left_today`、`semrush_stop`（今天已用到 90 次时为 true，此时不再开始花 Semrush 的步骤）。

## 7. 新词快道

### 7.1 运行清单

```bash
python3 $S/run_log.py --plan --lane quick
python3 $S/run_log.py --skill xinci-bench-quick --run-id quick-20261014-a --round 1 --max-rounds 1 \
  --source-kind quick --seed-value "自动补全、Trends 飙升、SteamCharts、Product Hunt" --outcome started --next-step quick
python3 $S/run_log.py --finish --run-id quick-20261014-a --outcome completed --semrush-calls 1 --note "扫 40 条原料,登记 1 个"
```

快道一次运行只有一个阶段：`round` 与 `max-rounds` 固定为 1，`source-kind` 固定为 `quick`；每天最多开 1 轮，`--plan --lane quick` 给出 `quick_rounds_today`、`quick_rounds_per_day`、`quick_new_round_allowed`，为 false 时不开新的一轮（恢复受阻的不算）；受阻用 `--outcome blocked`，之后同一运行编号再 `--finish`。快道与标杆道的未完成运行互不阻塞。

### 7.2 扫信号与原料池

```bash
python3 $S/suggest_snapshot.py --object "Grow a Garden 2"          # 对象名 + 空格,以及对象名 + 10 个任务词
python3 $S/suggest_snapshot.py --query "grow a garden 2 calculator"
python3 $S/suggest_snapshot.py --object "Grow a Garden 2" --gl gb  # 地区性对象查别的英文国家:gb | ca | au | nz | ie
python3 $S/write_observation.py --input <quick_signal 观察文件>
python3 $S/quick_pool.py add --observation 证据/_quick/<文件名>
python3 $S/wiki_releases.py --output <scratchpad>/wiki_releases.json  # 最近 14 天已上线与未来 30 天要上线的新游戏,按浏览量取前 20(items 并进 quick_signal)
python3 $S/quick_pool.py pending --top 10                          # 按优先级取首屏速判的 10 个(还没到开玩日的不列)
python3 $S/quick_pool.py upcoming --days 14                        # 即将开玩:开玩日在今天之后 14 天内的原料
python3 $S/quick_pool.py expire                                     # 7 天没拿到"有人在搜"证据的标 expired
python3 $S/quick_pool.py mark --id <原料 id> --status used
python3 $S/quick_pool.py reject --term "<说法>" --gate occupied --observation 证据/<方向>/<速判观察> --seed-domain <占位小站>
```

Trends 飙升词在 Trends 页面里用 `scripts/trends_fetch.js` 全文加一行 `await xinciTrendsRising({term: "beta", cat: 8})` 执行（`cat: 8` 是游戏分类，任务词用 `cat: 0`），每次运行最多 6 个种子词、两次执行之间隔 ≥ 30 秒、遇 429 停下（`数据采集.md` §7.2）。返回的 `rising[].rising` 是百分比或 `"breakout"`，可原样写进原料 `rising`。

对象页面和首页都读不到开玩日期时，在 Trends 页面里用 `await xinciTrendsFirstSeen({term: "huss valley roblox"})` 查首次出现日：`first_seen` 有值就当 `first_public`（`date_source` 写"Trends 首次出现"与返回的 `url`）；`before_window` 为 true 说明早于约 90 天，Q1 不过；`never` 为 true 时 Q1 记 null。

带 `playable_at` 的原料：开玩日在今天之后的不进 `pending`、只进 `upcoming`，看板列出"建议开玩当天到第 3 天跑一次快道"；保留 7 天从开玩日起算；同一对象再被看到时开玩日期与阶段以最新的为准。

`quick_pool.py reject` 与 `ledger.py register-quick` 会把对应说法的待看原料自动标 used；过期的原料再被来源取回时重新进池（保留原 id，记 `revived_at`）；淘汰过的词再被取回时报淘汰原因。

快道观察的公共字段同 §3.1，`stage` 固定为 `quick`。`quick_signal` 一批一份，`slug` 为 null：

```json
{
  "kind": "quick_signal",
  "readings": {
    "items": [
      {
        "source": "autocomplete",               // autocomplete | trends_rising | trends_rss | steamcharts | apple | itunes | google_play | producthunt | github | hackernews | youtube | wikipedia | policy | reddit | other
        "object": "Grow a Garden 2",            // 催生新说法的对象
        "term": "grow a garden 2 calculator",   // 冒出的任务说法;只有对象时为 null
        "url": "https://suggestqueries.google.com/complete/search?q=grow%20a%20garden%202%20",  // 实际取回的网址
        "seen_at": "2026-10-14",                // 看到日期
        "rising": 200,                          // 可选:Trends 飙升百分比,飙升词标 "breakout";排优先级用
        "playable_at": "2026-10-20",            // 可选:第一次让大量普通用户用上的日期,可在未来(没到这天只进即将开玩)
        "stage": "closed beta",                 // 可选:阶段,如 closed beta、playtest、Early access、Original
        "platform": "roblox"                    // 可选:平台;roblox 的兑换码(说法里有 codes)排到其他说法后面
      }
    ]
  }
}
```

### 7.5 量级观察与简报素材

量级观察用工具生成，不手算：

1. 内置浏览器打开 `https://trends.google.com/trends/explore?hl=en-US`，把 `scripts/trends_fetch.js` 全文加一行 `await xinciTrends({geo: "US", terms: ["<新词>", "<美国锚词>"]})` 交给页面执行；6 国（US、GB、CA、AU、NZ、IE）各一次，两次之间隔几秒，遇到 429 停下。每次执行都要带全文（作用域不保留）。
2. 把各国返回的 JSON 放进下面的输入文件，先只填美国的锚词月量跑一次：脚本会列出"读得出、要查锚词月量"的国家，读不出的自动记 0。
3. 只为列出来的国家去 Semrush 查锚词在该国的月量，补进 `anchors` 再跑一次，观察就写入了。


### 7.7 上线前预判

对开玩日在预判窗口内（契约 10.6）的游戏，在开玩前按预测量判 go；判据、公式与口径见契约 10.9，取数规程见 `数据采集.md` §7.6。一款游戏的顺序：先有参照库（7.7.1），再测对象名的量、生成预判观察（7.7.2），建议是 `go` 或 `watching` 的登记并结算（7.7.3），开玩日变了用 `ledger.py update` 改（7.7.4），开玩后复核或复查（7.7.5）。下面的 JSON 带 `//` 注释只为说明字段，写文件时去掉注释。

#### 7.7.1 取参照

参照只测美国，开玩后凑满任务词窗口才写（取数日 ≥ 开玩日 + 窗口长度，否则 `build` 拒收：开玩后曲线不够长）。三步：

```bash

```


起 = 开玩日前第 9 天；止 = 开玩日 + 59 天与取数日前一天里较早的那天（取数日当天的点还没走完，不要）。取数日太早、曲线还没走出来时命令拒收。

在 Trends 页面里（每次执行都带 `trends_fetch.js` 全文），同一个锚词各查一次，两次间隔 ≥ 35 秒：

```
await xinciTrends({geo: "US", terms: ["wardogs map", "map seed"], time: "2026-08-13 2026-10-15"})    // 第二次:任务词 + 锚词
```

```json
  "forecast_p25": 90000,                        // 下四分位倍数下的站点预测月搜索量(英文区合计)
  "forecast_median": 120000,                    // 中位数倍数下的站点预测月搜索量
  "下四分位基准访问": 10800                      // 下四分位下基准份额的预计月访问;六条没全过时为 null
}
```

预判观察（`kind` 为 `quick_forecast`，`slug` 是方向名）的读数。倍数从参照库取，不手填；`write_observation.py` 只核对形状与算术（参照条数与路径数一致且不重复、`r_p25` ≤ `r_median`、合计等于对象名量 × 各任务倍数之和、建议与合计对得上），倍数是不是真来自参照库，要到结算时才按引用的参照路径重新算（7.7.3）；六条没有全过时 `object_volume_pre`、`forecast_*` 与各任务倍数置 null，`suggestion` 只能是 `skip`：

```json
{
  "object": "Monster Hunter Outlanders",
  "category": "mmo_gacha",
  "playable_at": "2026-10-29",
  "date_source": "https://example.org/mho",
  "object_volume_pre": {"US": 600000},           // 对象名开玩前月搜索量,读得出的国家各一项(美国须 > 0);没测、读不出的国家不在里面

  "tasks": [

      "task": "map",
      "terms": ["mho map", "mho interactive map"],
      "r_p25": 0.15,                             // 参照库下四分位倍数

      "references": 3,                           // 用到的参照条数(须 ≥ 契约 10.6 的下限)
      "reference_refs": ["证据/_quick/20261016T080000000000Z-0a0a0a0a-quick_reference.json"],   // 参照观察路径,条数与 references 一致、不重复;结算时 settle.py 按它们向参照库重算
      "scope": "category"                        // category:取自同类别;task_type:同类别不够,退到同任务类型的全部类别
    }
  ],
  "forecast_p25": 90000,                         // = Σ(对象名各国量合计 × r_p25),取整
  "forecast_median": 120000,                     // = Σ(对象名各国量合计 × r_median),取整
  "suggestion": "go",                            // go | watching | skip | measure_rest
  "checks": {"P1": {"pass": true, "basis": "…"}, "P2": {"pass": true, "basis": "…"}, "P3": {"pass": true, "basis": "map 参照 3 条(同类别 mmo_gacha),下四分位 0.15、中位数 0.2"},
             "P4": {"pass": true, "basis": "…"}, "P5": {"pass": true, "basis": "…"}, "P6": {"pass": true, "basis": "…"}},   // 恰好 P1–P6;pass 可为 null(前项已不过、没查),全过时不能有 null
  "serp": [{"query": "monster hunter outlanders map", "top10": []}, {"query": "monster hunter outlanders wiki", "top10": []}]   // 两次首页的前 10,格式同输入
```

预判是方向登记**之前**的步骤，所以预判观察的 `slug` 是拟用的方向名。预判方向在结算前（`found`）不能用 `ledger.py quick-preview`：它读的是开玩后的当前量，预判方向没有，会拒收"缺当前月搜索量"；看预判结果就读 `quick_forecast.py` 的输出（或生成的观察）。

#### 7.7.3 登记与结算

```json
{
  "slug": "mho-map",
  "title": "怪物猎人新作地图",
  "site_type": "tool",
  "object": {"name": "Monster Hunter Outlanders", "type": "game", "first_public": "2026-10-29", "date_source": "https://example.org/mho"},   // type 须为 game;first_public 写开玩日,须与预判观察的 playable_at 一致,且在预判观察日之后窗口内
  "terms": [{"term": "mho map", "source": "autocomplete", "first_seen": "2026-10-12"}],   // 每个说法都须在预判观察某项任务的 terms 里
  "forecast": "证据/mho-map/20261016T080100000000Z-5e6f7a8b-quick_forecast.json",   // 预判观察路径;与 screen 二选一,不能同写
  "reason": "预判过线"
}
```

```bash
python3 $S/ledger.py register-quick --input <上面的文件>      # 只收预判建议为 go 或 watching 的;skip、measure_rest 不登记
python3 $S/ledger.py update --slug mho-map --patch <{}> --ref 证据/mho-map/<quick_brief 观察>   # go 要最小版本简报素材(quick_brief),补进引用
python3 $S/settle.py --slug mho-map --verdict go --reason "预判过线" --biggest-unknown "开玩日会不会推迟"
```

登记后方向是 `found`，记 `"basis": "forecast"`，`evidence_refs` 先有预判观察与对象名量级观察两份；同时把原料池里这个游戏本身的待看原料（开玩日历里以对象名为键）标已用。开玩前结算只能 `--verdict go`、`watching` 或 `parked`，**不能 `rejected`**（没有速判观察可作依据；要否决，等复核日按现行路径）。`go` 与 `watching` 在 `settle.py` 结算时要求：最新预判观察的开玩日等于方向的 `object.first_public`；结算日在开玩前预判窗口内；6 国都测过（`skipped_geos` 为空）；对象名量级观察已在方向引用里、数对得上，并满足契约 10.6 的"预判对象名量的时效"（在预判之后测的、或比预判早上限天数以上的都拒收）；每项任务的倍数与参照条数按引用的参照路径向参照库重算一致；重算的 `suggestion` 与结论一致（`go` 只认 `go`，`watching` 只认 `watching`）；`go` 另要 `quick_brief`（≤ 3 天能做出、数据拿得到）。`parked` 直接放行。

#### 7.7.4 开玩日变化

```json
{
  "object": {
    "first_public": "2026-11-12",               // 新开玩日;只能是今天之后的日期(更早或当天拒收)
    "date_source": "官方延期公告 https://example.org/delay"   // 必须同时给;名称、类型登记后不能改
  }
}
```

```bash
python3 $S/ledger.py update --slug mho-map --patch <上面的文件>   # 预判方向在 found、watching、go 都可以;go 只许改 object
```

开玩前（`found`）改了开玩日：账本里还没有 `forecast` 块，旧预判观察的开玩日对不上，`settle.py` 会拦下；按新开玩日重做预判，写新的 `quick_forecast`，`ledger.py update --ref` 引用后再结算。已结算的（观察中、go）：`forecast.playable_at`、`forecast.review_at`、观察中的 `watch.expires_at`、还没开建的 go 的 `follow_up.launch_by`（开玩日前 1 天）自动顺延，`forecast.slipped_days` 累加；开玩后已经复核（`forecast.review` 非空）或复查过（`watch.checks` 非空）的，开玩日不能再改。累计推迟超过契约 10.6 的天数，看板提醒重新评估（7.7.7）。

#### 7.7.5 开玩后复核与复查

**预判 go：`review-forecast`。** 复核日（`forecast.review_at`，开玩日 + 7 天）起，对最小版本的每项任务测任务词的量（用 7.5 的方法，`trends_volume.py --term <任务词>`，`--term` 取预判观察里该任务的说法之一，一项任务一份，没写 `term` 的量级观察不算），各写一份 `quick_volume`；**须复核日当天或之后测、英文区 6 国都测**（预测是 6 国合计，只测美国会误报止损），然后：

```bash
python3 $S/ledger.py review-forecast --slug mho-map --ref 证据/mho-map/<任务一的量级观察> --ref 证据/mho-map/<任务二的量级观察>
```

```json
{
  "slug": "mho-map",
  "at": "2026-11-05",                           // 复核日(命令缺省取今天;复核日前拒收)
  "actual": 20000,                              // 每项任务各取复核日及之后测的最新量级(estimate_7d,6 国都测过),合计
  "forecast_p25": 90000,                        // 预测下四分位(开玩前结算时记下的)
  "ratio": 0.2222,                              // actual ÷ forecast_p25
  "stop": true,                                 // actual < forecast_p25 × 契约 10.6 的预判止损比例时为 true
  "by_task": [{"task": "map", "ref": "证据/mho-map/<量级观察>", "estimate_7d": 20000}],   // 每项任务用的是哪份
  "message": "预判失准,建议停止追加投入"        // stop 为 false 时写达到下四分位的几成、没低到止损线
}
```

`review-forecast` 只把上面这一块写进 `forecast.review`，不改状态；每个方向只复核一次。任务与说法按 `forecast.ref`（结算时那份预判观察）取，go 之后再挂的预判观察不改复核口径。缺哪项任务复核日或之后测的量级就拒收并写明；某项任务取到的最新量级里有没测的国家（`basis` 以"未查:"开头）也拒收，补测后再复核。**只对开玩前就判 go 的方向**（`model.basis` 为 `forecast`）：开玩前判观察中、开玩后按现行路径才判 go 的，当初下四分位没过线，拿它判失准没有意义，命令拒收。`stop` 为 true 时看板提示"预判失准"（7.7.7），这只是提示，要不要放弃由用户定；用户说放弃，再用 `ledger.py follow-up --status abandoned --reason …` 记（记了放弃，看板就不再提示）。

**预判观察中：`watch-check`。** 命令与 7.6 相同，另有三条：复核日前拒收；最新速判与量级观察都须是开玩日或之后看的，量级观察测的词（`trends_volume.py --term`）须是该方向登记的说法之一（对象名的量不算；没写 `term` 的量级观察也会被取到，所以预判方向的量级一律带 `--term`）；第一次复查把到期日改为复查日 + 观察天数（契约 10.6），之后建议按现行路径给（go、watching、`rejected:<门>`）。复查过才能结算：`settle.py` 给预判观察中的方向结算 `go`、或按 `volume`、`oneoff` 否决（这几种要读量级）时，要求复核日已到、`watch.checks` 至少一条，最新速判与登记说法的量级观察都是开玩日或之后看的（取量级同 `watch-check`，对象名的量不算），不满足就拒收；复核日过了还没复查时，`validate_ledger.py` 报"到了复核日，先跑 watch-check"，不再提示直接结算。

```bash
python3 $S/ledger.py watch-check --slug mho-map --ref 证据/mho-map/<开玩后的速判观察> --ref 证据/mho-map/<开玩后任务词的量级观察>
```

注意两个命令认的词不同：`watch-check` 取该方向**登记的说法**（`register-quick` 的 `terms`）里的量级观察；`review-forecast` 取**结算时那份预判观察里该任务的说法**（`tasks[].terms`，可以比登记的多，如预判写了 `mho map`、`mho interactive map`，只登记了 `mho map`）。用 `mho interactive map` 测的量级只能给 `review-forecast`，给 `watch-check` 会被当成别的词、取不到。

#### 7.7.6 记录里新增的字段

方向记录：`basis` 与 `forecast` 块（现行方向都没有；不写 `basis` 就是现行）。`forecast` 块在开玩前结算为 go 或观察中时由 `settle.py` 写入；`model` 是预判模型（`quick_model.forecast`），`volume`、`serp` 为 null；`validate_ledger.py` 只按账本里的 `forecast` 块重算 `model`，不回头重算倍数：

```json
{
  "basis": "forecast",                           // 预判方向;现行方向不写
  "object": {"first_public": "2026-10-29"},      // 未来的开玩日
  "forecast": {
    "ref": "证据/mho-map/20261016T080100000000Z-5e6f7a8b-quick_forecast.json",   // 结算时用的预判观察(引用里最新的一份)
    "playable_at": "2026-10-29",                 // 开玩日;开玩日变化时跟着变
    "object_volume_pre": {"US": 600000},         // 对象名开玩前月搜索量
    "tasks": [{"task": "map", "r_p25": 0.15, "r_median": 0.2}],   // 各任务倍数
    "forecast_p25": 90000,                       // 下四分位预测月搜索量
    "forecast_median": 120000,                   // 中位数预测月搜索量
    "review_at": "2026-11-05",                   // 复核日 = 开玩日 + 7 天
    "review": null,                              // review-forecast 之后是 {at, actual, forecast_p25, ratio, stop, by_task}
    "slipped_days": 0                            // 开玩日累计推迟的天数
  },
  "model": {
    "basis": "forecast",                         // 预判模型;现行模型没有这个键
    "assumptions_version": "2026-10-16.q4",
    "object_volume": 600000,                     // 对象名开玩前月搜索量(各国合计)
    "us_share": 1.0,                             // 美国占对象名量的比例,用来分美国访问
    "aio_factor": 0.6,                           // 预判一律按在场未答完
    "forecast_p25": 90000,
    "forecast_median": 120000,
    "scenarios": {"low": {}, "base": {}, "high": {}},          // 下四分位倍数下三档:share、visits、us_visits、revenue
    "median_scenarios": {"low": {}, "base": {}, "high": {}},   // 中位数倍数下三档
    "passes": true,                              // 下四分位基准 ≥ 门槛
    "passes_median": true,                       // 中位数基准 ≥ 门槛
    "single_site_100": false,                    // 基准预计收入是否 ≥ $100
    "threshold_visits": 10000,
    "searches_needed": 83334,                    // 基准过线所需的站点预测月搜索量

    "suggestion": "go"                           // go | watching | skip | measure_rest
  },
  "follow_up": {"launch_by": "2026-10-28"},      // go 的建议最晚上线日 = 开玩日前 1 天(现行是判 go 后 7 天)

```

观察：`quick_reference`、`quick_forecast` 两类（7.7.1、7.7.2），`stage` 都是 `quick`；`quick_volume` 多一个可选的 `term`，记测的是哪个词（对象名或任务词）。

#### 7.7.7 看板提醒

`report_status.py` 在原有提醒之外加五类，只读账本、原料池和参照库；`--json` 里在 `quick` 下：

```json
{
  "forecast_window": [{"object": "Monster Hunter Outlanders", "stage": "Original", "playable_at": "2026-10-29", "days_ahead": 13}],   // 可预判:待看原料里开玩日在预判窗口内的
  "forecast_reviews_due": [{"slug": "mho-map", "state": "go", "review_at": "2026-11-05"}],   // 复核到期:go(开玩前预判的,没复核过)或观察中(没复查过),到了复核日
  "forecast_warnings": [{"slug": "mho-map", "actual": 20000, "forecast_p25": 90000}],        // 预判失准:复核 stop 为 true、没放弃的
  "forecast_slipped": [{"slug": "mho-map", "first_public": "2026-11-12", "slipped_days": 14}],   // 开玩日推迟:累计超过 10.6 的天数的观察中或 go
  "references_due": [{"object": "WARDOGS", "task": "map", "action": "add", "due": "2026-09-05"}]   // 补参照:add = 有 forecast 块的方向开玩满窗口长度、参照库里还没有这款游戏这项任务;update = 参照库里 full_60_days 为 false、开玩满 60 天
}
```

文字版每类一行：`  可预判 <对象>:<开玩日>,还有 N 天`、`  复核到期 <方向>:<复核日>,…`、`  预判失准 <方向>:实测 X / 预测 Y,建议停止追加投入`、`  开玩日推迟 <方向>:累计 N 天,现为 <日期>,请重新评估`、`  补参照 <对象> <任务>` 或 `  更新参照 <对象> <任务>`；预判 go 的"【立即建站】"行在方向名后加 `(开玩前预判)`，`pending_go[].forecast` 为 true。看板每次运行都重新校验整个参照库，库里有一条不合规就整个看板拒收。
