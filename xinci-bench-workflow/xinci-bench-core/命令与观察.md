## 2. 运行清单

```bash
python3 $S/run_log.py --plan
python3 $S/run_log.py --skill xinci-bench-scan --run-id run-20261014-a --round 1 --max-rounds 3 \
  --source-kind legacy --seed-value "种子池 legacy 前 16 个" --outcome started --next-step scan
python3 $S/run_log.py --finish --run-id run-20261014-a --outcome completed --semrush-calls 5 \
  --direction-touched example-county --note "16 个初核,2 个登记"
```

- 每阶段先写 started，结束用 `--finish`（completed / blocked / skipped），脚本推导下一步。
- found 已有 ≥ 3 个时 `--plan` 返回 `scan_outcome=skipped`：照样先写 scan started，再 `--finish --outcome skipped`。
- `--semrush-calls` 只填本条新增的调用数。
- `--plan` 还给出今天两条道合计的 Semrush 用量：`semrush_calls_today`、`semrush_daily_limit`（100）、`semrush_left_today`、`semrush_stop`（今天已用到 90 次时为 true，此时不再开始花 Semrush 的步骤）。

## 7. 新词快道

### 7.1 运行清单

```bash
python3 $S/run_log.py --plan --lane quick
python3 $S/run_log.py --skill xinci-bench-quick --run-id quick-20261014-a --round 1 --max-rounds 1 \
  --source-kind quick --seed-value "自动补全、Trends 飙升、SteamCharts、Product Hunt" --outcome started --next-step quick
python3 $S/run_log.py --finish --run-id quick-20261014-a --outcome completed --semrush-calls 1 --note "扫 40 条原料,登记 1 个"
```

快道一次运行只有一个阶段：`round` 与 `max-rounds` 固定为 1，`source-kind` 固定为 `quick`；每天最多开 1 轮，`--plan --lane quick` 给出 `quick_rounds_today`、`quick_rounds_per_day`、`quick_new_round_allowed`，为 false 时不开新的一轮（恢复受阻的不算）；受阻用 `--outcome blocked`，之后同一运行编号再 `--finish`。快道与标杆道的未完成运行互不阻塞。

### 7.2 扫信号与原料池

```bash
python3 $S/suggest_snapshot.py --object "Grow a Garden 2"          # 对象名 + 空格,以及对象名 + 10 个任务词
python3 $S/suggest_snapshot.py --query "grow a garden 2 calculator"
python3 $S/suggest_snapshot.py --object "Grow a Garden 2" --gl gb  # 地区性对象查别的英文国家:gb | ca | au | nz | ie
python3 $S/suggest_snapshot.py --derivative "neal.fun"            # 飙升词里冒出的陌生站名:<站名> alternative / like / unlimited 各查一次,输出同 --object
python3 $S/write_observation.py --input <quick_signal 观察文件>
python3 $S/quick_pool.py add --observation 证据/_quick/<文件名>
python3 $S/wiki_releases.py --output <scratchpad>/wiki_releases.json  # 最近 14 天已上线与未来 30 天要上线的新游戏,按浏览量取前 20(items 并进 quick_signal)
python3 $S/suggest_discover.py --output <scratchpad>/discover.json     # 4 个前缀 × a–z 查补全找新对象,第一次只建基线(items 并进 quick_signal)
python3 $S/suggest_discover.py --letters abc --patterns "tier list,codes for" --output <scratchpad>/discover.json  # 只跑一部分
python3 $S/upstream_fetch.py --output <scratchpad>/upstream.json      # Product Hunt、Show HN、GitHub、联邦公报近 7 天,非政策对象各查 1 次补全(items 挑过再并进)
python3 $S/upstream_fetch.py --sources producthunt,github --limit 10 --on 2026-10-19 --output <scratchpad>/upstream.json
python3 $S/quick_pool.py pending --top 10                          # 按优先级取首屏速判的 10 个(还没到开玩日的不列)
python3 $S/quick_pool.py upcoming --days 14                        # 即将开玩:开玩日在今天之后 14 天内的原料
python3 $S/quick_pool.py expire                                     # 7 天没拿到"有人在搜"证据的标 expired
python3 $S/quick_pool.py mark --id <原料 id> --status used
python3 $S/quick_pool.py reject --term "<说法>" --gate occupied --observation 证据/<方向>/<速判观察> --seed-domain <占位小站>
```

Trends 飙升词在 Trends 页面里用 `scripts/trends_fetch.js` 全文加一行 `await xinciTrendsRising({term: "beta", cat: 8})` 执行，种子词与 `cat` 照 `run_log.py --plan --lane quick` 输出里的 `rising_seeds` 写（`cat: 8` 是游戏分类，`cat: 0` 是不加分类），每轮 6 个、两次执行之间隔 ≥ 30 秒、遇 429 停下（`数据采集.md` §7.2）。返回的 `rising[].rising` 是百分比或 `"breakout"`，可原样写进原料 `rising`。

```json
{
  "rising_seeds": [                // run_log.py --plan --lane quick 输出里的一项:今天的 6 个种子,按天轮换,同一天跑几次都一样
    {"term": "beta", "cat": 8},        // 固定种子;term 为种子词,cat 为 Trends 分类(8 = 游戏)
    {"term": "playtest", "cat": 8},    // 固定种子
    {"term": "tier list", "cat": 8},   // 游戏任务词 3 个,按天轮换
    {"term": "codes", "cat": 8},
    {"term": "map", "cat": 8},
    {"term": "generator", "cat": 0}    // 非游戏 1 个(0 = 不加分类),和当天的游戏任务词不重复
  ]
}
```

### 7.7 上线前预判

#### 7.7.1 取参照

参照只测美国，开玩后凑满任务词窗口才写（取数日 ≥ 开玩日 + 窗口长度，否则 `build` 拒收：开玩后曲线不够长）。三步：

```bash

```

```

起 = 开玩日前第 9 天；止 = 开玩日 + 59 天与取数日前一天里较早的那天（取数日当天的点还没走完，不要）。取数日太早、曲线还没走出来时命令拒收。

在 Trends 页面里（每次执行都带 `trends_fetch.js` 全文），同一个锚词各查一次，两次间隔 ≥ 35 秒：

    "task_window": ["2026-09-04", "2026-09-17"],   // 开玩后 60 天内,恰好 14 天,终点早于观察日
    "task_ratio": 0.1447,                          // 任务词窗口均值 ÷ 锚词同期均值
    "full_60_days": false,                         // 观察日 ≥ 开玩日 + 60 天才可写 true;此例观察日 10-16 不到 10-21,写 false
    "object_volume_pre": 8623,                     // = anchor_volume × object_ratio(误差 ≤ 1)
    "task_volume_post": 1172,                      // = anchor_volume × task_ratio(误差 ≤ 1)
    "r": 0.1359,                                   // = task_volume_post ÷ object_volume_pre,四位小数
    "assumptions_version": "2026-10-17.q5",        // 写入时的假设表版本;写入时须等于当前版本

      "object_window": [9, 3],                     // 对象名窗口:开玩日前第 9 到第 3 天
      "task_days": 14,                             // 任务词窗口长度(天)
      "task_span": 60                              // 任务词窗口须在开玩后多少天内;满多少天算 full_60_days
    }
  }
}
```

**观察按自己记下的口径校验。** `assumptions_version` 与 `params` 记的是写入当时的假设表（契约 10.6、10.9）。

- **写入时**：`quick_reference.py build` 自己按当前假设表填这两项，不手写；`write_observation.py` 拒收与当前假设表不一致的（不能自己编口径）。
- **读回时**：`write_observation.read` 先核 `params` 的形状（键恰好是上面三项、值是正整数或窗口列表），再按观察自己的 `params` 校验窗口与天数，不拿当前假设表比；假设表后来改了，历史参照照样读得进来。
- **参照库只用当前口径的**：`quick_reference.py summary`、`quick_forecast.py` 取倍数、看板，都只用 `params` 与当前假设表相同的参照。口径不同的不进库、不混着算，也不算坏参照（不拒收，`summary` 里直接不出现）；"参照不可用"里照写，原因是 `口径已变,需重测(写于 <假设表版本>)`（看板 `references_unusable`、`quick_forecast.py` 输出的"参照不可用"与观察 `points` 写法相同，见 7.7.7）。要继续用这款游戏这项任务的参照，用当前口径重新 `quick_reference.py build` 一条。

- **预判观察自己的口径过时**（它的 `params`：开玩日窗口、参照条数下限、门槛、份额、系数、只测美国的截断线，不等于当前假设表）→ 拒收 `口径已变,重做预判`。处理：对象名量级观察若不是预判当天或之前 2 天内测的（契约 10.6 的"预判对象名量的时效"，重新预判时按重新预判那天算），先重测对象名的量（`trends_volume.py --term <对象名>`，见上）；再重新 `quick_forecast.py` 生成新的预判观察；把新的预判观察和（重测过的）对象名量级观察都用 `ledger.py update --ref` 挂进方向引用（预判观察引用的对象名量级观察不在方向引用里，结算也会拒收）；然后结算。
- **引用的某条参照口径过时**（参照的 `params`：对象名窗口、任务词窗口长度与范围，不等于当前假设表）→ 拒收 `参照 <路径> 口径已变,需重测(写于 <版本>):…`；看板"参照不可用"与 `quick_forecast.py` 输出的"参照不可用"也会列出这样的参照。处理：先用当前口径重新 `quick_reference.py build` 这些参照（7.7.1），再按上一条重新预判。
- 改的是哪些数就触发哪一条：只改门槛、份额、系数，参照仍然有效；只改参照窗口，预判观察自己的口径不变，但它引用的参照作废。

搁置不受此限：搁置只尝试写模型，被拒就把 `model` 记空，照样放行。

预判是方向登记**之前**的步骤，所以预判观察的 `slug` 是拟用的方向名。预判方向在结算前（`found`）不能用 `ledger.py quick-preview`：它读的是开玩后的当前量，预判方向没有，会拒收"缺当前月搜索量"；看预判结果就读 `quick_forecast.py` 的输出（或生成的观察）。

开玩前（`found`）改了开玩日：账本里还没有 `forecast` 块，旧预判观察的开玩日对不上，`settle.py` 会拦下；按新开玩日重做预判，写新的 `quick_forecast`，`ledger.py update --ref` 引用后再结算。已结算的（观察中、go）：`forecast.playable_at`、`forecast.review_at`、观察中的 `watch.expires_at`、还没开建的 go 的 `follow_up.launch_by`（开玩日前 1 天）自动顺延，`forecast.slipped_days` 累加；开玩后已经复核（`forecast.review` 非空）或复查过（`watch.checks` 非空）的，开玩日不能再改。开玩前搁置的（`parked`）也没有 `forecast` 块，只改 `object.first_public`；开玩后判 go 的 14 天窗口按新开玩日算（7.7.5）。累计推迟超过契约 10.6 的天数，看板提醒重新评估（7.7.7）。

#### 7.7.5 开玩后复核与复查

**预判 go：`review-forecast`。** 复核日（`forecast.review_at`，开玩日 + 7 天）起，对最小版本的每项任务测任务词的量（用 7.5 的方法，`trends_volume.py --term <任务词>`，`--term` 取预判观察里该任务的说法之一，一项任务一份，没写 `term` 的量级观察不算），各写一份 `quick_volume`；**须复核日当天或之后测、英文区 6 国都测**（预测是 6 国合计，只测美国会误报止损），然后：

```bash
python3 $S/ledger.py review-forecast --slug mho-map --ref 证据/mho-map/<任务一的量级观察> --ref 证据/mho-map/<任务二的量级观察>
```

```json
{
  "slug": "mho-map",                            // 方向名
  "at": "2026-11-05",                           // 复核日期:命令总按今天(UTC)算,没有 --on 参数;今天在复核日之前就拒收
  "actual": 20000,                              // 每项任务各取复核日及之后测的最新量级(estimate_7d,6 国都测过),合计
  "forecast_p25": 90000,                        // 预测下四分位(开玩前结算时记下的)
  "ratio": 0.2222,                              // actual ÷ forecast_p25
  "stop": true,                                 // actual < forecast_p25 × 契约 10.6 的预判止损比例时为 true
  "by_task": [                                  // 每项任务用的是哪份
    {
      "task": "map",                            // 任务类型
      "ref": "证据/mho-map/<量级观察>",          // 用到的量级观察路径
      "estimate_7d": 20000                      // 它的英文区月搜索量
    }
  ],
  "message": "预判失准,建议停止追加投入"        // stop 为 false 时写达到下四分位的几成、没低到止损线
}
```

`review-forecast` 只把上面这一块写进 `forecast.review`，不改状态；每个方向只复核一次。任务与说法按 `forecast.ref`（结算时那份预判观察）取，go 之后再挂的预判观察不改复核口径。缺哪项任务复核日或之后测的量级就拒收并写明；某项任务取到的最新量级里有没测的国家（`basis` 以"未查:"开头）也拒收，补测后再复核。**只对开玩前就判 go 的方向**（`model.basis` 为 `forecast`）：开玩前判观察中、开玩后按现行路径才判 go 的，当初下四分位没过线，拿它判失准没有意义，命令拒收。`stop` 为 true 时看板提示"预判失准"（7.7.7），这只是提示，要不要放弃由用户定；用户说放弃，再用 `ledger.py follow-up --status abandoned --reason …` 记（记了放弃，看板就不再提示）。

**预判观察中：`watch-check`。** 命令与 7.6 相同，另有三条：复核日前拒收；最新速判与量级观察都须是开玩日或之后看的，量级观察测的词（`trends_volume.py --term`）须是该方向登记的说法之一（对象名的量不算；没写 `term` 的量级观察也会被取到，所以预判方向的量级一律带 `--term`）；第一次复查把到期日改为复查日 + 观察天数（契约 10.6），之后建议按现行路径给（go、watching、`rejected:<门>`）。复查过才能结算：`settle.py` 给预判观察中的方向结算 `go`、或按 `volume`、`oneoff` 否决（这几种要读量级）时，要求复核日已到、`watch.checks` 至少一条，最新速判与登记说法的量级观察都是开玩日或之后看的（取量级同 `watch-check`，对象名的量不算），不满足就拒收；复核日过了还没复查时，`validate_ledger.py` 报"到了复核日，先跑 watch-check"，不再提示直接结算。

```bash
python3 $S/ledger.py watch-check --slug mho-map --ref 证据/mho-map/<开玩后的速判观察> --ref 证据/mho-map/<开玩后任务词的量级观察>
```

注意两个命令认的词不同：`watch-check` 取该方向**登记的说法**（`register-quick` 的 `terms`）里的量级观察；`review-forecast` 取**结算时那份预判观察里该任务的说法**（`tasks[].terms`，可以比登记的多，如预判写了 `mho map`、`mho interactive map`，只登记了 `mho map`）。用 `mho interactive map` 测的量级只能给 `review-forecast`，给 `watch-check` 会被当成别的词、取不到。

**预判后搁置的方向：开玩后判 go。** 预判登记后在开玩前搁置的方向（`basis` 为 `forecast`、状态 `parked`）没有 `forecast` 块、复核日和观察期。开玩后要判 go，走现行路径：开玩后重做速判（`quick_screen`）、测登记说法的量级（`trends_volume.py --term <登记的说法之一>`）、写最小版本简报素材 `quick_brief`，用 `ledger.py update --slug <方向> --patch <{}> --ref <各观察>` 挂上，再 `settle.py --verdict go`。`settle.py` 对这类方向的 go 另加两条（契约 10.9），不满足就拒收：

- 最新速判的观察日须在开玩日当天到开玩后 14 天内（相当于开玩后重新判一次 Q1；开玩日取方向的 `object.first_public`，14 天是契约 10.6 里游戏"真新"的窗口）。开玩前看的不算，开玩后重新速判。窗口已过的：游戏推迟了，要在新开玩日到来前用 `ledger.py update` 记下新开玩日（7.7.4，同时给 `date_source`），窗口跟着新开玩日走；没推迟的，这个方向只能否决或继续搁置。
- 登记说法的最新量级观察（对象名的量不算）若有，观察日须在开玩日当天或之后。

不要求复核日和复查（搁置没有观察期）。**否决不受这两条限制**：`not_new`、`occupied`、`answered`、`scope`、`volume`、`oneoff` 照现行规则，开玩前就看到专做本作的站，当场否决反而省事。观察中的预判方向（上面 `watch-check` 那段）规则不变。
