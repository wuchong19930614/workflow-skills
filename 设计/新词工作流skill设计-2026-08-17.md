## 1. 范围与已定决策

本套 skill 只做一件事:发现并验证**新兴/全新**的英文 Google 搜索词,产出"这个词能否支撑一个独立 SEO 站"的决策书。

已确认的边界决策:

- **只做新兴词**:目标词是刚诞生或正在形成中的搜索词。成熟存量词不在范围内(账本预留 `lane` 字段作扩展点,但本设计不涉及)。
- **完全独立新建**:逻辑上吸收旧四个 skill 的验证成果(闸门、陷阱、失败案例、反原则),运行时不调用、不引用旧 skill 的任何文件;数据目录与旧系统零交集。
- **终点到建站决策为止**:终产物是决策书。注册域名、建站、发布内容全部是用户的人工动作,skill 一律不执行。
- **双环境兼容**:同一份 skill 文件在 Codex CLI 和 Claude Code 都能使用。
- **人工驱动**:工作流由用户手动推进。skill 不自我调度、不设默认节奏参数、不自动执行状态转移;一切时间字段只作事实记录与汇报,判断与触发永远归用户。

## 2. 总体架构

### 2.1 单元构成与命名

6 个单元:5 个 skill + 1 个共享核心目录。家族前缀 `xinci-`(拼音"新词"),与旧 `keyword-*` 家族明确区隔,避免触发混淆。

```
xinci-status    状态看板:只读账本,汇报全局事实,不推荐不调度
xinci-scan      扫描发现:双入口捕获新词候选,当场初筛(G1–G5)
xinci-track     追踪复查:对用户指定的追踪候选做复查,提议状态转移
xinci-qualify   深度认定:对形成确认的候选做 G6–G8 + 100 分制评分
xinci-decide    建站决策:页面地图 + 收入模型 + go/no-go,产出决策书
xinci-core/     共享核心:契约、闸门、schema、脚本(唯一来源,无 SKILL.md,非 skill)
```

各 skill 职责单一:status 只读、scan 只捕获初筛、track 只复查、qualify 只认定、decide 只决策。任何判断标准都不写在 skill 内,一律指向 xinci-core 的唯一定义。

### 2.2 部署与双环境兼容

- 正本(唯一可编辑副本)放 `/Users/vito.wu/IdeaProjects/workflow-skills/`,每个 skill 一个子目录(`xinci-status/`、`xinci-scan/`、`xinci-track/`、`xinci-qualify/`、`xinci-decide/`、`xinci-core/`),连同本设计文档一起纳入该仓库的 git 版本控制。
- 通过 symlink 让两个环境发现同一份正本:`~/.codex/skills/xinci-* → /Users/vito.wu/IdeaProjects/workflow-skills/xinci-*`,`~/.claude/skills/xinci-*` 同理。两环境读同一份文件,不存在副本。
- SKILL.md 采用两环境通用的最小格式:frontmatter 只含 `name` 与 `description`;description 中文为主,附英文触发词。
- 互相引用一律用**绝对路径 + 纯文字**("接下来按 xinci-qualify 的流程执行,其 SKILL.md 位于 …"),不使用 `$skill` 或 Skill 工具等环境特有语法。
- 脚本统一 `python3 <绝对路径>` 调用,不依赖任一环境的运行时特性。

### 2.3 数据目录

数据与代码同仓库,住 `workflow-skills` 下的独立子树,与旧系统数据完全隔离:

```
/Users/vito.wu/IdeaProjects/workflow-skills/数据/新词工作流/
├── 账本/
│   └── 候选账本.json      registrar 独占写入;生命周期状态的唯一事实来源
├── 证据/
│   └── <候选slug>/<日期>-<事件>.json   各 skill 写观察记录,只描述不裁决
├── 决策书/
│   ├── <候选slug>.md      给落地网站内容的 AI 读(唯一事实来源)
│   └── <候选slug>.html    给人读的渲染视图(与 md 同批产出,见 7.3)
└── 运行/
    └── <日期>-<skill>.json   每次运行一个小 JSON:日期、skill、打开过的来源、触及的候选、计费调用数;不写过程日志
```

**数据极简原则**(用户要求):所有数据文件只写简单清晰、服务于决策的内容——不写仪式性字段、不写过程流水账、不为"显得完整"而填充。schema 里每个字段都必须回答得出"哪个决策会用到它";观察记录写要点,不写转录。

继承旧系统"观察与裁决分离"的原则:`证据/` 里的文件只记录看到了什么,不携带任何读起来像裁决的字段;生命周期状态只存在于 `账本/`,只能由 registrar 脚本写入。

代码与数据分离但同仓库:skill、契约、脚本在仓库根的 `xinci-*/` 子目录;运行产物统一在 `数据/` 子树,互不混放。

## 3. 候选生命周期状态机

### 3.1 状态与转移图

```
(新候选)
   │ xinci-scan 捕获
   ▼
captured ──G1–G5 全过──→ screened ──登记 expiry──→ tracking ──形成达标──→ formation_confirmed
   │                        │                        │    │                      │
   │任一闸门否决             │窗口以天计               │    │expiry 过,用户确认      │ xinci-qualify
   ▼                        │(快道)                  │    ▼                      ▼
rejected                    │                        │  expired          qualified / disqualified
                            ▼                        │                          │
                     xinci-decide 快速模式            │复查中 G1 翻转             │ xinci-decide
                            │                        │或竞品占位                 ▼
                            ▼                        ▼              ┌───────┬────────┬──────┐
                     fast_grab_ready              rejected          ▼       ▼        ▼      ▼
                            │                                 build_ready pilot_ready hold no_site
                            │用户建站/放弃                          │        │
                            ▼                                      └───┬────┘
                     built / expired                                   │用户建站
                                                                       ▼
                                                                     built
```

补充转移:

- 任何非终态候选可由用户转 `withdrawn`(主动撤回)或 `superseded`(被更好的措辞候选取代,记录指向新候选)。
- `hold`(证据可能在未来成熟)可由用户送回 xinci-qualify 或 xinci-decide 重审。
- `built` 的快道候选,词若被证明耐久,可由用户发起转回 `tracking`,走完整认定升级成正经全站(升级通路,修复旧 radar play 分配后无下文的断头路)。

终态词汇:`rejected` / `expired` / `superseded` / `withdrawn` / `built`。

**快道是显式分支而非例外**:窗口期候选从 `screened` 直达决策,但决策书必须列明跳过的闸门、expiry 与风险确认(见 7.2)。设计依据:全新词的窗口以天计(旧系统实测竞品 4 天到位),主管道数周的观察期在结构上无法兑现这类机会;而快道赌注小且可逆(一个域名 + 48 小时内可发布的页面),赌注大小与闸门严格度成比例。

### 3.2 各转移的证据要求

状态转移只能由 registrar 脚本执行,每个转移校验证据齐备性,缺证据即拒绝:

- `→ captured`:精确观察措辞(禁转述)、来源 URL、时间戳。
- `captured → screened`:G1–G5 逐项结论,每项附"SERP 上实际看到什么";窗口评估(以天/周/月计,附推理)。
- `captured/screened → rejected`:失败闸门编号 + 现场证据。
- `screened → tracking`:expiry 日期(附推理)+ 失效条件清单 + 形成信号基线(当前叫法、当前 SERP 快照要点)。
- `screened → fast_grab_ready`:快道决策书(见 7.2),含跳过闸门清单、expiry、用户风险确认。
- `tracking → formation_confirmed`:至少 2 次带日期的独立观察;命名已定型;至少 1 项需求形成信号(自动补全出现 / 首批 Semrush 行 / 社区讨论持续增长);最近一次复查重跑过 G1。
- `tracking → expired`:expiry 已过且用户确认;或失效条件命中。
- `formation_confirmed → qualified`:G6–G8 全过 + 评分 ≥80 + 完整竞争审计(含至少一个竞品的实测 footprint)。
- `formation_confirmed → disqualified`:决定性缺口记录(哪一项、差多少)。
- `qualified → build_ready / pilot_ready / hold / no_site`:完整决策书(见 7.1);pilot 决策不得携带全站分数。
- `* → built / withdrawn / superseded`:用户动作,registrar 记录即可。

### 3.3 时间字段:只记录,不调度

账本为每个候选记录三个时间事实:

- `first_observed_at`:首次捕获时间;
- `last_checked_at`:最近一次复查时间;
- `expiry`:窗口/形成失效日期(观察者判断并附推理)。

约束(本设计的核心修正,用户 2026-08-17 明确要求):

- **没有** `next_check_at`、默认复查间隔、调紧/放宽规则等任何调度机制;
- skill 被调用时只**汇报**时间事实("该候选 12 天未复查,expiry 还剩 5 天"),不据此自动做任何事;
- expiry 过期**不自动**转 `expired`:skill 提议,用户确认后 registrar 才执行;
- 复查哪些候选、何时复查、何时推进到下一阶段,全部由用户决定。

## 4. 闸门体系

### 4.1 八道闸门定义

一份定义,存于 `xinci-core/闸门契约.md`,所有 skill 按路径引用,零复制:

- **G1 Google 直接回答 = 硬否决**。美区桌面、未登录搜索精确词。首屏若已完成任务(featured snippet 完整作答 / 原生计算器、转换器组件 / knowledge panel / 把任务做完的 AI Overview)即否决。最便宜、杀伤最大,任何阶段都最先跑。仅摘要而任务仍需工具或流程的 AI Overview 不构成否决。
- **G2 完整首页结构阅读**。读完第一页,再到第二页或明显质量断层。禁止用 top-3 判断竞争(保留旧系统 page-2 强竞品的失败案例作为规则出处)。视频占屏但任务非视频、维基/大媒体霸榜、大品牌首页(非内页)霸榜均为拒绝信号;内页、小站、论坛帖、明显老化内容占比高则放行。
- **G3 exact-task completion**。按竞品"做什么"分类,永不按"是谁"。两个以上免费结果把任务做好且有持续可见度即拒绝。下结论前必须实测至少一个竞品的真实 footprint(authority、流量、词量、增速)——存在不等于占据。
- **G4 任务可完全在线完成**。需要实地检查、物理采样、持照人员到场的任务一票否决,指标再好也不看(保留旧系统 16,250 月搜、KD 13 的屋顶检查词失败案例)。
- **G5 陷阱类别检查**。先于 G2 结构阅读执行(陷阱类别的特征是"过 G2、死 G3",先读结构必然误判)。初始清单移植两类:新发布 AI 模型(保留 Qwen VRAM 计算器全案:约 8 个免费工具、无抢跑窗口、耐久性以周计)、纯品牌名发布(无任务可完成)。清单可增长:每次出现"过 G2 死 G3"的新模式即追加,记录实际观察而非只记泛化结论。
- **G6 商业闭环**。明确付费者 + 被迫或重复的任务 + 自助变现路径 + 最终 $1,000/月收入上限的合理性。
- **G7 耐久性**。版本更替风险(为一个版本买的域名随下一版过期)、官方答案风险(厂商/平台自己发布答案)、一周好奇 vs 重复任务的区分。
- **G8 簇广度**。全站要求 ≥3 个任务型查询 × ≥2 个独立 family;达不到只配 pilot 或 no_site。全站页面地图要求 ≥12 个任务互异页面 × ≥3 个簇 + ≥1 个自助产品资产。

### 4.2 时间光谱与适用矩阵

每个候选携带 `first_observed_at`,其年龄决定哪些闸门有意义(修复旧 radar 与 new-strong-80 之间的灰区):

- **窗口期(约 0–14 天)**:适用 G1–G5。只要浏览器证据;禁用 KD、KGR、Trends(天级新词无年度曲线无月volume,Semrush 查无是本赛道的定义属性,不是缺陷)。
- **形成期(约 15–90 天)**:复查 G1–G5 + 观察形成信号(命名定型、自动补全、首批 Semrush 行、讨论增长、竞品到位速度)。允许轻量 Semrush 探针,仅限能改变决策的查询。
- **确认期(约 90 天+,或提前达标)**:适用 G6–G8 + 100 分制评分,用早期 Semrush 数据 + 完整竞争审计。

年龄分段是**参考刻度而非调度器**:何时把候选送进下一阶段由用户判断,分段只约束"此刻哪些证据是可得且有意义的"。

## 5. 各 skill 规格

### 5.1 xinci-status 状态看板

- **触发**:"看下新词工作流状态"、"账本里有什么"。
- **输入**:无(读账本)。
- **职责**:只读汇报——各状态候选数;每个候选的年龄、`last_checked_at`、expiry 余量;expiry 已过但未处理的候选;缺证据引用的异常记录。纯事实陈述,不推荐动作、不安排日程、不执行转移。
- **产出**:一份状态报告(终端输出即可,不落盘)。
- **硬规则**:零写入;账本是唯一事实来源,不从证据文件反推状态。

### 5.2 xinci-scan 扫描发现

- **触发**:"扫一下今天有什么新词"、"发现新机会"、"跑一轮雷达"。
- **输入**:可选的来源偏好或变化线索。
- **职责**:双入口发现 + 当场初筛。
  - 信号面:真浏览器直读 Reddit rising / Product Hunt / Hacker News / X trending / 即刻 / 应用商店新品 / 厂商发布博客,轮换选源,覆盖优先。继承并保留原则出处:判断"这像不像人们会搜的东西"必须来自读真实页面,API 结果集恰恰剥掉所需语境(旧系统有实测失败案例)。
  - 变化面:从有日期的法规/平台/技术/成本/术语/工作流变化出发,推导受影响付费者与被迫任务,翻译成自然搜索语言假设。
  - 初筛:G1 最先(最便宜杀伤最大),G5 陷阱检查先于 G2 结构阅读,G1–G5 当场跑完。
  - 窗口评估:估计窗口以天/周/月计(可发现性、多少人能做出同样页面、官方答案多久出现),据此提议快道或 tracking。
- **产出**:每个候选一份 captured/screened 观察 JSON + registrar 注册;run 清单记录打开过哪些来源。空扫描是合法产出,如实报告优于凑数。
- **硬规则**:精确措辞 + 来源 URL + 时间戳,缺一不注册;每个候选必写 expiry;未在本次会话打开的来源不得声称已检查;区分"发布"与"一时热闹"——只产生一周好奇、没有重复任务的东西直说不值得,不进清单。

### 5.3 xinci-track 追踪复查

- **触发**:"复查追踪清单"、"看看候选 X 现在什么情况"。
- **输入**:用户指定的候选(或全部 tracking 状态候选)。
- **职责**:对指定候选逐个复查四件事——SERP 变化(竞品到位?官方答案出现?)、命名定型进度、需求形成信号、expiry 余量。每次复查**必重跑 G1**(新词 SERP 突变快,上次的结论会腐烂)。三种提议出口:继续追踪(更新观察)/ 提议 `formation_confirmed` / 提议 `expired` 或 `rejected`。
- **产出**:每候选一份复查观察 JSON;更新 `last_checked_at`;向用户提交转移提议清单,用户确认后由 registrar 执行。
- **硬规则**:提议与执行分离——本 skill 永不直接改状态;expiry 已过的候选必须给出明确提议(expired 或说明为何值得用户续期),不许沉默跳过;形成期 Semrush 探针仅限能改变决策的查询。

### 5.4 xinci-qualify 深度认定

- **触发**:"认定候选 X"、"X 值不值得建站"。
- **输入**:`formation_confirmed` 状态的候选(registrar 强制,其他状态拒收)。
- **职责**:G6–G8 + 完整竞争审计(全 top-10 按"做什么"分类;实测至少一个竞品 footprint)+ 意图簇枚举(能否撑一个站)+ 100 分制评分。评分权重(存于评分契约,继承旧 new-strong-80 思想):触发真实性 15 / 被迫付费任务 12 / 搜索语言形成 8 / 竞争 30 / 变现对齐 15 / 收入可行性 20;红队扣分后 ≥80 为过线。
- **产出**:评分表 + 逐项证据引用;`qualified`(附分数)或 `disqualified`(附决定性缺口)提议,用户确认后注册。
- **硬规则**:低 KD 只触发 exact-task 完成度检查,不作为鼓励(保留旧系统 KD 14 对实测竞争 89 的背离案例);veto 清除后仍须过数值闸门;79 分不算过,永不为凑候选降门槛。

### 5.5 xinci-decide 建站决策

- **触发**:"给 X 出建站决策"、"能不能建站"。
- **输入**:`qualified` 候选(完整模式)或 `screened` 候选(快道模式,仅限窗口评估为天级的候选)。
- **职责**:
  - 完整模式:页面地图(G8 标准)+ 收入三情景(downside/base/upside,base ≥$1,000/月、无主动销售、保守假设、所需流量不超 owned-intent 估计)+ 风险清单(技术/合规/免费与付费替代/维护负担/数据成本)+ 红队复核 + go/no-go。
  - 快道模式:轻量决策书(见 7.2),核心是把跳过的闸门与风险明码标价。
- **产出**:go 决策(build_ready / pilot_ready / fast_grab_ready)产出决策书两份——`<slug>.md`(给 AI)与 `<slug>.html`(给人),存入 `决策书/`(约定见 7.3);no-go 结论(hold / no_site)不出决策书,只在账本记录决定性理由(数据极简原则)。registrar 注册对应状态。
- **硬规则**:不注册域名、不花钱、不发布——决策书交付即停,后续是用户动作;pilot 决策不得声称全站分数;每份决策书必含失效条件(出现什么信号即放弃)与下一步人工动作清单。

## 7. 决策书模板要点

### 7.1 完整决策书(build_ready / pilot_ready)

必含章节:词与精确措辞;站点论点(一句话:给谁、完成什么任务、凭什么赢);意图簇枚举;全部闸门记录(逐项结论 + 证据引用);竞争审计(全 top-10 分类 + 实测 footprint);收入三情景(假设来源逐条标注);页面地图(页面 × 簇 × 产品资产);play;风险清单;**失效条件**(出现什么信号即放弃);下一步人工动作清单(注册域名、建站、发布均在此,skill 不执行)。

pilot 决策书同构,但页面地图为 5–8 页的有界实验,且不得携带全站分数。

### 7.2 快道决策书(fast_grab_ready)

必含章节:词与任务;G1–G5 证据;窗口估计与 expiry(附推理);**跳过的闸门清单及"为何此刻无法执行"**(G6–G8 所需证据对天级新词客观不存在);48 小时发布计划(最小页面集);投入上限声明(损失封顶:一个域名 + 若干页面工时);风险确认(这是窗口赌注,不是被验证的生意);失效信号;升级通路说明(词若耐久,可转回 tracking 走完整认定)。

### 7.3 双格式产出约定(md 给 AI,html 给人)

- 只有 go 决策(build_ready / pilot_ready / fast_grab_ready)产出决策书;hold / no_site 只在账本记决定性理由,不出文档。
- 每份决策书两个文件,内容同源:
  - `<slug>.md` —— 给之后落地网站内容的 AI 读。结构化、字段完整、无修辞:主关键词与精确措辞、意图簇及每页对应的查询、页面地图(每页的任务定义)、自助产品资产规格、竞争审计中发现的可利用缺口、变现路径、失效条件、明确的"不要做什么"。**md 是唯一事实来源**。
  - `<slug>.html` —— 给人读的渲染视图:结论先行、分节排版、关键数字醒目。单文件、内联样式、零外部依赖,双击即可在浏览器打开。
- html 是 md 的视图:两者必须同批产出、同批更新,禁止只改一份(防漂移,与 xinci-core 单一来源原则一致)。

## 9. 错误处理与不变式

- 认证 / CAPTCHA / 付费墙 / 权限 / 文件系统失败 = blocker,不是 quota 耗尽,不能作为完成或停止的理由。
- registrar 拒绝一切非法转移与证据不齐的转移;证据缺失 = 不通过,没有"待定通过";缺失的 volume 不是零需求,缺失的证据也仍是缺失的证据。
- 空扫描、零合格是合法结果,如实报告;禁止凑数、禁止 maybe 清单、禁止为保候选软化闸门。
- 连续拒绝原因收敛到少数结构性模式时,产出 `screen_unsatisfiable` 假设报告交给用户,但这是发现不是停止理由,更不是降门槛的许可。
- 未实际打开的来源、未实际读到的 SERP,不得声称已检查(evidence before claims)。
- skill 永不执行:注册域名、花钱、发布内容、自动状态转移、自我调度。

## 10. 落地验收标准

实现完成后,以下四项全过才算落地成功:

1. **全链演练**:一次真实扫描把至少一个候选走通 `captured → screened → tracking`,账本、证据、run 清单齐备且 `validate_ledger.py` 零报错。
2. **回归案例**:用旧系统记录的两个已知案例做回归——Qwen VRAM 计算器类候选必须死在 G5(且在读 SERP 结构之前);屋顶检查类词必须死在 G4。
3. **registrar 非法转移测试**:`captured` 直接提 `build_ready`、缺证据的 `tracking → formation_confirmed` 等必须被拒绝。
4. **双环境加载测试**:Codex CLI 与 Claude Code 各运行一次 xinci-status,读同一账本得到一致输出。
