# 通用约定(七个 xinci skill 共用)

每个 SKILL.md 开头都要求先读本文件。这里收的是所有 skill 一模一样的开局步骤与硬规则,各 SKILL.md 只写自己独有的部分。

## 路径约定

相对路径以仓库根为基准。正本在 `xinci-workflow/<skill>/SKILL.md`;通过 symlink 加载时 `readlink` 后上溯两级即仓库根。bash 在仓库根执行,或展开为绝对路径。

## 第 0 步:确认数据区(先于一切写操作)

```bash
python3 xinci-workflow/xinci-core/scripts/report_status.py
```

- 正常返回看板 → 数据区已配置,直接往下走,不再问。
- 退出码 2、提示「数据区未配置」→ 停下来问用户数据区放哪,不替用户选。这不是故障,脚本刻意不猜(理由见生命周期契约「开工第一步」)。

拿到路径后固定下来(幂等):

```bash
python3 xinci-workflow/xinci-core/scripts/init_workspace.py --data-root <用户给的路径>
```

## 运行模式与 `--by`

| 模式 | 触发 | 转移前要不要用户确认 | registrar 的 `--by` |
| --- | --- | --- | --- |
| 单步 | 用户直接调用某个阶段 skill | 要。skill 只提议,用户确认后才调 registrar | 阶段名(`xinci-scan` / `xinci-track` / `xinci-mature` / `xinci-qualify` / `xinci-decide`) |
| 连续 | 用户启动 xinci-run | 不要。启动命令即标准授权,既定路径上的转移直接执行 | `xinci-run`,并同时传 `--run-id <活动会话>` |

- 各 SKILL.md 的命令模板写的是单步形态。连续运行(含 xinci-run 派出的子代理)一律改成 `--by xinci-run --run-id <run_id>`;只改 `--by` 或照抄模板都是错的。`register` / `checked` 的 `--by` 有默认值,连续运行下必须显式传。
- 连续运行下 `register` 多三项硬要求(registrar 强制):`--site-thesis`、至少两个 `--task-family`、`--origin signal|trigger`(变化面另带 `--trigger-id <已 approve 的 trigger id>`)。单步下前两项推荐、第三项不需要。
- **标准授权的唯一例外**:`G3=veto_window_bet` 的 `captured→screened`。无论哪种模式都要用户对该候选做一次性明确确认;连续模式下用 `run_controller.py confirm-window-bet --run-id <run_id> --slug <slug>` 记录,未确认时 registrar 拒收出闸。候选在此期间留在 `captured` 挂起,不得转 `rejected`。
- 活动会话存在时 registrar 拒绝所有单步写入。
- 取值规则的正本见生命周期契约「registrar 用法」的 `--by` 取值节。

## 运行清单

单步模式每次执行结束写一份运行清单,用脚本原子写入,不手写 JSON:

```bash
python3 xinci-workflow/xinci-core/scripts/run_manifest.py record-single \
  --date <YYYY-MM-DD> --skill <skill名> [--suffix <HHMM>] [--source-opened <URL>] \
  [--candidate-touched <slug>] [--billable-calls <N>] [--note '<事实>'] ...
```

同日再次运行显式传 `--suffix`,控制器拒绝覆盖。连续运行模式不调用本命令,内容统一由 `run_controller.py record-round` 写进 run 清单。

## lane 边界

| 状态段 | `lane=new` 归谁 | `lane=mature` 归谁 |
| --- | --- | --- |
| 发现、captured 接队、captured→screened | xinci-scan | xinci-mature |
| tracking 复查、→formation_confirmed | xinci-track | xinci-mature(复查动作照抄 xinci-track 第 1–7 步,`--by xinci-mature`) |
| formation_confirmed→qualified / hold 重审 | xinci-qualify | xinci-qualify |
| qualified / hold→决策、screened 快道 | xinci-decide | xinci-decide(快道须用户显式调用) |
| xinci-run 连续运行 | 全部状态 | 只从 formation_confirmed 起 |

registrar 对两边都做 lane 硬校验。xinci-scan / xinci-track 遇到 mature 候选只报告"应交 xinci-mature",不写入。

## 四条 expired 边的提议人(单步模式)

| 来源态 | `--expiry-trigger` | 提议人 |
| --- | --- | --- |
| captured(排队过期) | date | xinci-scan 开局接队时(mature 归 xinci-mature) |
| tracking | date / invalidation | xinci-track 复查后(mature 归 xinci-mature) |
| screened | date | xinci-decide(它是快道模式的输入) |
| fast_grab_ready | date / window_closed | xinci-decide(它是快道模式的产出) |

expired 没有失败的闸门,不许塞进 `rejected`。连续运行下四条都归 xinci-run 运行循环步骤 1,标准授权直接转。xinci-status 只汇报到期清单,不提议。

## 面向用户只说中文

机器内部保留英文状态码,但 commentary、最终报告、状态解释、错误转述用中文展示名;候选英文搜索词、网址、文件名、命令参数原样保留。结束状态对照:`go`=已产出可交付结论;`quota_exhausted`=查询额度已用完;`budget_reached`=运行预算已用完;`resource_exhausted`=会话资源已用完;`calibration_triggered`=已触发闸门校准;`blocked`=执行受阻;`cancelled`=已取消。

## 所有 skill 共同的硬规则

- 不注册域名、不花钱、不发布。找到词就停,建站是用户的动作。
- 真浏览器直读,不走 API/MCP 数据工具拉社区内容;未在本次会话打开的来源不得声称已检查,不得列入 `source_urls`。
- 精确措辞 + 来源 URL + 时间戳,缺一不注册;凭记忆重构的词不是证据。观察写要点不写转录。
- Semrush 只做 decision-changing 查询;窗口期(captured / screened)禁用 Semrush / KD / KGR / CPC / Google Trends(mature 道例外见数据采集指南)。
- 账本只能由 registrar 写;淘汰方向索引只能由 `screen_index.py` 写。手工编辑一律禁止。
- 产出为零如实说零;禁止凑数,禁止 maybe 清单。
