## 类别四:厂商 release note / changelog 衍生任务(SERP 陷阱型 · 直接筛除型)

- **识别特征**:方向来自某个厂商自己的 release note / changelog / what's-new / 产品更新博客(AWS what's-new、GitHub Changelog、Cloudflare Changelog、GCP Release Notes、Vercel Changelog、Apple Developer News 等),任务是"怎么用/怎么配这个新功能"。
- **死因**(每次相同,与具体方向无关):
  1. 发布方在同日或次日就把官方文档发出来,往往就是分步操作;
  2. 官方文档域(docs.aws.amazon.com / docs.github.com / github.blog)永久收录、在该查询上有持续可见度,不是临时空位——连 `veto_window_bet` 都判不出来,只能是 `veto`;
  3. 聚合站(daily.dev、aws-news.com、West Loop Strategy、DevelopersIO、LinkedIn 转载、awsi.click、skitbranyheter.nu)24 小时内填满剩余位置;
  4. SERP 上没有大媒体、没有维基,G2 一路放行——过 G2、死 G3。
  - 变体:新功能挂在一个十年期的成熟查询上(`s3 access denied`),新增字段并不开出新位置;不要反过来以为"老查询 + 新字段"是机会。
- **处置档**:直接筛除型。跨 3 个日期、3 个来源家族、3 个独立发布方(Apple / GitHub / AWS),满足「如何追加新类别」对改档的全部要求;命中零成本弃,一次 SERP 都不跑,仍按 G5 追加一行淘汰方向索引。
- **零成本判法**:方向出处是不是厂商自家的变更公告?是 → 弃。
- **不覆盖**:第三方对多个厂商变化做横向汇总 / 对比 / 迁移的任务(发布方各自只写自己那一半)——不适用本类别的零成本筛除,按正常序列跑 G1/G2/G3;横向那一半的死因另见类别七。
- 历史样本见 [陷阱案例历史](陷阱案例历史.md) 的同名类别，仅在复核来源时读取。



## 类别八旧处置依据

## 类别八:厂商不利的开关型任务(前置筛除型 · 直接筛除型)

- **识别特征**:措辞形态是「怎么关掉 X 的某个默认行为」「怎么从 X 的某项计划里退出」「怎么批量删掉 X 存的我的数据」——厂商在结构上不愿意记录的任务。
- **死因**:死在 G6/G7 零成本预筛,连 SERP 都不必读(前置筛除型的定义据此扩到"产生了可搜索任务,但既不耐久、付费者也不付费")。双重塌陷:
  - 厂商真的不写 → 任务通常是一次性开关,不构成被迫重复完成的耐久任务(G7「好奇 vs 任务」与「一次性配置」);
  - 任务真的重要到有人反复搜 → 舆论压力让厂商很快把开关做出来并写进帮助中心,官方答案随即在位(G7「官方答案风险」),压力越大写得越快。"厂商不愿记录"是个不稳定状态。
  - 付费者层:搜索者绝大多数是不付费的消费者,subscription 通常不成立,new 道 advertising 又是 `N/A`。
- **处置档**:直接筛除型。
- **零成本判法**:
  - 是不是找到并关掉一个设置就结束的一次性开关?
  - 厂商是否已在舆论压力下补上开关与帮助中心文档?
  - 搜索者是不是不付费的消费者?
  - 仍须逐线检查 affiliate、transaction、paid_report 与 lead_generation,不能用前两项代替六线结论。
- **不覆盖**:①付费者是有预算的企业、且该开关要按对象反复设置(为每个项目/每个租户逐个关闭,厂商只写了一次性说明)——可能形成耐久任务,按正常序列跑 G1/G2/G3;②"迁出 X"不归本类别,归类别七。
- 历史样本见 [陷阱案例历史](陷阱案例历史.md) 的同名类别，仅在复核来源时读取。



## 类别九旧处置依据

## 类别九:零回答与悬赏问题(前置筛除型 · 直接筛除型)

- **识别特征**:发现策略是直接找"任务存在、答案不存在"的证据——Stack Overflow 一类站点的零回答问题、悬赏问题、高分未回答榜。
- **死因**:反向选择。很多人有这个问题 → 已经有人把答案变现了;没人有这个问题 → 提问者只能悬赏,因为他是一个人。零回答不是"答案缺失"的证据,而是"提问者孤立"的证据。量化上限:全站最高分未回答问题的浏览量是累积多年 1,016–9,228 次——六条线都找不到付费者(G6 那条"≥$200/月"现只约束 advertising,new 道又固定 `N/A`,结论不变)。
- **处置档**:直接筛除型,零成本弃,不必开 SERP;前置筛除型不受"三次观察"约束。
- **零成本判法**:这个任务是不是只有一个人有?来源是零回答榜或悬赏页 → 是 → 弃。
- **不覆盖**:①近期出现的零回答问题里,同一问题在多个独立提问者处反复出现(同一周内多条相似提问、或提问量在上升)——正在从"一个人的问题"变成"很多人的问题",按正常序列跑 G1/G2/G3;②有回答但回答明显过时或被投票否决的高浏览问题——那是"答案在位但答错了",另一回事。
- 历史样本见 [陷阱案例历史](陷阱案例历史.md) 的同名类别，仅在复核来源时读取。



## 类别十四旧处置依据

## 类别十四:新旧法规过渡条款(前置筛除型 · 直接筛除型)

- **识别特征**:方向是过渡期判定——看起来天然多维(产品类型 × 首次投放市场日期 × 已有证书有效期 × 协调标准状态 × 是否实质性改动),有明确日期压力,过渡期的选择只体现在制造商自己的 DoC/DoP 里、没有人收这个判定结果。
- **死因**:立法者写过渡条款的目的正是消除不确定性——一份过渡条款如果本身需要逐对象判定,它就没有完成它被写出来的那件事。所以它天然被写成「一条时间线 + 一两个统一例外」,判定维度为 1,与正向画像①要求的「≥3 维、数百到数千条目」正好相反。
  - 第二道锁:即使分阶段,立法者一边规定分阶段、一边把阶段表公布出来(COM(2025) 772 Table 3 逐产品族带 "Standard made mandatory and DA adoption" 日期列)——按数据采集指南画像④第 2 句,清单带了搜索者要的那一列,位置从一开始就没有。
- **处置档**:直接筛除型,零成本判定,一次 SERP 都不必跑。索引 `pattern` = `过渡条款判定表只有一条时间线`。
- **零成本判法**:打开那部法规的过渡条款(通常是最后几条,标题为 Transitional provisions / Derogations and transitional provisions),数它有几段、有没有超过一个维度。一条时间线加统一例外 → 弃。
- **不覆盖**(两个口子都要留):
  1. 过渡资格真的附带多项条件的——典型是 MDR 延长过渡期(Regulation (EU) 2023/607 把 MDR Art 120 改为按器械类别分两档到期日,并附「无重大变更 + 按期建立 QMS + 按期正式申请 + 按期签署书面协议」四项条件)。要逐条判,但先查有没有对应的官方 Q&A / MDCG 指南(属类别十三的解释例表形态),也要先确认它的条件截止日是否已过。
  2. 过渡措辞真正载重的判定其实是另一件事的——机械一例「我这台机器过渡后怎么办」实际回落到「它属不属于 Annex I Part A/B」的分类判定,按它自己的死因判;写 reason 时不要把分类判定的死因挂到本类别名下(`eu-machinery-regulation-risk-category` 已 rejected;淘汰索引裁决 `dd-9d61078157acb7e8` 判两者 same)。
- 历史样本见 [陷阱案例历史](陷阱案例历史.md) 的同名类别，仅在复核来源时读取。
