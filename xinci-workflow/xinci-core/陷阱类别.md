# 陷阱类别

陷阱按**死因**分两型,按**处置**分两档,两者独立标注在每个类别的标题里。

死因型:

- **SERP 陷阱型**:过 G2、死 G3——SERP 结构看起来诱人(没有大站、没有官方源),但任务早已被免费工具做完。
- **前置筛除型**:在"这个发布产生了什么任务"一问就出局,根本产生不了可搜索的任务;也含"产生了可搜索任务,但既不耐久、付费者也不付费",死在 G6/G7 零成本预筛的情形(类别八起扩入)。

处置档(G5 命中时怎么做,正本见闸门契约「G5:陷阱类别检查」):

- **验证型**:跳过结构阅读直接跑 G3 验证,先按暂定盈利线判断占位否决是否生效——只有当前通过线全部依赖 affiliate / advertising 时判 `veto` 才弃(只追加一行淘汰方向索引),判 `veto_window_bet` 才走窗口赌注出口;任一非流量线暂定可行时,同样的占位事实只作为竞争输入,G3 有效门结论写 `pass`。用于死因取决于本方向具体情形的类别。
- **直接筛除型**:零成本判定即弃,一次 SERP 都不跑,按 G5 追加一行淘汰方向索引。用于死因已结构性确定、逐条验证只是重复劳动的类别。

验证存活候选的注册(G5 记 pass、按排队位注册 `captured` + gates + expiry、本轮补 G1/G2、`veto_window_bet` 只有快道出口)与"陷阱验证 `veto` 走索引、无类别命中的深审否决要注册"的分界(类别级死因 vs 方向级死因),见闸门契约「G5:陷阱类别检查」与生命周期契约「留痕分界」。

## 如何追加新类别

每当一次扫描出现新模式:

1. 在本文件追加一节,标题为类别名,标注**死因型**(SERP 陷阱型 / 前置筛除型)与**处置档**(验证型 / 直接筛除型)。处置档按死因型定,两条规则不可混用:
   - **SERP 陷阱型**默认验证型。改标直接筛除型要求 ≥3 次实际观察指向同一结构性死因,且至少跨 2 个日期、2 个来源家族,并包含跨行业或跨发布方的独立样本;同一天、同一行业的三例只能形成待验证假设。计数合并索引侧 `pattern` 与账本侧运行清单 notes。
   - **前置筛除型一律直接筛除型,不受"三次观察"约束**——没有词可搜就没有 SERP 可读、没有 G3 可验证,验证型对它在物理上不成立(类别二即此例)。
2. 记录**实际观察**:日期、具体候选词、来源;SERP 陷阱型附 G3 验证中数到的免费工具清单,前置筛除型附判定无任务的依据——不许只写泛化结论。
3. 若该类别还独立命中 G7(无窗口/无耐久),一并记录。

各类别统一按「识别特征 / 死因 / 处置档 / 零成本判法 / 不覆盖 / 案例」写;建类过程、实测叙述与被改写的旧版本见闸门校准 §13。

## 类别一:新发布 AI 模型(SERP 陷阱型 · 验证型)

- **识别特征**:方向是刚发布的 AI 模型(HN 首页、Product Hunt、r/LocalLLaMA 当日榜),任务是"这个模型能不能装进我的 GPU、用哪个量化"一类部署需求。首页没有大站、没有官方源(Hugging Face 与厂商都没排上),G2 干净通过。
- **死因**:底层任务已被免费 VRAM 计算器与对比站饱和,过 G2、死 G3。G7 另独立命中两条:①没有抢跑窗口——通用工具收录新模型以天计;②耐久性以周计——为一个模型版本买的域名随下一版发布过期,重复任务属于通用工具那条已被争夺的赛道。
- **处置档**:验证型。收录时差是一个会变的量,必须每次实测、不能引用:2026-04 实测 4 天(Spheron 对 Llama 4),2026-08 实测同一工具(ApX)≥17 天。不要把 4 天当常数——它同时是 G3 判 `veto_window_bet` 时"位置只空几天"的定价依据与 G7「官方答案风险」的依据,用过期的数会同时高估两处风险。
- **零成本判法**:
  - 这个新对象是厂商的公共对象(一个答案服务所有人),还是搜索者手上的对象?前者 → G6 第一问答否、也不满足类别十二合取条件 1 → 弃,不必逐条走完其他类别。
  - 有没有人被迫用它?答"没有"(玩具模型)→ G6 预筛出局,不必再花 G3 测收录时差。
  - 先核对对象的真实年龄(见数据采集指南「零成本批的一条前置纪律」),别采信信号面的"新"标记。
  - 收录时差与任务反向绑定:有人真部署的模型,发布方页面小时级收录、通用工具天级(实测 4 天 / ≥17 天)、有任务;没人部署的玩具模型,通用工具可能永远不收、但没有任务。"通用工具还没收录"的空位只存在于没有任务的那一行,本类别的 `veto_window_bet` 出口在实践中极难成立(判据不改:临时空位仍记 `veto_window_bet` 而非 `veto`)。
  - 有效 G3 结论先做盈利线条件映射(见序言);不得照历史补记新造 `veto_window_bet`,也不得把决策书交付后的阅读倒写成事前风险确认。
- **不覆盖**:原文未设口子。
- **案例**:

| 词 | 死因要点 | 观察日 |
| --- | --- | --- |
| `qwen 3.8 27b vram requirements` | HN 首页第 1 位(419 分);G3 数到 9 个免费工具(ApX、HF Space、Onyx AI、社区计算器、Spheron、smcleod.net、logarithmicspirals.com、AIMultiple、GitHub 实现);按当时规则记 `veto_window_bet`,留痕为索引行,不回填账本 | 2026-08-17 |
| `GLM-5.3` | Product Hunt;真实发布日 2026-08-14,HN 显示 3 天前;复测时 ApX 未收录(`glm-53` 404,同批 404 的还有 `glm-53-flash`、`qwen38-flash-next`、`hy4`) | 2026-08-17 / 08-31 |
| `deepseek v4 flash-0731` | 根本不新(线程可追到三个月前);ApX 已按模型逐个建页;G3=veto | 2026-08-21 |
| `Aurora-80K` | 发布 18 小时,发布方 HF 页已排第 2;玩具模型,无付费者被迫使用,G6 两项直接不成立;串与英雄联盟角色、薪资查询碰撞 | 2026-08-21 |

## 类别二:纯品牌名发布(前置筛除型 · 直接筛除型)

- **识别特征**:发布的搜索需求只有品牌名本身——导航意图,没有一个页面可以完成的任务。看它的讨论里除了名字和"这是什么"之外,有没有人在要一个 guide、calculator、converter、checker、tier list 或兼容性答案;没有,就没有词。
- **死因**:在"这个发布产生了什么任务"这一问就出局,不用到 G3。
- **处置档**:直接筛除型(前置筛除型,不受"三次观察"约束)。
- **零成本判法**:讨论里有没有人在要 guide / calculator / converter / checker / tier list / 兼容性答案?没有 → 弃。
- **不覆盖**:讨论里有人明确在要上述工具或答案的,说明任务存在,按正常序列跑 G1/G2/G3。
- **案例**:

| 词 | 死因要点 | 观察日 |
| --- | --- | --- |
| Product Hunt 当日 14 个发布全部(总数以 `运行/2026-08-17-xinci-scan.json` 为准) | 留下措辞的有 `Blume`、`Expeditione`、`Vidaya`、`Chert`、`AirAlarm`、`CostLogic`、`HarnessRouter Community Edition`;运行清单另点名 `AGI-64`、`Vocal Slice`、`MathCode`、`nurb`、`OpenTrade`——同一批的两份名单,不是两次扫描 | 2026-08-17 |
| 信号面 57 条 | 一轮 158 条方向里纯品牌名发布 57 条,全数零成本弃 | 2026-08-31 |

## 类别三:厂商已占位的 B2B 强制任务(SERP 陷阱型 · 验证型)

- **识别特征**:有日期的法规/平台变化 → 受影响付费者明确且有预算(开发者、合规负责人、营销团队)→ 正因为付费者有预算,服务该付费者的厂商早已用内容营销占满 SERP,且发布方常自带完整免费答案。G6 越漂亮,G3 越可能否决——付费者明确本身就是竞争已存在的证据。
- **死因**:过 G2、死 G3。两条可直接用于筛除的判据:①发布方自带模板/计算器/最佳实践的变化,任务已被官方做完,第三方信息站没有位置;②该付费者群体已存在成规模的合规/工具 SaaS 行业(合规软件、ASO 工具、支付网关、律所),其内容机器收录以天计(实测 4 天排上首页),窗口不存在。G7 附带:这类任务的耐久版本通常归工具厂商所有,第三方信息站即便抢到一时位置也无可守之地。
- **处置档**:验证型。独立性要求已凑够(跨 2 日期、2 来源家族、跨行业与发布方),但死因取决于该付费者群体是否已存在对应厂商行业——方向级事实;付费者被迫、有预算、却还没有厂商围着他转的变化确实存在,零成本弃会误杀。只有未来样本证明「有预算的付费者必然已被厂商内容占位」与具体方向无关时,才可再次修订本节改档。
- **零成本判法**(命中后跳过结构阅读直接跑 G3 验证具体 SERP):
  - 发布方有没有自带模板 / 计算器 / 最佳实践?
  - 该付费者群体有没有成规模的合规 / 工具 SaaS 行业?
  - 先按盈利线判断占位否决是否生效:只有当前通过线全部依赖 affiliate / advertising 时判 `veto` 才弃,任一非流量线暂定可行时只记竞争压力。
  - 选源反推:变化面优先探索付费者被迫、但尚无对应厂商行业的群体。
- **不覆盖**:付费者有预算而厂商内容机器尚未围上来的变化——这是本类别放行的空间。与类别七在 `harvest` 一例重叠:类别三讲"谁在写",类别七讲"写的是哪一格",命中任一即按验证型跑 G3。
- **案例**(均已注册进账本并转 rejected,证据在 `证据/<slug>/2026-08-18-scan.json`):

| 词 | 死因要点 | 观察日 |
| --- | --- | --- |
| `significant change api` | Apple 2026-06-03 公告 + Texas SB 2420;Apple 官方 /kids 与文档、blakecrosley.com、eCorpIT、dev.to、k-ID、Gummicube、ASO World(2025-11 页面稳定排两页内) | 2026-08-18 |
| `ppwr empty space ratio` | 欧盟 PPWR 2026-08-12 起适用;三个 PPWR 专用站(ppwrcopilot.com 带计算器、ppwrconnect.com、gramta.com)+ osapiens、ecosistant、Clarity、Packsize、corplex、Carriyo、TraceX、Measurlabs | 2026-08-18 |
| `app store creative assets` | Apple 2026-08-05 宣布新素材位,同日自发布 best practices + Figma/PS/Pixelmator 模板(官方答案当场做完任务)+ ASO World、44Degrees、Moburst | 2026-08-18 |

## 类别四:厂商 release note / changelog 衍生任务(SERP 陷阱型 · 直接筛除型)

- **识别特征**:方向来自某个厂商自己的 release note / changelog / what's-new / 产品更新博客(AWS what's-new、GitHub Changelog、Cloudflare Changelog、GCP Release Notes、Vercel Changelog、Apple Developer News 等),任务是"怎么用/怎么配这个新功能"。
- **死因**(每次相同,与具体方向无关):
  1. 发布方在同日或次日就把官方文档发出来,往往就是分步操作;
  2. 官方文档域(docs.aws.amazon.com / docs.github.com / github.blog)永久收录、在该查询上有持续可见度,不是临时空位——连 `veto_window_bet` 都判不出来,只能是 `veto`;
  3. 聚合站(daily.dev、aws-news.com、West Loop Strategy、DevelopersIO、LinkedIn 转载、awsi.click、skitbranyheter.nu)24 小时内填满剩余位置;
  4. SERP 上没有大媒体、没有维基,G2 一路放行——过 G2、死 G3。
  - 变体:新功能挂在一个十年期的成熟查询上(`s3 access denied`),新增字段并不开出新位置;不要反过来以为"老查询 + 新字段"是机会。
- **处置档**:直接筛除型。跨 3 个日期、3 个来源家族、3 个独立发布方(Apple / GitHub / AWS),满足「如何追加新类别」对改档的全部要求;命中零成本弃,一次 SERP 都不跑,仍按 G5 追加一行淘汰方向索引。
- **零成本判法**:方向出处是不是厂商自家的变更公告?是 → 弃。
- **不覆盖**:第三方对多个厂商变化做横向汇总 / 对比 / 迁移的任务(发布方各自只写自己那一半)——不适用本类别的零成本筛除,按正常序列跑 G1/G2/G3;横向那一半的死因另见类别七。
- **案例**(2026-08-18 起三轮扫描注册的 58 个候选,凡出自厂商自家变更公告的,深审无一存活):

| 词 | 死因要点 | 观察日 |
| --- | --- | --- |
| `significant change api`、`app store creative assets` | Apple Developer News;G3 veto(官方 /kids 文档、官方 best practices + 模板) | 2026-08-18 |
| AWS what's-new / GitHub Changelog 40 余个方向 | 零成本秒弃;索引 pattern「GitHub 官方变更已自带答案」累计 120 次、「官方SaaS内建功能答案在途」17 次 | 2026-08-20 |
| `gh-org-pull-request-limits`、`gh-ruleset-auto-migration`、`gh-usage-report-per-model-tokens` | GitHub Changelog;三例 G2 pass、G3 veto;github.blog 摘要即 "Navigate to your organization's settings → Moderation tools → …" | 2026-08-21 |
| `aws-secrets-manager-jenkins-sonarqube`、`aws-workspaces-nested-virtualization`、`aws-quick-dlp-purview`、`aws-iam-policy-autopilot-terraform-plan`、`aws-s3-access-denied-policy-details` | AWS what's-new;五例 G2 pass、G3 veto;docs.aws 首位即分步操作;最后一例为"老查询 + 新字段"变体 | 2026-08-21 |

## 类别五:信号面的观点、新闻与旧文回流(前置筛除型 · 直接筛除型)

- **识别特征**:方向来自 Hacker News / Reddit 一类社区信号面的高分条目,而条目本身是随笔、观点评论、时事新闻、科研报道、事故复盘,或多年前旧文回流。
- **死因**:高分等于讨论热度,不等于任务存在——信号面的排序机制奖励可争论、可共鸣、可转发的内容,而"有人被迫重复完成"的任务安静无聊;分数越高往往越是前者。与类别二同理,在「这个帖子产生了什么任务」一问就出局。
- **处置档**:直接筛除型(前置筛除型,不受"三次观察"约束)。
- **零成本判法**:
  - 这个条目让谁被迫重复做什么?答不出具体页面能完成的任务 → 弃。
  - 判之前先按类别二的识别要点扫一眼讨论里有没有人在要工具。
- **不覆盖**:①条目虽是新闻/事故,但牵出了有日期的强制变化并落到具体付费者身上——属类别三,仍要跑 G3 验证;②社区帖里明确有人在要 guide、calculator、converter、checker、tier list 或兼容性答案——任务存在,按正常序列跑 G1/G2/G3。
- **案例**(索引侧 `pattern` 累计 66 次,归并了同一死因的六个近义 pattern;实例来自 2026-08-21 HN 首页、第 2 页与 hn.algolia.com 近 24 小时榜):

| 词 | 死因要点 | 观察日 |
| --- | --- | --- |
| `no small software team anymore`、`the amazon tax` 等 | 无被迫任务的观点或新闻(累计 26):职业/架构观点文,读完没有任何页面可完成的动作 | 2026-08-21 |
| `zuckerberg growth over child safety testimony`、`stwipe acquires openwouter` 等 | 新闻非任务(累计 14):时事,下一周就不再被搜 | 2026-08-21 |
| `dont paste the ai please`(992 分)、`anti-ai fonts useless harmful` 等 | 观点非任务(累计 10):高分仍只是一份宣言站 | 2026-08-21 |
| `early life stress scar brain cells`、`elliptic curve of rank 30` 等 | 科研新闻无付费者任务(累计 8):研究成果不是任务,受众也不付费 | 2026-08-21 |
| `windows rorschach test oldnewthing`(2003)、`project cybersyn`(2022)等 | 旧内容回流(累计 5):回流不产生新措辞 | 2026-08-21 |
| `github august 17 outage postmortem` 等 | 一次性事件(累计 3) | 2026-08-21 |

## 类别六:管辖机构自维护的对象全集权威查询(SERP 陷阱型 · 验证型)

- **识别特征**:方向来自有日期的法规/标准变化(Federal Register、TTB、APHIS、NPS 一类),而这个变化落在一个已有权威全集查询覆盖的对象类上——发证或管辖机构为该对象类的每一个成员维护一页,或第三方已建成覆盖该对象全集的数据库站。新对象一进入全集,就自动获得一个永久收录、稳定排名的页面。
- **死因**:"被迫任务"与"位置空着"是两件事。有全集维护者,第三方信息站从第一天起就没有位置;这类页面通常是机构官方域的内页,G2 看不出异常——过 G2、死 G3。联邦公报全集的自动镜像(federalregister.gov、govinfo.gov、regulations.justia.com、reginfo.gov)让任何一条规则一发布就自动获得多个永久收录页面。
- **处置档**:验证型,不得零成本弃。是否存在全集维护者是这个对象类的事实,不是变化本身的属性——确实存在没人维护全集的对象类,零成本弃会误杀。(六例同日、同来源家族,亦不满足改档独立性要求。)
- **零成本判法**:
  - 措辞落在哪一格?落在「这条规则说了什么 / 要求什么」→ 全集镜像已占位,直接判 veto,不必实测。落在规则之外的派生问题(某个具体对象够不够条件、跨管辖区怎么比、迁到哪里去)→ 进入下一问。
  - 这个对象类有没有全集维护者?再实测一个具体对象的查询(G3 验证)。
  - "机构没有中央清单"不等于"位置空着":机构常按对象分页维护,分散的每园页合起来就是全集。要问的不是"有没有一张总表",而是"这个对象自己有没有一页权威答案"。
- **不覆盖**:①对象类本身很新、还没有任何全集维护者的——那才是这条赛道要找的东西;②任务是跨管辖区横向比较的(各机构只维护自己那一格),按正常序列跑 G1/G2/G3,横向那一格的死因另见类别七与类别十二。与类别十是同一枚硬币的两面:本类别是位置被占(死 G3),类别十是没有付费需求(死 G6),可同时命中但死因分开写。

## 类别七:跨厂商横向对比与迁移(SERP 陷阱型 · 验证型)

- **识别特征**:措辞形如 `alternatives to X`、`X vs Y`、`migrate off X`、`从 A 平台迁到 B 平台`。诱惑在于 X 的厂商确实不会写它,看起来无人占位。
- **死因**:钳形,两侧都不通。本类别堵住类别四与类别六留下的"横向那一半"口子——横向那一半有自己的全集维护者,只是维护者不是发布方。
  - X 的市场足够大 → 横向对比本身已成为一个对象类,并有全集维护者(替代品目录站、分析机构榜单、社区 awesome 清单、专做成对对比的内容站、竞品自建对比页),覆盖每一个有真实市场的 X 与每一对 X/Y,收录以天计。
  - X 的市场小到没人做目录 → subscription 与 advertising 往往一起塌陷,但这不是六线全灭的充分条件,仍须检查 lead_generation / affiliate / transaction / paid_report,少量高价值需求可能让其中一线成立。
- **处置档**:验证型(三例同日,不满足改档所需的 ≥2 个日期)。
- **零成本判法**(命中措辞形态后跳过结构阅读直接跑一次 G3,重点数三样):
  - 有没有替代品目录站?
  - 有没有分析机构榜单或社区 awesome 清单?
  - 有没有专做成对对比的内容站?
- **不覆盖**:横向任务的一侧是尚无市场的新对象(例如刚发布三天、还没进任何目录的东西 vs 一个老对象)——钳形第一侧暂时不成立,属窗口赌注的判断范围,按 G3 三分去测收录时差,不直接判 veto。

## 类别八:厂商不利的开关型任务(前置筛除型 · 直接筛除型)

- **识别特征**:措辞形态是「怎么关掉 X 的某个默认行为」「怎么从 X 的某项计划里退出」「怎么批量删掉 X 存的我的数据」——厂商在结构上不愿意记录的任务。
- **死因**:死在 G6/G7 零成本预筛,连 SERP 都不必读(前置筛除型的定义据此扩到"产生了可搜索任务,但既不耐久、付费者也不付费")。双重塌陷:
  - 厂商真的不写 → 任务通常是一次性开关,不构成被迫重复完成的耐久任务(G7「好奇 vs 任务」与「一次性配置」);
  - 任务真的重要到有人反复搜 → 舆论压力让厂商很快把开关做出来并写进帮助中心,官方答案随即在位(G7「官方答案风险」),压力越大写得越快。"厂商不愿记录"是个不稳定状态。
  - 付费者层:搜索者绝大多数是不付费的消费者,subscription 通常不成立,new 道 advertising 又是 `N/A`。
- **处置档**:直接筛除型。
- **零成本判法**:
  - 是不是找到并关掉一个设置就结束的一次性开关?
  - 厂商是否已在舆论压力下补上开关与帮助中心文档?
  - 搜索者是不是不付费的消费者?
  - 仍须逐线检查 affiliate、transaction、paid_report 与 lead_generation,不能用前两项代替六线结论。
- **不覆盖**:①付费者是有预算的企业、且该开关要按对象反复设置(为每个项目/每个租户逐个关闭,厂商只写了一次性说明)——可能形成耐久任务,按正常序列跑 G1/G2/G3;②"迁出 X"不归本类别,归类别七。

## 类别九:零回答与悬赏问题(前置筛除型 · 直接筛除型)

- **识别特征**:发现策略是直接找"任务存在、答案不存在"的证据——Stack Overflow 一类站点的零回答问题、悬赏问题、高分未回答榜。
- **死因**:反向选择。很多人有这个问题 → 已经有人把答案变现了;没人有这个问题 → 提问者只能悬赏,因为他是一个人。零回答不是"答案缺失"的证据,而是"提问者孤立"的证据。量化上限:全站最高分未回答问题的浏览量是累积多年 1,016–9,228 次——六条线都找不到付费者(G6 那条"≥$200/月"现只约束 advertising,new 道又固定 `N/A`,结论不变)。
- **处置档**:直接筛除型,零成本弃,不必开 SERP;前置筛除型不受"三次观察"约束。
- **零成本判法**:这个任务是不是只有一个人有?来源是零回答榜或悬赏页 → 是 → 弃。
- **不覆盖**:①近期出现的零回答问题里,同一问题在多个独立提问者处反复出现(同一周内多条相似提问、或提问量在上升)——正在从"一个人的问题"变成"很多人的问题",按正常序列跑 G1/G2/G3;②有回答但回答明显过时或被投票否决的高浏览问题——那是"答案在位但答错了",另一回事。

## 类别十:参数发布方连带供给答案(前置筛除型 · 直接筛除型)

- **识别特征**:义务是「按官方公布的参数,对每个对象算出一个数或做出一个判定」——每个商品码的原产地、每吨货的隐含排放、每个航段的应税福利、每批进口物质的税额。逐对象重复、付费者明确、有生效日,七条正向选源信号往往一路全中。
- **死因**:执行参数化义务的前提是有人先公布参数;公布参数的那一方几乎必然连带把查询、计算或免算路径一并提供——不提供,义务就无法执行。答案在义务生效之前就已免费到位,第三方计算工具没有可卖之物,死在 G6(没有付费需求)。
  - 位置空不空都不改变结论(`irs-aircraft-fringe-benefit-sifl-2026` 的 G1 与 G2 都是 pass,死在 G6)。三种供给形态,任一存在即弃:
  - ①发证机关把派生计算做成官方工具或全集查询;
  - ②法律本身给出默认值或从价率的免计算路径——立法者为降低合规负担设的简化路径同时消灭了第三方工具的付费需求,付费者越多、合规负担越受关注,立法者给免算路径的可能性越大;
  - ③行业协会免费提供计算器并维护参数全集。最强变体:立法直接批准行业机构的文本为法定标准——标题带 *Approval of…Code*、*…(Approval) Order* 的立法,先查它批准的是谁写的哪份文件,那份文件才是答案所在。
- **处置档**:直接筛除型,零成本判定,一次 SERP 都不必跑;前置筛除型不受"三次观察"约束。索引 `pattern` 统一写「参数发布方连带供给答案」(归并了「官方对象全集已自维护」「行业协会即全集维护者」「发证机关自带计算工具」「官方流程与既有系统已维护」「核心判定已被工具化」)。
- **零成本判法**(数据采集指南判据 6 的动作扩成四问,一起问,任一为是即弃;四问是同一件事的四个可能答案——谁有动机、又有资格把答案做成权威版本:发证机关、立法者、行业专业机构、既有软件类目厂商;先看证据指向谁,不要先挑一个再去凑):
  1. 发证机关关于该义务的官方页,有没有逐对象的参数表、查询页或计算器?
  2. 法条里有没有默认值、从价率或简化申报的免算条款?
  3. 该领域有没有行业协会已经把计算器做出来?
  4. 这件事会不会落进某个既有软件类目的默认功能(薪资、报税、ERP、物业管理、预订、许可管理…)?口径:义务的执行动作发生在某个软件里(算工资、报税、开工单、发租约),该软件厂商比任何内容站都更接近任务,且边际成本接近零。
- **不覆盖**(三条口子都是实测出来的,不要顺手扩大):
  1. 参数不由单一一方公布的——同一件事跨两个管辖区、各自公布各自的参数,横向那一半没有天然的连带供给者(`uk-machinery-safety-gb-ni-2026`:自助工具 0 个,占位者只写文章,进 tracking)。
  2. 分歧或对象类已经成熟到第三方建起全集数据库的——属类别六,死因是位置被占(`uk-reach-amendment-2026`:存续五年,ChemLinked 逐法规建页,判 veto)。与上一条合起来的时间判据:决定位置是否还空着的不是"是不是跨管辖区",而是这个分歧本身有多新。
  3. 任务根本不需要工具的——是 G6 第②③项自己塌陷,写 reason 时不要挂到本类别名下(`uk-protect-duty-notification-2026` 的 tier 判一次即定;`uk-automated-vehicle-marketing-terms-2026` 是 8 项固定短清单)。

## 类别十一:持牌机构合规义务(前置筛除型 · 直接筛除型)

- **识别特征**:义务来自金融监管机构(FCA、PRA、SEC、HMRC 的机构条线、各国央行与证监会),受约束主体是持牌或受监管机构——银行、保险公司、授权基金管理人、券商、支付机构。措辞形如「按 XX 规则分类/评估/申报」。
- **死因**:三层叠加,任一层单独就足以出局:
  1. 发证机关自建规则全集(FCA Handbook、PRA Rulebook、SEC 解释性发布与拟议规则逐条建页、永久收录),实测自占 4 个位次;
  2. 顶级律所内容机器已占满其余位置(付费者法律预算极高,每份政策声明都被写成客户通报),首页没有一个小站、论坛帖或第三方内页,G2 放行信号一个都不成立;
  3. 付费者买的不是工具——持牌机构自带合规部门,采购企业级 RegTech 订阅与律所意见函,G6 第③项自助变现路径不成立,付费结构性流向正在同一 SERP 上写内容的律所。
  - 本类别贡献给 G6 第③项的判据(待验证,见校准 §16「待验证清单」):判错代价是「钱与时间」时,工具可以降低它,付费流向工具;判错代价是「法律责任」时,工具无论多准都不能承担它,付费必然流向能签字的人。估算订阅线时先分清是哪一种。起判据作用的是判错代价的性质,不是主体的牌照身份——两者常重合,是因为持牌机构的义务通常都带法律责任。
- **处置档**:直接筛除型,零成本判定(索引 pattern「机构合规无自助变现」累计 36 次后归并)。
- **零成本判法**:
  - 受约束主体是不是持牌或受监管机构?
  - 判错的后果是不是法律责任?
  - 两问皆是 → subscription、paid_report 一类声称替代律所意见的自助交付结构性不成立。
  - 但按闸门契约 G6 六线 OR 口径这不是全局否决:仍要零成本过一遍其余适用线——尤其 lead_generation(把有预算的持牌机构导给律所或 RegTech);全部适用线均 `tentative_veto` 才弃、一次 SERP 都不跑;任一线暂定可行则按正常序列继续,律所与发证机关的占位只记作竞争输入。
- **不覆盖**:
  1. 受约束主体是普通企业、且判错代价只是钱与时间的——一般制造商、进口商、雇主、物业占用者,没有合规部门也请不起国际律所,按正常序列跑 G1/G2/G3。(原口径「普通企业而非持牌机构」已收窄:`ca-foreign-influence-transparency-2026` 的主体是普通实体,但未按期登记属刑事罪,仍死于第 3 层。)
  2. 任务是给持牌机构的交易对手做判断的(例如"我这家小企业发的这个东西,对方银行会怎么归类")——付费者是没有合规部门的那一侧,不适用本类别。

## 类别十二:横向汇总型任务已被 AI Overview 接管(SERP 陷阱型 · 验证型)

- **识别特征**:任务的答案能由 Google 首屏 AI Overview 当场合成或转交。诱惑真实(义务新、付费者有预算、没有一方有动机做那张表),但这正是生成式摘要最擅长的形态。三种形态:
  - ①横向汇总——「同一件事在 N 个管辖区 / N 个平台分别怎么规定」的对照表;
  - ②逐对象判定,但规则是已公布的少分支决策树,输入在搜索者脑子里(我是制造商还是进口商?我在不在加州?);
  - ③逐对象计算,首屏把方法、公式与表给完后主动索要对象参数并提出代算。
  - 本类别关的是类别四、六、十留下的"横向那一半没有天然供给者"的口子——占位者不是某个站,是首屏本身。
- **死因**:"没人做那张表"与"那张表很难做"是两件事。原料全是公开且已收录的官方页,合成成本对 AI Overview 接近零,位置被首屏本身占住,任何内容质量都赢不了(G1)。把参数直接写进查询也逃不掉——长尾化不是逃生路线。
  - 变体:首屏不合成而是转交——点名一个官方登记册说"去那里看"(索引 `pattern` = `AI Overview 指路官方转化登记册`,1 例,待验证;它是 IED 2.0 那一格的事实,不是转化矩阵族的通性,逐词实测,不得据此预判)。
- **处置档**:验证型,不得零成本弃。同一题材换一个措辞结论会翻转(措辞级事实),G1 本来就永不跳过;本类别的实际作用是排序纪律,不是零成本筛除权。尚未实测的一半(待验证,见校准 §16「待验证清单」):搜索者接受首屏代算邀请、在 AI Mode 提交参数后,答案对不对、算不算把任务做完——这是处置为验证型的真正理由。
- **零成本判法**(挑措辞用的三问合取,答"是 / 是 / 否"才留下;一个方向的多个措辞要一起测,横向措辞死了不等于这个义务死了):
  1. 措辞指向搜索者手上的某个对象(my mixture / this SKU / 我这台机器),而不是问规则、公式或表本身?——问表或公式的措辞首屏当场给全(`battery regulation recycled content calculation methodology`、`cpr product family list 2026`)。
  2. 把那个对象解析成答案,必须对一张大表查行或做一次计算,而不是走一棵分支数得过来的决策树?——问的是"列出规则算不算把任务做完"。小表(4–5 行默认因子表、一个公开罚款率)列出即完成,归条件 1 那半边。
  3. 那份对象参数,官方有没有一个按对象返回答案的系统?有 → 死在判据 6(类别六 / 类别十三),不必等 G1。
  - 不得采用的简化判据:"措辞里有没有一个 AI Overview 拿不到的对象,有就活"——`california textile epr am i a producer` 的 `am i` 正是首屏拿不到的对象引用,首屏仍把五级 producer 层次列全。
  - 三问都过的正例:`does my mixture need reclassification gb clp`(逐物质对 GB MCL 清单查行再按浓度限值加和)、`cpr avcp system 1+ 2+ 3 4 which applies`(四维查 AVCP 表)。
  - 豁免口②(转化矩阵:横向那一半要逐格追踪当期状态、且 AI Overview 实测给不出完整矩阵)收窄为四条同时成立,极少指令满足;第 1、4 条零成本先筛,别一上来跑 G1:
    1. 转化截止日在当期(NTM 已有部分成员国通报、但远未通报齐);
    2. 受约束主体是有名称且官方计数的普通企业(G6 第二问那一关);
    3. 判错代价是钱与时间,不是刑责(否则命中类别十一);
    4. 该买方群不是大所、合规 SaaS 厂商或倡导型 NGO 的现成关注对象——否则 tracker 早被当获客漏斗或倡导工具免费做掉了。零成本查一句:这个议题有没有一个以"把各州/各国做法摊开给公众看"为使命的组织?
  - 第 4 条是转化矩阵族的**注册前强制前置筛**:这个指令约束的那批人,是不是某类受理侧服务商(EOR、HR SaaS、合规 SaaS、大所)的核心客群?答是,不注册。索引 `pattern`:`转化矩阵已被受理侧 SaaS 做成获客漏斗`(1 例,待验证)、`多辖区矩阵已被免费 tracker 占位`。
  - 与类别十三互补:类别十三是受理方为收数自建判定工具,本条是想成为受理方的服务商为收客自建横向矩阵——谁在这条链上有结构性动机,谁就会免费把表做出来。
- **不覆盖**:①三问都过的逐对象判定——那正是这条赛道要找的;②满足四条的转化矩阵,且 G1 实测首屏给不出完整矩阵的——G1 记 pass 后回正常序列跑 G2/G3。

## 类别十三:发证机关自带吃对象的计算工具(前置筛除型 · 直接筛除型)

- **识别特征**:有日期的法规变化 → 受影响付费者明确、任务确实是"拿我这个对象去查一张大表或算一个数"(完全符合类别十二合取的两个条件)→ 但已有主体发了一个吃你的对象、直接出结果的东西。
  - 交付形态不限网页工具,更常见的是不起眼的形态:一份 Excel、一张 correlation table、一个在线申请系统的下拉、PDF 里附的计算模板、一份逐对象的判定解释例 / 对象非对象一览 / 附加声明 checklist、covered-materials 定义文档、免费判定软件或数据库、设计电子表格、体制强制设立的登记册。

## 类别十四:新旧法规过渡条款(前置筛除型 · 直接筛除型)

- **识别特征**:方向是过渡期判定——看起来天然多维(产品类型 × 首次投放市场日期 × 已有证书有效期 × 协调标准状态 × 是否实质性改动),有明确日期压力,过渡期的选择只体现在制造商自己的 DoC/DoP 里、没有人收这个判定结果。
- **死因**:立法者写过渡条款的目的正是消除不确定性——一份过渡条款如果本身需要逐对象判定,它就没有完成它被写出来的那件事。所以它天然被写成「一条时间线 + 一两个统一例外」,判定维度为 1,与正向画像①要求的「≥3 维、数百到数千条目」正好相反。
  - 第二道锁:即使分阶段,立法者一边规定分阶段、一边把阶段表公布出来(COM(2025) 772 Table 3 逐产品族带 "Standard made mandatory and DA adoption" 日期列)——按数据采集指南画像④第 2 句,清单带了搜索者要的那一列,位置从一开始就没有。
- **处置档**:直接筛除型,零成本判定,一次 SERP 都不必跑。索引 `pattern` = `过渡条款判定表只有一条时间线`。
- **零成本判法**:打开那部法规的过渡条款(通常是最后几条,标题为 Transitional provisions / Derogations and transitional provisions),数它有几段、有没有超过一个维度。一条时间线加统一例外 → 弃。
