# 生命周期契约

候选从捕获到建站决策的唯一状态机。状态只存在于 `数据/新词工作流/账本/候选账本.json`,只能由 `scripts/registrar.py` 写入。skill 提议转移,用户确认,registrar 执行——三者永不合并。

## 状态机

```
(新候选)
   │ xinci-scan 捕获
   ▼
captured ──G0–G5 全过──→ screened ──登记 expiry──→ tracking ──形成达标──→ formation_confirmed
   │                        │                        │    │                      │
   │任一闸门否决             │窗口以天计               │    │expiry 过,用户确认      │ xinci-qualify
   ▼                        │(快道)                  │    ▼                      ▼
rejected                    │                        │  expired          qualified / disqualified
                            ▼                        │                          │
                     xinci-decide 快速模式            │复查中 G1 翻转             │ xinci-decide
                            │                        │或竞品占位                 ▼
                            ▼                        ▼              ┌───────┬────────┬──────┐
                     fast_grab_ready              rejected          ▼       ▼        ▼      ▼
                            │                                 build_ready pilot_ready hold no_site
                            │用户建站/放弃                          │        │
                            ▼                                      └───┬────┘
                     built / expired                                   │用户建站
                                                                       ▼
                                                                     built
```

补充转移:

- 任何非终态候选可由用户转 `withdrawn`(主动撤回)或 `superseded`(被更好措辞的候选取代,`superseded_by` 指向新候选)。
- `hold` 可由用户送回 xinci-qualify 或 xinci-decide 重审(hold → build_ready / pilot_ready / no_site / disqualified)。
- `built` 的快道候选,词若被证明耐久,可由用户发起转回 `tracking`,走完整认定升级成正经全站。

终态:`rejected` / `expired` / `superseded` / `withdrawn` / `built`,以及决策终局 `disqualified` / `no_site`(除 superseded 外无出边)。

## 每转移的证据要求

registrar 逐项校验,缺证据即拒绝;完整表与 `scripts/registrar.py` 实现一致:

| 转移 | 必须提供 |
| --- | --- |
| register(→captured) | slug、term(精确措辞,禁转述)、source.url、task、≥1 个证据文件 |
| captured→screened | 闸门 G0–G4/G5 全 pass;**G3 为 pass 或 `veto_window_bet`**(后者是临时空位降级出口,判据见闸门契约 G3,额外要求 window_estimate=days + reason + by≠xinci-run);window_estimate ∈ {days, weeks, months};≥1 证据 |
| *→rejected | reason(失败闸门 + 现场证据要点) |
| screened→tracking | expiry(YYYY-MM-DD)+ ≥1 条失效条件 + ≥1 证据;**G3 不得为 `veto_window_bet`**(豁免候选只能走快道或 rejected,进追踪等于绕过 G3) |
| screened→fast_grab_ready | **仅限 window_estimate=days 的候选**;decision_ref(md 存在且同名 html 同批存在)+ expiry;play 固定 fast_grab;G3=`veto_window_bet` 的候选唯一的 go 出口 |
| tracking→formation_confirmed | 累计 ≥2 个 `-track` 观察,且最早与最新观察 observed_at 相隔 ≥7 天(形成期以周计,单次运行凑不出);本次 G1=pass;≥1 证据 |
| tracking→expired | reason(expiry 已过经用户确认 / 失效条件命中) |
| formation_confirmed→qualified | 整数 score ≥80 + G6/G7/G8 全 pass + ≥1 证据 |
| formation_confirmed→disqualified;hold→disqualified | reason(决定性缺口:哪一项、差多少) |
| qualified/hold→build_ready / pilot_ready | decision_ref md+html 双文件存在;play ∈ {single_domain, cluster_expansion} |
| qualified→hold / no_site;hold→no_site | reason;**不得**携带 decision_ref(no-go 不出决策书)。hold→hold 不是合法转移 |
| built→tracking | reason(升级理由)+ 新 expiry;**若原 G3=`veto_window_bet`,本次须带 G3=pass**(重跑 G3;快道豁免不可继承) |
| *→withdrawn | reason |
| *→superseded | superseded_by(账本中已存在的其他 slug);disqualified/no_site 的唯一出边 |
| checked(非转移) | ≥1 证据;更新 last_checked_at、追加证据、写一条 from==to 的 history 条目(记 by 与本次观察),不改状态 |
| amend(非转移) | 观察性字段修订,限 expiry 续期、追加 aliases/invalidation;reason 必填并入 history;终态不可修订。经用户确认后调用 |

证据文件除存在性外,registrar 还校验内容齐备性:必须是合法 JSON,含 slug(与候选一致)、observed_at、stage(与文件名 `-<阶段>.json` 一致)、非空 points;路径必须是数据区内相对路径(禁绝对路径与 `..`)。

## 连续运行模式(xinci-run)

用户显式启动 xinci-run 后,工作流进入连续运行,直至命中终止契约。此模式是**每次启动的选择**,不是默认;五个阶段 skill 单独调用时仍是提议-确认。

- **标准授权**:启动命令即构成对本次运行内全部 registrar 转移的授权,无需逐条确认;xinci-run 派出的子代理在同一授权范围内执行。闸门、评分线、证据要求**原样适用,不因连续模式软化**。
- **预算(有默认值)**:用户启动时可附 `max_rounds=N` / `max_hours=H`;**未指定时默认 `max_rounds=6`**。命中即正常收尾(处理同会话资源收尾:写运行清单、如实报告推进到哪,下次启动从账本现状继续)。预算是用户主权,不属于禁止的停止理由;不因缺参数暂停,按默认值开跑。
  设默认值的理由:下条列的"正常终止"第 2 项(额度耗尽)在单次运行内实际不可达——扫描期禁用 Semrush、形成期只允许轻探针、7 天跨度闸使单次运行做不出 formation_confirmed,因而单次运行烧不动额度。没有默认预算时"不限"实际等于跑到会话资源耗尽(收尾 C),那是操作边界而非任务边界;跨天累积应由定时任务按天驱动,而不是靠单次运行硬撑。
- **正常终止,仅两条**:
  1. registrar 记录任一 go 决策(fast_grab_ready / pilot_ready / build_ready)——找到了合适建站的关键词,停,交付决策书;
  2. Semrush 网页版额度耗尽——必须在网页界面**实际观察到**额度耗尽提示,并把提示要点记入运行清单;假设、推断、报错猜测都不构成额度耗尽。
- **正常收尾——会话资源耗尽**:执行者的上下文/会话资源接近极限时,完成当前动作、写运行清单、如实报告"会话资源耗尽,任务未完成、额度未耗尽"后停。这是操作边界,不是任务终点:不得伪装成终止 1 或 2;已完成的转移与清单保持有效,下次启动从账本现状继续。
- **异常中止**:认证、CAPTCHA、支付、浏览器封锁等 blocker 使所有可行工作停摆时,停止并如实报告 blocker。blocker 不是额度耗尽,不是完成,不得伪装成任何正常终止。
- **禁止的停止理由**:扫描空轮、候选池为空、"看起来找不到"、运行时间长、轮次多。空轮换来源、换角度(信号面↔变化面)继续。(会话资源耗尽属操作边界,不在此列。)
- **screen_unsatisfiable**:拒绝原因收敛到少数结构性模式时,写一份假设报告入运行清单并继续运行——它是发现,不是终止理由。
- **反空烧**:Semrush 纪律仍为 decision-changing only。额度是终止条件,不是消耗目标;为触发终止而空烧额度是禁止的。
- **去重**:每轮开始先读账本与淘汰方向索引(`数据/新词工作流/淘汰方向.md`);已弃候选与已记录的淘汰方向不重复评估。
- **如实说明**:形成期以周计,单次运行无法压缩。运行把存量候选推进到当下证据允许的最远处(tracking 复查、formation→qualify、qualified→decide),同时持续扫描新候选;单次运行内最可能先出现的 go 决策是快道(fast_grab_ready)。

## 时间字段:只记录,不调度

- 三个时间事实:`first_observed_at`(首见)、`last_checked_at`(上次复查)、`expiry`(失效日,附推理于证据)。
- **没有** next_check_at、默认复查间隔、调紧/放宽规则等任何调度机制。
- skill 被调用时只汇报时间事实("该候选 12 天未复查,expiry 还剩 5 天"),不据此自动做任何事。
- expiry 过期不自动转 expired:skill 提议,用户确认后 registrar 才执行。
- 复查哪些候选、何时复查、何时推进阶段,全部由用户决定。

## 证据与命名约定

- 观察文件:`证据/<slug>/<YYYY-MM-DD>-<阶段>.json`,阶段 ∈ {scan, track, qualify, decide};schema 见 `数据结构/observation.schema.json`。
- 观察只描述看到了什么,不携带读起来像裁决的字段;裁决只在账本。
- **数据极简原则**:只写简单清晰、服务于决策的内容——不写仪式性字段、不写过程流水账、不为"显得完整"而填充。观察写要点,不写转录。
- 运行清单:`运行/<YYYY-MM-DD>-<skill>.json`,每次运行一个小 JSON(日期、skill、打开过的来源、**被拦截的来源**、触及的候选、计费调用数),不写过程日志;字段约定见 `数据结构/run-manifest.schema.json`,**字段白名单由 `scripts/validate_ledger.py` 强制**(清单不经 registrar 写入,漂移只能靠它捕获)。被拦来源如实记入 `sources_blocked`——覆盖面缺口是事实,不是可以省略的失败。同日再次启动同一 skill 时,文件名追加启动时刻:`运行/<YYYY-MM-DD>-<HHMM>-<skill>.json`,不覆盖已有清单。xinci-run 连续运行只写一份自己的清单(轮次在其中追加),期间执行的各阶段流程不再另写各阶段清单。
- **淘汰方向索引**:`数据/新词工作流/淘汰方向.md`,追加式清单,每条一行:`- <YYYY-MM-DD> <词/方向> — <一句话:哪道门、为何>`。**留痕分界**:走到 G1 真实搜索及之后才被否决的候选,注册进账本再转 rejected(SERP 证据落观察文件);G0 / G4 / 陷阱类别 / 纯品牌名 / 无任务等零成本秒弃的方向,不注册,只追加一行进本索引。扫描与连续运行的开局去重读账本 + 本索引,不必翻历史运行清单。**归并纪律**:同一结构性模式在索引中第三次出现时,按陷阱类别.md 的追加规则把它归并成正式类别(附实际观察),并在索引补一行 `- <日期> [已归并] <模式> → 陷阱类别 <类别名>`;此后命中该模式的方向由 G5 直接筛掉,不再逐条记入索引——索引每行保持是独立方向,不随运行次数线性膨胀。

## registrar 用法

```bash
python3 xinci-workflow/xinci-core/scripts/registrar.py register \
  --slug <slug> --term "<精确措辞>" --source-url <URL> --task "<任务>" \
  --evidence "证据/<slug>/<日期>-scan.json"

python3 xinci-workflow/xinci-core/scripts/registrar.py transition \
  --slug <slug> --to <状态> --by <skill名> [--gates G0=pass,G1=pass,...] [--expiry YYYY-MM-DD] \
  [--invalidation "条件1;条件2"] [--score N] [--decision-ref 决策书/<slug>.md] \
  [--play ...] [--reason "..."] [--evidence <路径>]

python3 xinci-workflow/xinci-core/scripts/registrar.py checked \
  --slug <slug> --evidence "证据/<slug>/<日期>-track.json"

python3 xinci-workflow/xinci-core/scripts/registrar.py amend \
  --slug <slug> --by <skill名> --reason "<用户确认的修订理由>" \
  [--expiry YYYY-MM-DD] [--add-alias <别名>] [--add-invalidation "条件1;条件2"]
```
