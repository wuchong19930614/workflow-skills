# 生命周期契约

候选从捕获到建站决策的唯一状态机。状态只存在于 `<数据区>/账本/候选账本.json`,只能由 `scripts/registrar.py` 写入。

数据区定位、首次初始化与相对路径基准统一见 [通用约定.md](通用约定.md)「第 0 步」。本契约不重复定义环境配置。

授权形态:单步模式下 skill 提议转移、用户逐条确认、registrar 执行;xinci-run 连续模式把确认时点前移到启动命令(见「连续运行模式」),`G3=veto_window_bet` 的 `captured→screened` 仍须用户单步确认(见「窗口赌注的挂起与出闸」)。两种模式都不允许 skill 越过对应授权自行改变状态。

## 状态机

```
(新候选)
   │ xinci-scan 捕获
   ▼
captured ──有效初筛结论满足出闸要求──→ screened ──登记 expiry──→ tracking ──形成达标──→ formation_confirmed
  ↑ 也是扫描漏斗的排队位:本轮没走完的存活候选停在这里(gates 记已得结论、expiry 必填),
    下轮按 gates 补跑缺的门(缺 G1 先补 G1)再进深审;窗口过了走 captured→expired。
    还兼 G3=veto_window_bet 候选等待用户确认的挂起位(见「窗口赌注的挂起与出闸」)
   │                        │                        │    │                      │
   │任一闸门否决             │窗口以天计               │    │expiry 过,用户确认      │ xinci-qualify
   ▼                        │(快道)                  │    ▼                      ▼
rejected ←──快道 no-go──────┤                        │  expired          qualified / disqualified
                            ▼                        │                          │
                     xinci-decide 快速模式            │复查中闸门翻转             │ xinci-decide
                            │                        │或竞品占位                 ▼
                            ▼                        ▼              ┌───────┬────────┬──────┐
                     fast_grab_ready              rejected          ▼       ▼        ▼      ▼
                            │                                 build_ready pilot_ready hold no_site
                            │用户建站/窗口过                        │        │
                            ▼                                      └───┬────┘
                     built / expired                                   │用户建站
                                                                       ▼
                                                                     built
```

- "有效初筛结论满足出闸要求"精确定义为:G0/G1/G2/G4/G5=`pass`,G3=`pass` 或状态机兼容的 `veto_window_bet`;后者不是"G0–G5 全过",只可按窗口赌注专用出口推进。
- 图中未画全的边:`rejected` 有三个来源态(`captured` / `screened` / `tracking`);`expired` 有四个来源态(`captured` / `screened` / `tracking` / `fast_grab_ready`)。判据与提议人见「每转移的证据要求」。
- `hold` 可由用户送回重审,但不回 `formation_confirmed`(没有这条边;hold 已带 G6–G8 全 pass 与分数)。两个 skill 的输入核对都要接受 hold:
  - 送 xinci-qualify 重审,出口只有 `hold → disqualified`;
  - 送 xinci-decide 重审,出口是 `hold → build_ready / pilot_ready / no_site`。
- `built` 的快道候选,词若被证明耐久,可由用户发起转回 `tracking`,走完整认定升级成正经全站。

**终态集**是代码校验分组,由归档态 `rejected` / `expired` / `superseded` / `withdrawn` / `built` 与决策终局 `disqualified` / `no_site` 组成,不等同于"全部再无出边":

- `disqualified` / `no_site` 只可转 `superseded`(registrar 的 `SUPERSEDABLE_FINAL` 只含这两个);那是被更好的措辞取代,不是候选自己往前走。
- `built` 账本上不可 `checked`、不可 `amend`,只保留升级出边 `built → tracking`;`built → superseded` 不可用。它是唯一保留升级出边的终态。
- `rejected` / `expired` / `superseded` / `withdrawn` 无出边;`rejected` 另有下述受控重开。

### 受控重开

不是普通状态边。`rejected` 若决定性否决只来自会腐烂的 G1/G2/G3 SERP 事实,registrar 写入 `recheck_after`;到期只进入 xinci-status 的复核清单,不自动改变状态。同时满足下列两条,才能用 `registrar.py reopen` 回到 captured,清空旧窗口闸门并重新走全套初筛:

- 取得晚于最近拒绝时间的新现场观察;
- 观察中的 gates 把当时每一道 veto 都明确翻转为 `pass`。

只换一个新文件名、复用旧截图或只翻转部分 veto 都拒收。G0/G4/G5 的结构性否决不可重开。

承接与授权:new 道由 xinci-track 复核,mature 道由 xinci-mature 复核;单步模式先提议、用户确认后执行 `reopen`。xinci-run 可在活动轮内复核并重开 new,但不得借 `reopen` 推进 mature 前半程。registrar 按重开后的目标态 captured 执行 lane/actor 硬校验。

## 每转移的证据要求

registrar 逐项校验,缺证据即拒绝;完整表与 `scripts/registrar.py` 实现一致。提议人一列指单步模式:由该方提议、用户确认;连续运行模式下一律由 xinci-run 按标准授权直接执行(唯一例外见「窗口赌注的挂起与出闸」)。

| 转移 | 提议人 | 必须提供 |
| --- | --- | --- |
| register(→captured) | xinci-scan;`lane=mature` 归 xinci-mature | slug、term(精确措辞,禁转述)、source.url、task、≥1 个证据文件;可选 gates(排队位带已得闸门结论),带 gates 时 expiry 必填;`by=xinci-run` 另有三项硬要求,见「register 补注」 |
| captured→screened | 同 register | G0/G1/G2/G4/G5=`pass`,G3 为 `pass` 或 `veto_window_bet`;window_estimate、窗口失效日 expiry、≥1 证据。expiry 由 registrar 强制,排队位旧 expiry 必须在出闸时覆盖。连续模式的窗口赌注还要求活动 run_id 中存在一次未消费的用户确认记录 |
| captured/screened/tracking→rejected | 判否的一方(`screened`:xinci-decide 快道;`tracking`:xinci-track 复查;⑥:做归并的一方) | reason(失败闸门 + 现场证据要点);八种情形见「rejected 的八种情形」 |
| captured→expired;screened→expired | 见「四条 expired 边各自的提议人」 | `expiry_trigger=date` + reason(expiry 已过经用户确认——captured 是排队没排上,screened 是出闸后窗口自己过了)。registrar 实测账本 expiry ≤ 当前日期,未来日期拒收 |
| screened→tracking | xinci-scan(出闸后按窗口分流提议) | expiry(YYYY-MM-DD)+ ≥1 条失效条件 + ≥1 证据;G3 不得为 `veto_window_bet`(窗口赌注候选只能走快道或 rejected,进追踪等于绕过 G3) |
| screened→fast_grab_ready | xinci-decide 快速模式 | 仅限 window_estimate=days 的候选;decision_ref(md 存在且同名 html 同批存在)+ expiry;play 固定 fast_grab;G3=`veto_window_bet` 候选唯一的 go 出口 |
| fast_grab_ready→expired | xinci-decide | `expiry_trigger=date\|window_closed` + reason:date 要求账本 expiry 已到;window_closed 表示通用工具已收录该对象、赌注前提消失。赌注没赌成走这条边,不是 rejected |
| tracking→formation_confirmed | xinci-track;`lane=mature` 归 xinci-mature | 累计 ≥2 个 `-track` 观察,且最早与最新观察的 observed_at **自然日**相隔 ≥7 天(口径见「时间字段」);本次 G1=pass;本次 track 观察明确 `naming_status=stabilized`,且 `formation_signals` 至少一项;≥1 证据 |
| tracking→expired | xinci-track;`lane=mature` 归 xinci-mature | `expiry_trigger=date\|invalidation` + reason:date 要求账本 expiry 已到;invalidation 要求候选已有失效条件并写明本次命中的事实 |
| formation_confirmed→qualified | xinci-qualify | 整数 score ≥80 + `income_score` 为 1–20 + `g6_passed_lines` 至少一项(`lane=new` 不得含 advertising)+ G6/G7/G8 全 pass + ≥1 证据 |
| formation_confirmed→disqualified;hold→disqualified | xinci-qualify | reason(决定性缺口:哪一项、差多少)+ 本次 `-qualify` observation;不得只凭文字理由推翻认定 |
| qualified/hold→build_ready / pilot_ready | xinci-decide | decision_ref md+html 双文件存在且 html 内源 SHA-256 与当前 md 一致;play ∈ {single_domain, cluster_expansion} |
| qualified→hold / no_site;hold→no_site | xinci-decide | reason;不得携带 decision_ref(no-go 不出决策书)。hold→hold 不是合法转移 |
| fast_grab_ready/build_ready/pilot_ready→built | 建站是用户的人工动作(决策书交付后各阶段 skill 已停);建完站由用户告知,由用户或任一 skill 执行 `transition --to built --by <执行者>` | registrar 不作额外校验(decision_ref、分数、play 在进入 go 决策态时已校验过)。建议带 reason 记站点落地情况:built 之后不可 `checked`、不可 `amend`,不写就没地方补 |
| built→tracking | 用户 | reason(升级理由)+ 新 expiry;若原 G3=`veto_window_bet`,本次须带 G3=pass(重跑 G3;快道降级结论不可继承) |
| 非终态→withdrawn | 用户(主动撤回) | reason |
| 非终态/disqualified/no_site→superseded | 用户 | `superseded_by`(账本中已存在的、措辞更好的新候选 slug);disqualified/no_site 的唯一出边;rejected/expired/superseded/withdrawn/built 不可走此边 |
| defer-qualify(非转移) | xinci-qualify | 只对 `formation_confirmed`;≥1 个本次 `-qualify` 观察、≥1 项 `pending_evidence`、`pending_until` 在未来、reason 说明为何是环境性缺失。写 `qualify_pending` 与一条 from==to 的 history 条目,不出分、不改状态;判据见评分契约「证据缺失分两种」 |
| checked(非转移) | xinci-track | ≥1 证据;更新 last_checked_at、追加证据、写一条 from==to 的 history 条目(记 by 与本次观察),不改状态。同一自然日不重复复查,见「checked 补注」 |
| amend(非转移) | 提议方,经用户确认后调用 | 观察性字段修订,限 expiry 续期、追加 aliases/invalidation,以及 `captured` 候选补记闸门结论(`--gates`,见「amend 补注」)。reason 必填并入 history;终态不可修订 |

证据文件除存在性外,registrar 还校验内容齐备性:必须是合法 JSON,含 slug(与候选一致)、observed_at、stage(与文件名 `-<阶段>.json` 一致)、非空 points;路径必须是数据区内相对路径(禁绝对路径与 `..`)。

**register 补注**:`by=xinci-run` 注册必须带 `site_thesis`、≥2 个 `task_families`、`origin=signal|trigger`(trigger 来路还要 `trigger_ref`,CLI 写作 `--trigger-id`)。
单步模式下 registrar 不强制这三项,但 xinci-scan / xinci-mature 推荐前两项照样写。

**rejected 的八种情形**(编号供全文引用):

- ①G2 深审否决(captured);
- ②G3 占位否决对仅靠 affiliate/advertising 的模式生效(captured / tracking);
- ③复查中 G0/G1 翻转(tracking);
- ④快道读完证据判定赌注不值(screened);
- ⑤已注册的排队候选补跑 G1 被否(captured,须带 `atomic_only` 反事实);
- ⑥用户确认新归并陷阱类别后,当前 tracking 候选命中该类别(单步 new 由 xinci-track、mature 由 xinci-mature 提议;连续运行只记提案,不在标准授权内改契约);
- ⑦六条 G6 适用盈利线全部暂定否决(captured / tracking;`screened` 已过初筛、不再另做六线预筛,不在此列);
- ⑧G6 结构事实否决,见「G6 结构事实的出口边界」。

第⑦种必须提交 schema v2 scan/track observation 的完整 `g6_tentative_lines`,不得伪造正式 `gates.G6=veto`;任一非流量型盈利线暂定或正式可行时,占位事实只进入竞争记录,不得走 rejected。未注册方向的 G1 否决只进淘汰索引,但同样必须完成 `atomic_only` 站点簇反事实。

**四条 expired 边各自的提议人**(没有提议人的边等于不存在。四条边都没有失败的闸门,不得硬塞进 `rejected`;由用户确认后转,连续运行模式下由标准授权覆盖):

- `tracking→expired`:xinci-track 复查后提议;
- 排队中的 `captured→expired`:xinci-scan 开局接队时提议。带 `G3=veto_window_bet` 挂起等确认的候选同样是排队中的 `captured`,expiry 过了走同一条边——挂起不免疫过期;
- 以上两条边在 `lane=mature` 上都归 xinci-mature(xinci-scan 不接 mature 排队、xinci-track 不收 mature 追踪,见「lane 边界」);
- `screened→expired` 与 `fast_grab_ready→expired`:归 xinci-decide——前者是它快道模式的输入、后者是它的产出,由用户按 xinci-status 报出的到期清单把候选送给它;
- 连续运行模式下四条一律归 xinci-run 运行循环步骤 1,标准授权直接转,没有提议环节。

**checked 补注**:registrar 比对本次与已登记的 `-track` 观察的 `observed_at` 日期,撞车即拒。边界按观察日划、不按 run 划:同一天的两次运行同样受限;一天之内补录两份不同观察日的 `-track` 不受影响。确需当日重测(典型是上次复查时浏览器处于登录态、G1 结论不成立)时传 `--same-day-reason`,理由写进 history。

**amend 补注**:补记 gates 是排队位/挂起位在账本上唯一的 gates 写入口(`captured→captured` 不是转移,transition 写不了它;典型是还债深审判出 `G3=veto_window_bet`)。限制三条:

- 仅限 `captured`;
- 补记后必须有 expiry;
- 带 gates 必须同时用 `--evidence` 提交本次 observation 且逐门一致。

### 窗口赌注的挂起与出闸

`G3=veto_window_bet` 是 G3 的独立降级结论——不是 `pass`,也不是普通 `veto`。它出闸意味着用户接受"位置可能只空几天"的额外风险,不在连续运行的标准授权内;单步模式下同样须用户确认。

- **挂起位**:深审判出 `G3=veto_window_bet` 而转移尚未被确认时,候选留在 `captured`,gates 里带 `G3=veto_window_bet`、带 expiry;观察文件记明降级依据(数到的免费实现清单 + 收录时差实测)并填结构化 `window_bet`(见「证据与命名约定」)。
  这是合法挂起位,`validate_ledger` 认这个状态;连续运行下必然先经过它。
- **不许替代性处置**:转 `rejected` 是错的(它仍有待确认的快道出口),转 `screened` 是绕过拒收。运行清单 notes 记一句"有候选待用户单步确认窗口赌注",运行照常继续——它不是 blocker。
- **连续模式的确认机制**:用户明确接受后,由 `run_controller.py confirm-window-bet` 写入候选级一次性确认;registrar 要求本次活动 run_id 中存在该候选的一次未消费确认,没有即拒收 `by=xinci-run` 的出闸,成功出闸后消费它。确认不可预埋、覆盖或消费后重新激活。
- **gates 怎么写进账本**:本轮新扫方向判出这一档的,在 `register` 时带上 gates、expiry 与支撑同一结论的 evidence(按排队位注册);账本中已存在的排队候选补审才形成这一结论的,用 `registrar.py amend --gates G3=veto_window_bet --evidence <本次观察>`(附 `--reason` 降级依据)补记——`captured→captured` 不是转移。observation.gates 必须一致、`source_urls` 非空,并填写结构化 `window_bet`;只把判断写进命令或 points 会被拒收。
- **出闸后的路径**:只能走快道 `screened→fast_grab_ready`(唯一 go 出口)或 `rejected`,不得进 `tracking`;`built→tracking` 升级时须重跑 G3 并带 G3=pass。挂起不免疫过期,expiry 过了走排队中的 `captured→expired`。
- **与 G3=pass 快道的分界**:G3=`pass` 的快道跳过 G6–G8 是契约内的既定减配路径,在标准授权内;决策书必须逐条做风险披露与授权状态说明,不得把交付后的阅读写成事前"用户已确认"。

## 连续运行模式(xinci-run)

用户显式启动 xinci-run 后,工作流进入连续运行,直至命中终止契约。此模式是每次启动的选择,不是默认;五个有写入能力的阶段 skill(xinci-scan / track / mature / qualify / decide)单独调用时仍是提议-确认(xinci-status 零写入,没有转移可确认)。

**每轮 admission 策略是硬契约**:

- 恢复/创建 run 后,由本轮实际执行者以稳定 `executor_id` 执行 `begin-round`,并在同一条命令里提交浏览器预检四项(`--browser-controllable / --browser-desktop / --browser-region / --browser-logged-out`);预检写进 session 的当前轮,`run_policy.py` 与 registrar 只读它。父任务、其他子代理和上一轮的预检都不能借用。
- 只有 `full` 可新增正式候选。组合条件的优先级固定("无 G1 环境"与"积压 >20"同时发生时以 `trigger_only` 为准):
  1. 无 G1 环境 + trigger pending 达 200 → `paused`;
  2. 其他无 G1 环境 → `trigger_only`;
  3. G1 环境合规时,`lane=new,state=captured` 积压 >20 或连续三轮无真实决策迁移且队列增长 → `debt_only`;
  4. 否则 → `full`。
- registrar 的正式 CLI 在 register 前复核 `formal_admission`。`queued` 与初次 `from=null→captured` 都不是决策推进;推进只认既有候选 `from` 非空且 `to != from` 的 history 迁移。
- 停滞 ≥3 轮触发的 `debt_only` 只管本轮 admission(本轮不再新增候选),本轮 `record-round` 之后即按「收尾 E」结束运行,不再开下一轮;两者是同一件事的两步。它与 `calibration` 轮型(每累计 10 个 discovery 轮在 run 内强制插入一轮,见「schema v3」)是两套机制:前者是终止,后者是轮次。

**触发池与候选账本分层**:

- 法规、平台或技术变化的官方标题先写 `触发池.jsonl`,不得直接作为候选 term。trigger 只有在出现用户实际会搜索的 task query、至少一个独立搜索语言证据 URL,并补齐 payer、重复对象单元、自助交付路径、基础情景来源后才可 approve;approve 仅允许进入 G0。
- xinci-run 注册变化面候选必须带 `origin=trigger + trigger_ref`(CLI 写作 `--origin trigger --trigger-id <id>`,账本字段名为 `trigger_ref`),registrar 核对 trigger 已批准且 candidate term 与批准 query 一致。
  社区/信号面则显式记 `origin=signal`。
- 来源轮换:单一 source family 不得连续主导超过两轮;本 run 累计新增 trigger 达到 5 条后,任何 family 占比超过 40% 也必须轮换(5 条以前不启用占比规则,连续轮次规则仍独立生效)。
  - 轮换由 `run_policy.py` 返回 `blocked_source_families`,由 `trigger_pool.py add` 在写入口硬校验。
  - 命中时只暂停对应 family;只要策略仍给出 `trigger_harvest=true`,就换其他来源继续,不得实现成关闭全部触发采集。

**lane 边界**:

- `lane=new` 可由 xinci-run 推进全生命周期。
- `lane=mature` 在 `formation_confirmed` 前由 xinci-mature 单步承接,活动 run 不得操作其 captured/screened/tracking,也不把它们计入 new 道积压;mature 合法进入 `formation_confirmed` 后,xinci-run 才可调用 xinci-qualify / xinci-decide 接续。
- 前半程若已把 mature 合法送到 `screened` 且窗口为 days,用户仍可显式单步调用 xinci-decide 做快道决策或到期处置;这是决策 skill 的人工入口,不授权 xinci-run 自动推进 mature 前半程。
- xinci-mature 本身不在 xinci-run 的标准授权内——它是单步形态,每次转移都要用户确认(依据:校准 §8、§12.7)。

**授权与终止**:

- **标准授权**:启动命令即构成对本次运行内既定路径上的 registrar 转移的授权,无需逐条确认;xinci-run 派出的子代理在同一授权范围内执行。唯一的转移例外是 `G3=veto_window_bet` 的 `captured→screened`。分界线是「执行已接受的既定路径」与「接受额外窗口赌注风险」。闸门、评分线、证据要求原样适用,不因连续模式降低。
- **预算(轮次上限始终存在)**:用户启动时可附 `max_rounds=N` 和/或 `max_hours=H`;未显式给 `max_rounds` 时默认 6,即使只给了 `max_hours`。两项同时存在时谁先命中就走收尾 D;若希望主要按时长运行,须同时给足够大的 `max_rounds`,没有"轮次无限"这一档。预算是用户主权,不属于禁止的停止理由;不因缺参数暂停,按默认值开跑。
- **预算只算能干活的轮次。** 预检申报了但四项没过的轮次是**降级轮**:它做不了 G1、只能维护触发池,因此不消耗 `max_rounds`(控制器按 `rounds_completed - degraded_rounds` 判预算)。代价是不许无限降级:连续 3 个降级轮后控制器拒绝再开轮,执行者要么修好干净未登录通道,要么以「执行受阻」收尾——这也解决了「`trigger_only` 永远算可行工作,于是浏览器整场不可用时既不能停也不产出」的死角。没提交预检的轮次不算降级,照常消耗预算(否则省略预检就能白拿轮次)。
- 每轮的预检四项随 `record-round` 写进运行清单的 `browser_preflight`,事后可核对;不必再靠 notes 手写复述。
- **正常终止,仅两条**:
  1. **终止 A**:registrar 记录任一 go 决策(fast_grab_ready / pilot_ready / build_ready)——停,交付决策书。
     两类 go 的分量不同,不许混说:build_ready / pilot_ready 过了 G6–G8 与 80 分线,是"值得建站";fast_grab_ready 是"一份标好价的窗口赌注",按闸门契约 G8 的减配说明,不等于被验证的生意;
  2. **终止 B**:Semrush 网页版额度耗尽——必须在网页界面实际观察到额度耗尽提示,保存截图或其他可复核文件,并在 `finish` 传 `--evidence-ref <数据区相对路径>`;只写提示要点、假设、推断或报错猜测都不构成额度耗尽。
- **正常收尾 C(会话资源耗尽)/ D(预算命中)**:完成当前动作、写运行清单、如实报告后停——C 报"会话资源耗尽,任务未完成、额度未耗尽",D 报推进到哪与预算命中。这是操作边界,不是任务终点:不得伪装成终止 A 或 B;已完成的转移与清单保持有效,下次启动从账本现状继续。
- **收尾 E(连续三轮无真实决策迁移且队列增长)**:`run_policy.py` 的 `consecutive_decision_stall_rounds >= 3` 时本轮策略为 `debt_only`,完成当前轮 record-round 后以 `finish --status 已触发闸门校准` 结束运行,再转入闸门、来源与容量校准;下次启动前由用户单步做校准。
  不把 queued 当成功:它只证明又登记了新债。校准记录必须分别回答筛子是否过紧、浏览器是否阻断 G1、source family 是否单一、还债容量是否不足。
- **异常中止**:认证、CAPTCHA、支付、浏览器封锁等 blocker 使所有可行工作停摆时,停止并如实报告 blocker。blocker 不是额度耗尽,不是完成,不得伪装成任何正常终止。
- **禁止的停止理由**:扫描空轮、候选池为空、"看起来找不到"、运行时间长、轮次多。按运行策略换来源、维护触发池或还债;只有契约化预算、校准、资源或 blocker 才收尾。
- **screen_unsatisfiable**:拒绝原因收敛到少数结构性模式时,写一份假设报告入运行清单并继续运行——它是发现,不是终止理由。
- **反空烧**:Semrush 纪律仍为 decision-changing only。额度是终止条件,不是消耗目标;为触发终止而空烧额度是禁止的。
- **去重**:每轮都要去重,时点是本轮提取出方向之后、花任何筛选成本之前(同 xinci-scan 第 0 层「执行时点」)——用 `screen_index.py check` 批量查,一次覆盖淘汰索引与账本;已弃候选与已记录的淘汰方向不重复评估,索引本身不进上下文。命中的方向不计入 funnel 的 `extracted`(它们上一次已有归宿)。
- **如实说明**:形成期以周计,单次运行无法压缩。运行把存量候选推进到当下证据允许的最远处(tracking 复查、formation→qualify、qualified→decide),同时持续扫描新候选;单次运行内最可能先出现的 go 决策是快道(fast_grab_ready)。

## 时间字段:只记录,不调度

**形成跨度按自然日算,不按满 24 小时算(全文唯一口径)。** 起点是最早那份 `-track` 观察**文件**里的 `observed_at` 所在的自然日,终点是本次观察那天;`最早观察日 + 7 天` 就是最早可提交 `formation_confirmed` 的日子。

- 不要拿账本 history 里 `tracking` 那条的时间戳去推:两者可以差几十分钟(实测 `cpr-avcp-system-per-product`:history 03:42Z、观察文件 04:10Z),按 history 推算会早到被拒。
- 该日子由 `report_status.py` 与 `tracking_schedule.py` 直接给出(`formation_eligible_date`),与 registrar 判据同源,不必自己算。
- 3/7/14 天复查提醒按进入 tracking 起算,是"该再看一眼了",与"够不够跨度"是两件事;提醒逾期不代表可以推进。

- 三个时间事实:`first_observed_at`(首见)、`last_checked_at`(上次复查)、`expiry`(失效日,附推理于证据)。
- 没有 next_check_at、默认复查间隔、调紧/放宽规则等任何调度机制;没有任何时间字段会自己触发转移。
- skill 被调用时只汇报时间事实("该候选 12 天未复查,expiry 还剩 5 天"),不据此自动做任何事。
- expiry 过期不自动转 expired:单步形态下 skill 提议、用户确认后 registrar 才执行;连续运行模式下授权时点前移,`captured→expired`、`tracking→expired` 由 xinci-run 按标准授权直接执行,不再逐条回头问——这表示用户授权执行既定路径,不等于用户事前读过每个候选或逐条确认过风险。
- 复查哪些候选、何时复查、何时推进阶段、哪些候选进入本次运行、要不要启动连续运行,全部由用户决定。

## 证据与命名约定

- **观察文件**:`证据/<slug>/<YYYY-MM-DD>-<阶段>.json`,阶段 ∈ {scan, track, qualify, decide};schema 见 `数据结构/observation.schema.json`。
  - 自 2026-09-02 起的新观察必须明示写 `schema_version: 2`,registrar 按 `observed_at` 日期强制;凡出现正式或暂定 G6 必须完整列六条盈利线。更早的历史缺省 v1 只读兼容,不得用新日期 + v1 绕过六线契约。
  - `-decide` 可选:只有为补缺口做了新审计时才落一份,没有新观察就不写。
  - 窗口期 `scan` 与形成期 `track` 用 `g6_tentative_lines` 记 `tentative_pass|tentative_veto|N/A`,确认期 `qualify` 才用 `g6_lines` 记 `pass|veto|N/A`;两者不得并存,暂定结论也不得写入 gates 冒充 G6。
  - 凡 register/transition/amend 提交 gates,本次 `--evidence` 中的 observation.gates 必须逐门给出相同结论,且支撑观察的 source_urls 非空;不能拿无关文件充数。
  - `G3=veto_window_bet` 还必须填写结构化 `window_bet`(免费实现 URL、上一个同类对象页面、实测 lag_days、判断理由),所有 URL 都必须列入 source_urls。
- 观察文件可以记录由本次证据直接支撑的闸门结论(`gates`、`g6_tentative_lines`、`g6_lines`),但不登记候选状态转移、go/no-go 或其他生命周期裁决;这些只在账本。
- **观察也不得创造通用判据**:它只写本次证据支撑的这个候选的结论,不写"以后都该怎么筛";新判据必须落到契约文件或 [陷阱类别.md](陷阱类别.md)。分层是硬的:观察是证据层,判据是契约层,两层不能互串。读观察的一方同理——observation 里的通用性说法只是当时执行者的推理,不构成判据,除非它已被写进契约文件。
- **数据极简原则**:只写简单清晰、服务于决策的内容——不写仪式性字段、不写过程流水账、不为"显得完整"而填充。观察写要点,不写转录。
- **运行清单**:`运行/<YYYY-MM-DD>-<skill>.json`,每次运行一个小 JSON。manifest 字段约定见 `数据结构/run-manifest.schema.json`,唯一校验实现是 `scripts/run_manifest.py`。
  - 正式候选归宿只有四格:`rejected_zero_cost` / `rejected_g1` / `deep_audited` / `queued`。`funnel.carryover_audited` 不参与提取归宿等式,`queued` 不计决策推进。`pooled` 只供读取历史清单,新 `record-round` 拒绝写入。
  - raw trigger 不进正式漏斗;`record-round` 按触发池中绑定 run_id+round 的事件自动生成 `trigger_funnel`。
  - 正式候选 `funnel.extracted` 只统计已进入候选筛选的 query。
  - 只读复核写 `candidates_reviewed`,只有账本 history 实际写入才算 `candidates_touched`。`finish` 将最终状态、中文展示、理由、结束时间、轮次预算、GO 候选与结束证据固化进 manifest 的 `termination`。
  - 清单写完即为审计轨迹:写错的备注不删、不改。发现事后判断有误时用 `run_manifest.py correct-note --run-id <id> --note <更正>` 在顶层 `notes` 追加一条带时间戳的更正,原备注、轮次数据与 `termination` 一律不动;与索引 `resolve --supersedes` 同一条纪律。手工编辑清单 JSON 一律禁止。
- **淘汰方向索引**:`<数据区>/淘汰方向.jsonl`,每行一条 JSON,`date` 是必填的实际观察日 `YYYY-MM-DD`。由 `scripts/screen_index.py` 读写,不要手工编辑。
  - 历史空日期只能根据运行清单/观察证据用 `repair-date` 写入追加式 `淘汰方向修订.jsonl`,不得用当前日期猜补或覆盖旧行。
  - `[疑似重复·须快审]` 必须用 `resolve` 闭环;错误裁决只可 `--supersedes` 追加修订。
- **触发池**:`<数据区>/触发池.jsonl` 是官方变化原料的事件日志,状态为 pending/approved/discarded;它不是候选账本,不产生正式结论。raw trigger 只进独立 `trigger_funnel`,注册成候选之后才按 `deep_audited` / `queued` 等归格。
  - `discarded` 是终态,不可重开或覆盖。
  - `approved` 保留唯一一条 discard 出边——批准只表示可进 G0,方向随后被闸门否决(典型是 G1 实测 veto)时作废,reason 写明失败的闸门与现场结论。

**G6 结构事实的出口边界(rejected 边第⑧种)**:

- `repeat_paid_task` 只否决 subscription;`official_count_class` 只否决依赖该统计口径的算式。二者写入 `g6_entry_veto` 时必须同时完整列六条 `g6_tentative_lines`,只有所有适用线全灭才能走 rejected。
- `self_serve_legal_effect` 若证明所有声称的自助交付依法都无效,可作为整候选的独立结构否决。
- 三者都不写正式 `gates.G6`;tracking 只在新证据暴露结构事实时触发。

### 留痕分界

分界线是「这一条的现场证据值不值得单独留档」。两种情况注册进账本,其余都只配一行索引:

1. 它还有下一步(深审存活、排队待审);
2. 它的结论来自 G2/G3 深审——哪怕结论是出局(深审每轮配额 ≤5,它数到的免费实现清单、结构阅读要点、footprint 观察是该方向独有的证据,索引的一行 reason 装不下)。

只配一行索引的是成本低、数量大到留档会淹没账本的那些:批量秒弃、G1 否决、已归并的陷阱类别命中——死因是类别级的,单个方向没有独立留档价值。

**收口规则**:上面两条判的是「要不要注册」;一旦注册过,后续处置只在账本一侧。「G1 否决走索引」只说本轮首次见到、尚未注册的方向;已注册的排队候选补跑 G1 被否走 `captured→rejected`(第⑤种),索引管不着已注册的候选。

具体分派:

- **只追加一行进本索引,不注册**:零成本秒弃(G0 / G4 / G6–G7 预筛 / 无任务)、未注册方向的 G1 否决、陷阱类别命中,以及 mature 道不属于 G0–G8 的前置排除。前置排除省略 gate,改写 `stage=prescreen + reason_code`,不得借用 G3 等正式闸门名。
  - 新写入的 G1 否决除首屏证据要点外,还必须携带 `cluster_counterfactual=atomic_only`,证明批处理、监控、审计轨迹、导出集成、多辖区五种扩展均不形成独立任务;否则索引拒收。
  - 已注册排队候选补跑 G1 被否走 `captured→rejected`,同样由 observation 的 atomic_only 反事实支撑。
- **注册进账本**,三类:
  - ①走到 G2/G3 深审且存活的候选,按「下一步是不是就出闸」分两类。
    - a 类:本轮已走完 G0–G5 全程、下一步就出闸——register 只带证据,闸门结论与 `window_estimate` 随紧接着的出闸 `captured→screened` 一起提交(`register` 没有 `--window-estimate` 参数,带 `--gates` 会被强制要 `--expiry`,那是排队位的字段)。
    - b 类:深审存活但前面的门还缺(典型是 G5 陷阱验证取得有效 `pass`,或 G3 在占位否决生效前提下判出合法 `veto_window_bet`——含账本中已带该结论的历史兼容候选——而 G1/G2 尚未跑)——按②的排队位注册:`captured` + gates(含已得的 G3 结论)+ expiry。
      注册之后它回正常序列、在本轮继续补 G1/G2;只有本轮没排上(超 G1 上限或超深审配额)才留在 `captured` 到下轮。funnel 归格随之定:本轮走完就是 `deep_audited`,没排上才是 `queued`。
  - ②超配额排队的存活方向(`captured` + gates + expiry)。
  - ③走到 G2/G3 深审但被否决的候选——G2 结构阅读判否、或在占位否决生效前提下 G3 判 `veto`——先 register 再走 `captured→rejected`,reason 写清失败闸门与现场证据要点(数到的免费实现、结构阅读结论)。
    subscription / lead_generation / transaction / paid_report 任一暂定可行时,占位事实只进入竞争记录,G3 有效门结论写 pass,不属于③。
- **陷阱类别的一个例外**:命中陷阱类别、当场跑 G3 验证且占位否决确实生效时,判 `veto` 的方向留在索引一侧——该模式已是正式类别,单个方向没有独立留档价值;这一次数到的免费实现清单按陷阱类别.md 的追加规则写进该类别节里(证据落在规则文档,不落在候选证据区)。
  - subscription / lead_generation / transaction / paid_report 任一暂定可行时,同样的占位事实只记作竞争输入,G3 有效门结论写 `pass`,按①的 b 类注册进账本。
  - 判出的是 `veto_window_bet` 而不是 `veto` 时,它有了 go 出口(快道),必须注册进账本,索引不再记它。
- 扫描与连续运行的开局去重用 `screen_index.py check` 一次覆盖索引与账本,不必翻历史运行清单,也不必把任何一方读进上下文。

**归并纪律**:

- 每当认出一个新的结构性模式,执行者先以实际观察形成“新增类别 + 处置档 + 当前候选归并”的提案。新增或改写通用判据属于契约变更,不包含在 xinci-run 的标准授权里;用户确认后才按陷阱类别.md 的追加规则写入正式类别。发现即可提案,不必凑满三次——"≥3 次观察、跨日期、跨来源家族"是 SERP 陷阱型改标直接筛除型的门槛,不是提出或确认建类的门槛。
- 改档计数时索引一侧的秒弃 + 账本一侧的深审否决合并计数。`screen_index.py stats` 在某 `pattern` 累计 ≥3 次时提示该归并了——那是漏归并的兜底提醒,不是建类门槛;且它只看索引一侧(账本没有 `pattern` 字段,`stats` 只读 `淘汰方向.jsonl`)。
  账本一侧靠人:深审判否时若死因看起来是一个结构性模式,把模式名记进本次运行清单的 notes,改标直接筛除型前把两侧的次数合起来核一遍。
- 用户确认归并后在索引补一条归并记录:`term` 写模式名本身,不是任何一个具体方向(写成具体方向会被 `append` 的 term 去重静默跳过);`gate` 记 G5;`reason` 以 `[已归并]` 开头并指向类别号;`pattern` 填该模式名:
  `printf '%s\n' "厂商已占位的 B2B 强制任务|G5|[已归并] 见陷阱类别.md 类别三|厂商已占位的 B2B 强制任务" | python3 xinci-workflow/xinci-core/scripts/screen_index.py append --date <YYYY-MM-DD>`
- 此后命中该模式的方向由 G5 按该类别自带的处置档处理——「直接筛除型」零成本弃,「验证型」仍要跑 G3 验证。新类别的处置档按死因型定:SERP 陷阱型默认验证型、前置筛除型一律直接筛除型,见陷阱类别.md。
- 改标直接筛除型省掉的是"第四次验证同一个死因";归并本身不省验证(验证型类别照常跑 G3),更不省留痕:秒弃照常追加一行索引(gate 记 G5),否则下轮 `screen_index.py check` 认不出它。`screen_index.py append` 按归一化 term 跳过重复,每行始终是一个独立方向,索引不会因此线性膨胀。

## registrar 用法

### 中文交付与机器码边界

账本、schema 与 Python API 中的状态值是稳定机器码,不做破坏性迁移。面向用户的状态汇报、终止原因、错误解释与最终交付必须使用中文展示名;不得把 `budget_reached`、`active`、`captured` 等机器码直接当作自然语言结论。命令行控制器默认输出中文,只有机器解析时才显式使用 `--json`。

### `--by` 取值:按**运行模式**定,不按命令所在的文档定

`--by` 记执行者;连续运行授权还必须由活动 `run_id` 证明,不再相信调用者自报身份:

| 运行模式 | `--by` 取值 | 含义 |
| --- | --- | --- |
| 单步调用某个阶段 skill | 该 skill 名(`xinci-scan` / `xinci-track` / `xinci-qualify` / `xinci-decide` / `xinci-mature`) | 用户逐条确认过这次转移。`xinci-mature` 另受 registrar 硬校验:它只能写 `lane=mature` |
| xinci-run 连续运行(含它派出的子代理) | `xinci-run` + `--run-id <活动会话>` | 标准授权;会话必须已 begin-round |
| 用户亲自手工执行(无 skill 承接的单步操作:`built` 登记、闸门重算后的出清) | `user` | 用户本人决定并执行这次写入,不再有另一层确认 |

各阶段 SKILL.md 里的命令模板是单步形态;连续运行时必须同时传 `--by xinci-run --run-id <run_id>`。活动会话存在时 registrar 拒绝任何单步写入,漏传或伪造阶段名不能静默绕过授权边界。

### 会话与轮次收尾

- 连续模式下 registrar 把 `run_id` 与活动 `round` 一起写入每条 history;启动前用 `list` 获取 active run_id。
- session 每次载入都校验字段白名单、run_id/文件名、状态组合、轮次上下界、时间顺序与当前轮预检;手改出矛盾状态会立即停止授权。
- 窗口赌注确认(`confirm-window-bet`)只写进 session、不再改写;出闸时 registrar 在同一次账本原子写里把出闸 history 条目带上 `window_bet_confirmation: {confirmed_at, run_id}`。history 里已有引用即视为已消费,同一确认不能用第二次;账本写失败时什么都没发生,重试即可。
- 每轮必须由 `record-round` 收尾:它按轮号自动归集候选,并反查 `funnel.queued` 是否确有同轮新注册、带 gates+expiry、尚未深审的排队候选,然后原子追加 manifest、推进 session。中断时用相同 `record-round` 参数重试可幂等完成。
- `finish` 对零轮运行自动建空清单;其余情况要求恰好一份相同 run_id 的 manifest 并执行完整共享校验。

### schema v3：轮型、质量回路与派生调度

- 新会话使用 schema v3;历史 v1/v2 只读兼容,不补写、不迁移。每轮必须有 `round_type`。
- 每 10 个发现轮后,下一次发现前必须完成带证据的假阴性校准轮。完成态必须满足 G6=10、G7=10、G5=5、G1=5、G3=5 共 35 条分层样本;不足写 blocked,且 `untested_gates` 必须等于样本零覆盖的门。
- 运行清单的 `trigger_funnel` 与终止快照由控制器生成,禁止手填。
- 候选的 `first_observed_at`、`last_checked_at` 与首次进入 tracking 的 history 时间只记录事实。`tracking_schedule.py` 以首次进入 tracking 的时间派生第 3/7/14 天只读提醒(无历史字段的旧记录才回退 first_observed_at)。
  提醒不产生 registrar 写入、不自动改变状态,也不构成一次复查。
- `pattern` 的人类名称经 `pattern-aliases.json` 规范化并生成稳定 `pattern_id`。历史行不改写;统计时按 ID 合并别名,显示时仍保留规范中文名。

### CLI 入口

转移需要哪些字段以本节上方的证据表和 registrar 校验为准；各阶段的常用命令只保留在对应 SKILL.md。查询完整参数时运行：

```bash
python3 xinci-workflow/xinci-core/scripts/registrar.py --help
python3 xinci-workflow/xinci-core/scripts/registrar.py register --help  # 其他子命令同理
```

不要从历史校准稿复制旧命令，也不要因 `--help` 中某参数是可选就忽略证据表对特定转移的硬要求。
