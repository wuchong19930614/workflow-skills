# 生命周期契约

候选从捕获到建站决策的唯一状态机。状态只存在于 `数据/新词工作流/账本/候选账本.json`,只能由 `scripts/registrar.py` 写入。skill 提议转移,用户确认,registrar 执行——三者永不合并。

## 状态机

```
(新候选)
   │ xinci-scan 捕获
   ▼
captured ──G0–G5 全过──→ screened ──登记 expiry──→ tracking ──形成达标──→ formation_confirmed
  ↑ 也是扫描漏斗的排队位:本轮没走完的存活候选停在这里(gates 记已得结论、expiry 必填),
    下轮按 gates 补跑缺的门(缺 G1 先补 G1)再进深审;窗口过了走 captured→expired。
    还兼豁免候选的挂起位:深审判出 G3=veto_window_bet 而转移尚未被确认时,
    候选带着该结论停在 captured(连续运行下必然如此,见下「连续运行模式」)
   │                        │                        │    │                      │
   │任一闸门否决             │窗口以天计               │    │expiry 过,用户确认      │ xinci-qualify
   ▼                        │(快道)                  │    ▼                      ▼
rejected ←──快道 no-go──────┤                        │  expired          qualified / disqualified
                            ▼                        │                          │
                     xinci-decide 快速模式            │复查中 G1 翻转             │ xinci-decide
                            │                        │或竞品占位                 ▼
                            ▼                        ▼              ┌───────┬────────┬──────┐
                     fast_grab_ready              rejected          ▼       ▼        ▼      ▼
                            │                                 build_ready pilot_ready hold no_site
                            │用户建站/窗口过                        │        │
                            ▼                                      └───┬────┘
                     built / expired                                   │用户建站
                                                                       ▼
                                                                     built
```

补充转移:

- `rejected` 有**三个**来源态,图中都已画出,别只记住 captured 那一条:`captured`(任一闸门否决,**含 G2/G3 深审判否**——那是实际最常走的一条)、`screened`(快道读完证据判定这个赌注不值)、`tracking`(复查中 G0/G1 翻转或竞品占位到 G3 否决线)。
- 任何非终态候选可由用户转 `withdrawn`(主动撤回)或 `superseded`(被更好措辞的候选取代,`superseded_by` 指向新候选)。
- `hold` 可由用户送回重审,但**不回 formation_confirmed**(状态机没有这条边,hold 本身已带着 G6–G8 全 pass 与分数):
  送 xinci-qualify 重审即重新核对认定结论,出口只有 `hold → disqualified`(补审推翻了某道认定门);
  送 xinci-decide 重审即重出决策,出口是 `hold → build_ready / pilot_ready / no_site`。
  两个 skill 的输入核对都要接受 hold,不要按「只收 formation_confirmed / 只收 qualified」把它挡在门外。
- 排队中的 `captured` 候选,expiry 过了而始终排不到深审,可由用户确认后转 `expired`——它没有失败的闸门,不该被硬塞进 `rejected`。
- `built` 的快道候选,词若被证明耐久,可由用户发起转回 `tracking`,走完整认定升级成正经全站。

终态:`rejected` / `expired` / `superseded` / `withdrawn` / `built`,以及决策终局 `disqualified` / `no_site`(后两者除 superseded 外无出边)。

`built` 是终态集成员(账本上不可 `checked`、不可 `amend`),但不是死端:除 superseded 外,它保留 `built → tracking` 一条升级出边(见上「补充转移」)。
它是**唯一保留升级出边的终态**——`disqualified` / `no_site` 也有出边,但只有 `superseded` 一条,那是被更好的措辞取代,不是这个候选自己往前走。

## 每转移的证据要求

registrar 逐项校验,缺证据即拒绝;完整表与 `scripts/registrar.py` 实现一致:

| 转移 | 必须提供 |
| --- | --- |
| register(→captured) | slug、term(精确措辞,禁转述)、source.url、task、≥1 个证据文件;可选 gates(扫描漏斗中本轮没走完深审的存活候选带上已得闸门结论排队,下轮按 gates 补跑缺的门);**带 gates 时 expiry 必填**——排队位每轮进多出少,没有 expiry 就没有过期出口,方向会无声腐烂 |
| captured→screened | 闸门 G0–G5 全 pass;**G3 为 pass 或 `veto_window_bet`**(后者是临时空位降级出口,判据见闸门契约 G3,额外要求 window_estimate=days + reason + by≠xinci-run);window_estimate ∈ {days, weeks, months};≥1 证据 |
| captured/screened/tracking→rejected | reason(失败闸门 + 现场证据要点;快道读完证据判定不值得赌时,写不成立的那条判据)。**只有这三个来源态有 rejected 出边**(registrar 的 LEGAL 如此):formation_confirmed / qualified / hold 的 no-go 出口是 disqualified / no_site,不是 rejected。注:**扫描期的 G1 否决不走这条边**——它只追加一行淘汰方向索引,不注册进账本(见下「证据与命名约定」的留痕分界)。本边用于已注册候选的否决,四种情形:①**扫描期 G2/G3 深审否决**(最常走的一种,来源态 `captured`,深审结论先 register 再走本边);②复查中 G0/G1 翻转(`tracking`);③复查中竞品占位到 G3 否决线(`tracking`);④快道读完证据判定不值得赌(`screened`) |
| captured→expired | reason(排队 expiry 已过经用户确认;它没有失败闸门,不走 rejected) |
| screened→tracking | expiry(YYYY-MM-DD)+ ≥1 条失效条件 + ≥1 证据;**G3 不得为 `veto_window_bet`**(豁免候选只能走快道或 rejected,进追踪等于绕过 G3) |
| screened→fast_grab_ready | **仅限 window_estimate=days 的候选**;decision_ref(md 存在且同名 html 同批存在)+ expiry;play 固定 fast_grab;G3=`veto_window_bet` 的候选唯一的 go 出口 |
| fast_grab_ready→expired | reason(expiry 已过经用户确认,或窗口关闭:通用工具已收录该对象、赌注前提消失)。快道赌注没赌成就走这条边,不是 rejected——它没有失败的闸门 |
| tracking→formation_confirmed | 累计 ≥2 个 `-track` 观察,且最早与最新观察 observed_at 相隔 ≥7 天(形成期以周计,单次运行凑不出);本次 G1=pass;≥1 证据 |
| tracking→expired | reason(expiry 已过经用户确认 / 失效条件命中) |
| formation_confirmed→qualified | 整数 score ≥80 + G6/G7/G8 全 pass + ≥1 证据 |
| formation_confirmed→disqualified;hold→disqualified | reason(决定性缺口:哪一项、差多少) |
| qualified/hold→build_ready / pilot_ready | decision_ref md+html 双文件存在;play ∈ {single_domain, cluster_expansion} |
| qualified→hold / no_site;hold→no_site | reason;**不得**携带 decision_ref(no-go 不出决策书)。hold→hold 不是合法转移 |
| fast_grab_ready/build_ready/pilot_ready→built | registrar 不作额外校验(go 决策态该有的 decision_ref、分数、play 在进入该状态时已校验过)。**谁来登记**:建站是用户的人工动作,决策书交付后各阶段 skill 已经停了;用户建完站告知,由用户或任一 skill 代为执行这一条 `transition --to built --by <执行者>`。建议带 reason 记一句站点落地情况(registrar 不强制,但 built 之后账本上不可 `checked`、不可 `amend`,不写就没地方补) |
| built→tracking | reason(升级理由)+ 新 expiry;**若原 G3=`veto_window_bet`,本次须带 G3=pass**(重跑 G3;快道豁免不可继承) |
| *→withdrawn | reason |
| *→superseded | superseded_by(账本中已存在的其他 slug);disqualified/no_site 的唯一出边 |
| checked(非转移) | ≥1 证据;更新 last_checked_at、追加证据、写一条 from==to 的 history 条目(记 by 与本次观察),不改状态 |
| amend(非转移) | 观察性字段修订,限 expiry 续期、追加 aliases/invalidation;reason 必填并入 history;终态不可修订。经用户确认后调用 |

证据文件除存在性外,registrar 还校验内容齐备性:必须是合法 JSON,含 slug(与候选一致)、observed_at、stage(与文件名 `-<阶段>.json` 一致)、非空 points;路径必须是数据区内相对路径(禁绝对路径与 `..`)。

## 连续运行模式(xinci-run)

用户显式启动 xinci-run 后,工作流进入连续运行,直至命中终止契约。此模式是**每次启动的选择**,不是默认;四个阶段 skill(xinci-scan / track / qualify / decide)单独调用时仍是提议-确认(xinci-status 零写入,没有转移可确认)。

- **标准授权**:启动命令即构成对本次运行内全部 registrar 转移的授权,无需逐条确认;xinci-run 派出的子代理在同一授权范围内执行。闸门、评分线、证据要求**原样适用,不因连续模式软化**。
  **授权边界的分界线是「走既定路径」与「改变闸门结论」**:快道跳过 G6–G8 是契约内的既定减配路径(跳过项在决策书里逐条明码标价,风险确认由用户读决策书完成),在授权内;而 `G3=veto_window_bet` 是把一条已经判否的闸门结论软化掉,不在授权内——registrar 拒收 `by=xinci-run`,必须用户单步确认。
  **被拒后候选放在哪**:留在 `captured`,gates 里带着 `G3=veto_window_bet`、带 expiry,观察文件记明豁免依据(数到的免费实现清单 + 收录时差实测)。这是它的合法挂起位,`validate_ledger` 认这个状态。**不许替代性处置**:转 `rejected` 是错的(它没有失败的闸门,而且下次用户确认后本可以走快道),转 `screened` 是绕过拒收。运行清单 notes 记一句"有候选待用户单步确认豁免",运行照常继续——它不是 blocker。
- **预算(有默认值)**:用户启动时可附 `max_rounds=N` / `max_hours=H`;**未指定时默认 `max_rounds=6`**。命中即走**正常收尾 D**(处理同收尾 C:写运行清单、如实报告推进到哪,下次启动从账本现状继续)。预算是用户主权,不属于禁止的停止理由;不因缺参数暂停,按默认值开跑。
  设默认值的理由:下条列的"正常终止"第 2 项(额度耗尽)在单次运行内几乎不可达——扫描期禁用 Semrush、形成期只允许轻探针、7 天跨度闸使单次运行**做不出新的** formation_confirmed。(账本已有 formation_confirmed/qualified 存量时,qualify/decide 确实会动用 Semrush;但那是每候选个位数的 decision-changing 查询,离烧穿额度仍差得远。)没有默认预算时"不限"实际等于跑到会话资源耗尽(收尾 C),那是操作边界而非任务边界;跨天累积应由定时任务按天驱动,而不是靠单次运行硬撑。
- **正常终止,仅两条**:
  1. **终止 A**:registrar 记录任一 go 决策(fast_grab_ready / pilot_ready / build_ready)——本次运行拿到了可交付的结论,停,交付决策书。**两类 go 的分量不同,不许混说**:build_ready / pilot_ready 过了 G6–G8 与 80 分线,是"值得建站";fast_grab_ready 是"一份标好价的窗口赌注",按闸门契约 G8 的减配说明,它不等于被验证的生意;
  2. **终止 B**:Semrush 网页版额度耗尽——必须在网页界面**实际观察到**额度耗尽提示,并把提示要点记入运行清单;假设、推断、报错猜测都不构成额度耗尽。
- **正常收尾 C——会话资源耗尽**:执行者的上下文/会话资源接近极限时,完成当前动作、写运行清单、如实报告"会话资源耗尽,任务未完成、额度未耗尽"后停。这是操作边界,不是任务终点:不得伪装成终止 A 或 B;已完成的转移与清单保持有效,下次启动从账本现状继续。
- **正常收尾 D——预算命中**:上面「预算」一条给的轮次/时长用完(含未指定时的默认值)。处理同收尾 C:完成当前动作、写运行清单、如实报告推进到哪与预算命中,下次启动从账本现状继续。
- **异常中止**:认证、CAPTCHA、支付、浏览器封锁等 blocker 使所有可行工作停摆时,停止并如实报告 blocker。blocker 不是额度耗尽,不是完成,不得伪装成任何正常终止。
- **禁止的停止理由**:扫描空轮、候选池为空、"看起来找不到"、运行时间长、轮次多。空轮换来源、换角度(信号面↔变化面)继续。(收尾 C/D 分属操作边界与用户主权,不在此列。)
- **screen_unsatisfiable**:拒绝原因收敛到少数结构性模式时,写一份假设报告入运行清单并继续运行——它是发现,不是终止理由。
- **反空烧**:Semrush 纪律仍为 decision-changing only。额度是终止条件,不是消耗目标;为触发终止而空烧额度是禁止的。
- **去重**:**每轮**都要去重,时点是本轮提取出方向之后、花任何筛选成本之前——用 `screen_index.py check` 批量查(一次覆盖淘汰索引与账本)。它算开局纪律(先看见过什么,再花成本),但执行位置在提取之后,因为待查方向要先有(同 xinci-scan 第 0 层「执行时点」);已弃候选与已记录的淘汰方向不重复评估。索引本身不进上下文。命中的方向**不计入 funnel 的 `extracted`**——它们上一次已经有归宿了,再要求一次归宿,加总等式必然算不平。
- **如实说明**:形成期以周计,单次运行无法压缩。运行把存量候选推进到当下证据允许的最远处(tracking 复查、formation→qualify、qualified→decide),同时持续扫描新候选;单次运行内最可能先出现的 go 决策是快道(fast_grab_ready)。

## 时间字段:只记录,不调度

- 三个时间事实:`first_observed_at`(首见)、`last_checked_at`(上次复查)、`expiry`(失效日,附推理于证据)。
- **没有** next_check_at、默认复查间隔、调紧/放宽规则等任何调度机制。
- skill 被调用时只汇报时间事实("该候选 12 天未复查,expiry 还剩 5 天"),不据此自动做任何事。
- expiry 过期不自动转 expired:skill 提议,用户确认后 registrar 才执行。
- 复查哪些候选、何时复查、何时推进阶段,全部由用户决定。

## 证据与命名约定

- 观察文件:`证据/<slug>/<YYYY-MM-DD>-<阶段>.json`,阶段 ∈ {scan, track, qualify, decide};schema 见 `数据结构/observation.schema.json`。其中 `-decide` 是**可选**的:决策阶段的产出是决策书,只有为补缺口做了新审计时才落一份 `-decide` 观察,没有新观察就不写(数据极简)。
- 观察只描述看到了什么,不携带读起来像裁决的字段;裁决只在账本。
- **数据极简原则**:只写简单清晰、服务于决策的内容——不写仪式性字段、不写过程流水账、不为"显得完整"而填充。观察写要点,不写转录。
- 运行清单:`运行/<YYYY-MM-DD>-<skill>.json`,每次运行一个小 JSON(日期、skill、打开过的来源、**被拦截的来源**、触及的候选、计费调用数),不写过程日志;字段约定见 `数据结构/run-manifest.schema.json`,**字段白名单由 `scripts/validate_ledger.py` 强制**(清单不经 registrar 写入,漂移只能靠它捕获)。自 2026-08-19 起,`xinci-scan` 清单必须带顶层 `funnel`、`xinci-run` 清单的每一轮必须带 `rounds[].funnel`(该轮没扫描就把 `extracted` 与四个去向**五项全写 0**——只写四个去向会被 validate_ledger 判「funnel 缺字段 ['extracted']」;这同时也是「本轮只推进存量」的记录);阈值之前的历史清单豁免,不回填编造数字。消化存量 `captured` 所做的深审记 `funnel.carryover_audited`(可选字段,不参与加总等式)——它不属于本轮 `extracted`,记进 `deep_audited` 会把等式算破;但它是全流程最贵的动作,只还债不扫新的轮次五项全 0,没有这个字段那一轮就看不出花了什么。被拦来源如实记入 `sources_blocked`——覆盖面缺口是事实,不是可以省略的失败。同日再次启动同一 skill 时,文件名追加启动时刻:`运行/<YYYY-MM-DD>-<HHMM>-<skill>.json`,不覆盖已有清单。xinci-run 连续运行只写一份自己的清单(轮次在其中追加),期间执行的各阶段流程不再另写各阶段清单。
- **淘汰方向索引**:`数据/新词工作流/淘汰方向.jsonl`,每行一条 JSON(`date`/`term`/`gate`/`reason`,可选 `pattern`),由 `scripts/screen_index.py` 读写——**不要手工编辑,也不要整份读进上下文**(广度扫描下它按每天两三百条增长)。开局去重跑 `screen_index.py check`(同时查索引与账本),批量留痕跑 `screen_index.py append`。

**留痕分界**——分界线是「这一条的现场证据值不值得单独留档」。两种情况值得,其余都只配一行索引:

1. **它还有下一步**(深审存活、排队待审);
2. **它的结论来自 G2/G3 深审**——哪怕结论是出局。深审是全流程最贵的动作、每轮配额 ≤5,它数到的免费实现清单、结构阅读要点、footprint 观察都是**这一个方向独有的**证据,索引的一行 reason 装不下;而正因为每轮只有 ≤5 条,注册成本也不构成问题。

反过来说,只配一行索引的是**成本低到不值得留档、且数量大到留档会淹没账本**的那些:批量秒弃、G1 否决、已归并的陷阱类别命中——它们的死因是类别级的,单个方向没有独立留档价值。

具体分派:

- **只追加一行进本索引,不注册**:零成本秒弃(G0 / G4 / G6–G7 预筛 / 无任务)、**G1 否决**、陷阱类别命中(含当场跑 G3 验证判 `veto` 的;纯品牌名即陷阱类别二,归在这一项,不另列)。这些方向都已终结,永不复活。G1 否决走索引是 2026-08-19 定的:按漏斗目标量它每轮约 18 条,逐条写观察文件 + register + transition 是每轮 36 次脚本调用、每周 100+ 条 rejected 塞满账本,写入成本压过了本轮真正值钱的 5 次深审;而它需要留下的只有"这个方向见过、死在 G1",索引一行(`gate=G1`,reason 带首屏证据要点:是 featured snippet 还是原生组件把任务做完了)完整承载了这件事。
- **注册进账本**:①走到 G2/G3 深审**且存活**的候选(带闸门结论与 window_estimate);②超配额排队的存活方向(`captured` + gates + expiry);③**走到 G2/G3 深审但被否决的候选**——G2 结构阅读判否、或 G3 判 `veto`,同样先 register 再走 `captured→rejected`,reason 写清失败闸门与现场证据要点(数到的免费实现、结构阅读结论)。第三种是最常走的一条,别漏:陷阱类别三的三例(`significant change api` / `ppwr empty space ratio` / `app store creative assets`)正是这样留痕的,`screen_index.py check` 也靠账本这一侧才认得出它们。
- **陷阱类别的一个例外**:命中陷阱类别、当场跑 G3 验证**判 `veto`** 的方向留在索引一侧(判 `pass` 的按上一条注册进账本,回正常序列补 G1、G2;该模式已是正式类别,单个方向没有独立留档价值,这一次数到的免费实现清单按陷阱类别.md 的追加规则写进该类别节里——证据落在规则文档,不落在候选证据区);**但若这次 G3 判出的是 `veto_window_bet` 而不是 `veto`,它就有了 go 出口(快道),必须注册进账本**——按上一条走,索引不再记它。扫描与连续运行的开局去重用 `screen_index.py check` 一次覆盖索引与账本,不必翻历史运行清单,也不必把任何一方读进上下文。**归并纪律**:同一结构性模式在索引中第三次出现时,按陷阱类别.md 的追加规则把它归并成正式类别(附实际观察),并在索引补一条归并记录——**term 写模式名本身**,不是任何一个具体方向(写成具体方向会被 `append` 的 term 去重静默跳过,那条记录根本落不下去),`gate` 记 G5,`reason` 以 `[已归并]` 开头并指向类别号,`pattern` 填该模式名:
  `printf '%s\n' "厂商已占位的 B2B 强制任务|G5|[已归并] 见陷阱类别.md 类别三|厂商已占位的 B2B 强制任务" | python3 xinci-workflow/xinci-core/scripts/screen_index.py append --date <YYYY-MM-DD>`
  (`screen_index.py stats` 会在某 `pattern` 累计 ≥3 次时提示该归并了);此后命中该模式的方向由 G5 **按该类别自带的处置档**处理——标「直接筛除型」的零成本弃,标「验证型」的仍要跑 G3 验证(新类别默认验证型,见陷阱类别.md)。**归并省掉的是"第四次验证同一个死因",不是留痕**:秒弃照常追加一行索引(gate 记 G5),否则下轮 `screen_index.py check` 认不出它,同一方向每轮都要重新提取评估。索引不会因此线性膨胀——`screen_index.py append` 按归一化 term 跳过重复,每行始终是一个独立方向,而不是一次命中。

## registrar 用法

### `--by` 取值:按**运行模式**定,不按命令所在的文档定

`--by` 记的是"这次转移由谁、在什么授权下执行的",它是 history 里唯一能区分标准授权与逐条确认的字段,取值只有两种:

| 运行模式 | `--by` 取值 | 含义 |
| --- | --- | --- |
| 单步调用某个阶段 skill | 该 skill 名(`xinci-scan` / `xinci-track` / `xinci-qualify` / `xinci-decide`) | 用户逐条确认过这次转移 |
| xinci-run 连续运行(含它派出的子代理) | 一律 `xinci-run` | 标准授权、未经逐条确认 |

**各阶段 SKILL.md 里的命令模板一律写着自己的 skill 名,那是单步形态。连续运行时必须把 `--by` 改成 `xinci-run` 再执行——照抄模板是错的。** `register` 与 `checked` 的 `--by` 有默认值(分别是 `xinci-scan` / `xinci-track`),连续运行下**必须显式传 `--by xinci-run`**,漏传会静默落成单步的记录。

这不只是记账问题:`captured→screened` 携带 `G3=veto_window_bet` 时,registrar 唯一的拒收条件就是 `by == "xinci-run"`(闸门软化不在标准授权内)。连续运行下把 `--by` 写成 `xinci-scan`,这道拒收就形同虚设——**那正是「不许换个 `by` 硬推 screened」禁止的行为**,不因为它是从模板里抄来的而变得可以接受。

```bash
python3 xinci-workflow/xinci-core/scripts/registrar.py register \
  --slug <slug> --term "<精确措辞>" --source-url <URL> --task "<任务>" \
  --evidence "证据/<slug>/<日期>-scan.json" --by <skill名> \
  [--source-note "<现场摘要>"] [--aliases "别名1,别名2"] \
  [--gates G0=pass,G4=pass,G5=pass,G1=pass] [--expiry YYYY-MM-DD]
  # 排队位注册:带 --gates 就**必须**带 --expiry(registrar 强制),否则方向会在队列里无声腐烂

python3 xinci-workflow/xinci-core/scripts/registrar.py transition \
  --slug <slug> --to <状态> --by <skill名> [--gates G0=pass,G1=pass,...] \
  [--window-estimate <days|weeks|months>] [--expiry YYYY-MM-DD] \
  [--invalidation "条件1;条件2"] [--score N] [--decision-ref 决策书/<slug>.md] \
  [--play ...] [--reason "..."] [--evidence <路径>] [--superseded-by <slug>]
  # --window-estimate 是 captured→screened 的必填项;--superseded-by 是 *→superseded 的必填项
  # (两者上表都列为硬要求,别因为这里是方括号就当成可省)

python3 xinci-workflow/xinci-core/scripts/registrar.py checked \
  --slug <slug> --evidence "证据/<slug>/<日期>-track.json" --by <skill名>

python3 xinci-workflow/xinci-core/scripts/registrar.py amend \
  --slug <slug> --by <skill名> --reason "<用户确认的修订理由>" \
  [--expiry YYYY-MM-DD] [--add-alias <别名>] [--add-invalidation "条件1;条件2"]
```
