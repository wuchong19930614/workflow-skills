# 生命周期契约

候选从捕获到建站决策的唯一状态机。状态只存在于 `<数据区>/账本/候选账本.json`,只能由 `scripts/registrar.py` 写入。

> **数据区在哪(2026-08-24 起)**:`xinci-workflow` 仓库只放 skill 与契约,**执行产出不在本仓库内**——账本、证据、淘汰方向索引、去重裁决、运行清单、运行状态、决策书一律住在数据区。
> **本文与其他契约里的相对路径(`账本/`、`证据/`、`运行/`、`决策书/`、`淘汰方向.jsonl` 等)一律相对数据区,不是本仓库内的路径。**

### 开工第一步:数据区放哪,必须问过用户(强制,先于一切写操作)

**任何 skill 在第一次动数据之前,先跑这一条零成本检查:**

```bash
python3 xinci-workflow/xinci-core/scripts/report_status.py
```

- **正常返回看板** → 数据区已配置,照常干活,别再问。
- **退出码 2 并打印"数据区未配置"** → **停下来问用户,不要替他选路径。** 这不是故障,是设计:脚本刻意不猜。

问清之后按用户给的路径固定下来(它同时会创建目录结构与空账本,幂等):

```bash
python3 xinci-workflow/xinci-core/scripts/init_workspace.py --data-root <用户给的路径>
```

解析顺序:显式 `--data-root` > 环境变量 `XINCI_DATA_ROOT` > 仓库配置 `.xinci-data-root` > **拒绝执行**。

**为什么要有这一条**:2026-08-24 数据区迁出本仓库时,脚本里留了一条"回退到同级 `keywords-macdownds`"的默认值。后果是换一台机器或换一个用户第一次跑这套工作流,`init_workspace.py` 会在一个他从没同意过的位置直接建目录、建空账本,**而且不报错**——账本是这套流程唯一的事实来源,它落错地方等于整条流水线在错的地方留痕。默认值已删除,`.xinci-data-root` 不入库(入库会让别人一 clone 就继承你机器上的路径,等于绕过本条)。回归测试见 `scripts/tests/test_data_root.py`。

**单步模式**下 skill 提议转移、用户逐条确认、registrar 执行;**xinci-run 连续模式**把确认时点前移到启动命令,由标准授权覆盖既定路径,但 `G3=veto_window_bet` 的 `captured→screened` 风险接受仍须用户单步确认。两种模式都不允许 skill 越过对应授权自行改变状态。

## 状态机

```
(新候选)
   │ xinci-scan 捕获
   ▼
captured ──有效初筛结论满足出闸要求──→ screened ──登记 expiry──→ tracking ──形成达标──→ formation_confirmed
  ↑ 也是扫描漏斗的排队位:本轮没走完的存活候选停在这里(gates 记已得结论、expiry 必填),
    下轮按 gates 补跑缺的门(缺 G1 先补 G1)再进深审;窗口过了走 captured→expired。
    还兼窗口赌注候选的挂起位:深审判出 G3=veto_window_bet 而转移尚未被确认时,
    候选带着该结论停在 captured(连续运行下必然如此,见下「连续运行模式」)
   │                        │                        │    │                      │
   │任一闸门否决             │窗口以天计               │    │expiry 过,用户确认      │ xinci-qualify
   ▼                        │(快道)                  │    ▼                      ▼
rejected ←──快道 no-go──────┤                        │  expired          qualified / disqualified
                            ▼                        │                          │
                     xinci-decide 快速模式            │复查中闸门翻转             │ xinci-decide
                            │                        │或竞品占位                 ▼
                            ▼                        ▼              ┌───────┬────────┬──────┐
                     fast_grab_ready              rejected          ▼       ▼        ▼      ▼
                            │                                 build_ready pilot_ready hold no_site
                            │用户建站/窗口过                        │        │
                            ▼                                      └───┬────┘
                     built / expired                                   │用户建站
                                                                       ▼
                                                                     built
```

图中的“有效初筛结论满足出闸要求”精确定义为:G0/G1/G2/G4/G5=`pass`,G3=`pass` 或状态机兼容的 `veto_window_bet`;后者不是“G0–G5 全过”,只可按窗口赌注专用出口推进。

补充转移:

- `rejected` 有**三个**来源态,图中都已画出,别只记住 captured 那一条:`captured`(任一有效闸门否决,**含 G2 深审判否,以及占位否决按盈利线确实生效时的 G3 判否**)、`screened`(快道读完证据判定这个赌注不值)、`tracking`(复查中 G0/G1 翻转、占位否决生效时竞品到达 G3 否决线,或新类别归并后发现它正好命中该陷阱类别)。三个来源态另共享一种情形:**G6 没有任何适用盈利线能通过**(下表 rejected 边第⑦种；new 道是订阅 veto + 广告 `N/A`,mature 道才是两线 veto)。订阅线暂定或正式可行时,占位事实只进入竞争记录,G3 有效门结论写 pass,不得走 rejected。
- 任何非终态候选可由用户转 `withdrawn`(主动撤回)或 `superseded`(被更好措辞的候选取代,`superseded_by` 指向新候选)。
- `hold` 可由用户送回重审,但**不回 formation_confirmed**(状态机没有这条边,hold 本身已带着 G6–G8 全 pass 与分数):
  送 xinci-qualify 重审即重新核对认定结论,出口只有 `hold → disqualified`(补审推翻了某道认定门);
  送 xinci-decide 重审即重出决策,出口是 `hold → build_ready / pilot_ready / no_site`。
  两个 skill 的输入核对都要接受 hold,不要按「只收 formation_confirmed / 只收 qualified」把它挡在门外。
- `expired` 有**四个**来源态,图中画出了 `tracking` 与 `fast_grab_ready` 两条:`captured`(排队中 expiry 过了而始终排不到深审)、`screened`(已出闸但窗口自己过了——既没排上快道,也没转进追踪)、`tracking`(expiry 过或失效条件命中)、`fast_grab_ready`(赌注没赌成,见下表)。**四条都是同一条理由:它们没有失败的闸门,不该被硬塞进 `rejected`**。由用户确认后转;连续运行模式下由标准授权覆盖。
  **四条边各自的提议人**(没有提议人的边等于不存在):`tracking` 归 xinci-track 复查后提议;排队中的 `captured` 归 xinci-scan 开局接队时提议(**带 `G3=veto_window_bet` 挂起等确认的候选同样是排队中的 `captured`,expiry 过了走同一条边——挂起不免疫过期**);`screened` 与 `fast_grab_ready` 归 **xinci-decide**——前者是它快道模式的输入、后者是它的产出,由用户按 xinci-status 报出的到期清单把候选送给它。连续运行模式下四条一律归 xinci-run 运行循环步骤 1,标准授权直接转,没有提议环节。
- `built` 的快道候选,词若被证明耐久,可由用户发起转回 `tracking`,走完整认定升级成正经全站。

内部“终态集”实际由两类组成:归档态 `rejected` / `expired` / `superseded` / `withdrawn` / `built`,以及决策终局 `disqualified` / `no_site`。这里的“终态集”是代码校验分组,不等同于“全部再无出边”:后两者只可转 superseded,`built` 另保留下面的一条人工升级出边。

`built` 是终态集成员(账本上不可 `checked`、不可 `amend`),但不是死端:它保留 `built → tracking` 一条升级出边(见上「补充转移」)。**这也是它唯一的出边——`built → superseded` 不可用**:superseded 的来源只有非终态候选与两个决策终局(registrar 的 `SUPERSEDABLE_FINAL` 只含 disqualified / no_site),其余终态一律无出边。
它是**唯一保留升级出边的终态**——`disqualified` / `no_site` 也有出边,但只有 `superseded` 一条,那是被更好的措辞取代,不是这个候选自己往前走。

**受控重开不是普通状态边**:`rejected` 若决定性否决只来自会腐烂的 G1/G2/G3 SERP 事实,registrar 写入 `recheck_after`。到期只进入 xinci-status 的复核清单,不自动改变状态;只有取得**晚于最近拒绝时间**的新现场观察、且观察中的 gates 把当时每一道 veto 都明确翻转为 `pass`,才能用 `registrar.py reopen` 回到 captured,清空旧窗口闸门并重新走全套初筛。只换一个新文件名、复用旧截图或只翻转部分 veto 都拒收。G0/G4/G5 的结构性否决不可重开。

## 每转移的证据要求

registrar 逐项校验,缺证据即拒绝;完整表与 `scripts/registrar.py` 实现一致:

| 转移 | 必须提供 |
| --- | --- |
| register(→captured) | slug、term(精确措辞,禁转述)、source.url、task、≥1 个证据文件;可选 gates(扫描漏斗中本轮没走完深审的存活候选带上已得闸门结论排队,下轮按 gates 补跑缺的门);**带 gates 时 expiry 必填**——排队位每轮进多出少,没有 expiry 就没有过期出口,方向会无声腐烂 |
| captured→screened | G0/G1/G2/G4/G5=`pass`,G3 为 `pass` 或 `veto_window_bet`;window_estimate、窗口失效日 expiry、≥1 证据。expiry 现由 registrar 强制,排队位旧 expiry 必须在出闸时覆盖。连续模式的窗口赌注还要求活动 run_id 中存在一次未消费的用户确认记录 |
| captured/screened/tracking→rejected | reason(失败闸门 + 现场证据要点;快道读完证据判定不值得赌时,写不成立的那条判据)。**只有这三个来源态有 rejected 出边**(registrar 的 LEGAL 如此):formation_confirmed / qualified / hold 的 no-go 出口是 disqualified / no_site,不是 rejected。注:**未注册方向的 G1 否决不走这条边**——它只追加一行淘汰方向索引,不注册进账本(见下「证据与命名约定」的留痕分界)。本边用于已注册候选的否决,八种情形（第⑧种见本表后“G6 结构性入口否决出口”）:①**扫描期 G2 深审否决,或占位否决按盈利线确实生效时的 G3 深审否决**(来源态 `captured`,深审结论先 register 再走本边;订阅线暂定可行时不属于本项);②复查中 G0/G1 翻转(`tracking`);③复查中占位否决生效且竞品到达 G3 否决线(`tracking`);④快道读完证据判定不值得赌(`screened`);⑤**已注册的排队候选补跑 G1 被否**(来源态 `captured`,含陷阱验证存活的与超配额排队的)——它已经在账本里,索引管不着它,必须有一条账本上的出边,否则只能烂在 `captured` 等 expiry 把它当成无失败闸门的候选悄悄收走;⑥**新类别归并后发现某个 tracking 候选正好命中该陷阱类别**(来源态 `tracking`)——它是重新认识,不是例行复查项,由**做归并的一方**当场提议(单步是 xinci-scan、连续运行是 xinci-run),不是 xinci-track 的活:后者按闸门契约时间光谱表下「形成期为什么不是 G1–G5 全复查」根本不例行复查 G5;若类别死因只是占位,仍须先按盈利线判断否决是否生效;⑦**窗口期暂定 G6 没有任何适用盈利线能通过**(来源态 `captured` / `screened` / `tracking`)——`lane=new` 是 subscription=`tentative_veto` + advertising=`N/A`；`lane=mature` 是两线均 `tentative_veto`。这条边提交本次 scan/track observation,由其中完整的 `g6_tentative_lines` 支撑,**不得把暂定结论写成正式 `gates.G6=veto`**；reason 逐线写明 `tentative_veto` / `N/A` 及依据。registrar 对 captured/tracking 接受“至少一道正式 gate=veto”或“本次证据证明无适用暂定盈利线”二者之一。提议人:做该次预检或重算的一方(new 单步由 xinci-scan/xinci-track,mature 前半程由 xinci-mature,连续运行只处理 new 前半程并使用 xinci-run) |
| captured→expired;screened→expired | `expiry_trigger=date` + reason(expiry 已过经用户确认——captured 是排队没排上,screened 是出闸后窗口自己过了;两者都没有失败闸门,不走 rejected)。registrar 会实测账本 expiry ≤ 当前日期,未来日期拒收 |
| screened→tracking | expiry(YYYY-MM-DD)+ ≥1 条失效条件 + ≥1 证据;**G3 不得为 `veto_window_bet`**(窗口赌注候选只能走快道或 rejected,进追踪等于绕过 G3) |
| screened→fast_grab_ready | **仅限 window_estimate=days 的候选**;decision_ref(md 存在且同名 html 同批存在)+ expiry;play 固定 fast_grab;G3=`veto_window_bet` 的候选唯一的 go 出口 |
| fast_grab_ready→expired | `expiry_trigger=date|window_closed` + reason:date 要求账本 expiry 已到；window_closed 表示通用工具已收录该对象、赌注前提消失。快道赌注没赌成就走这条边,不是 rejected——它没有失败的闸门 |
| tracking→formation_confirmed | 累计 ≥2 个 `-track` 观察,且最早与最新观察 observed_at 相隔 ≥7 天(形成期以周计,单次运行凑不出);本次 G1=pass；本次 track 观察明确 `naming_status=stabilized`，且 `formation_signals` 至少一项；≥1 证据 |
| tracking→expired | `expiry_trigger=date|invalidation` + reason:date 要求账本 expiry 已到；invalidation 要求候选已有失效条件并写明本次命中的事实 |
| formation_confirmed→qualified | 整数 score ≥80 + `income_score` 为 1–20 + `g6_passed_lines` 至少一项(`lane=new` 不得含 advertising)+ G6/G7/G8 全 pass + ≥1 证据 |
| formation_confirmed→disqualified;hold→disqualified | reason(决定性缺口:哪一项、差多少)+本次 `-qualify` observation；不得只凭文字理由推翻认定 |
| qualified/hold→build_ready / pilot_ready | decision_ref md+html 双文件存在且 html 内源 SHA-256 与当前 md 一致;play ∈ {single_domain, cluster_expansion} |
| qualified→hold / no_site;hold→no_site | reason;**不得**携带 decision_ref(no-go 不出决策书)。hold→hold 不是合法转移 |
| fast_grab_ready/build_ready/pilot_ready→built | registrar 不作额外校验(go 决策态该有的 decision_ref、分数、play 在进入该状态时已校验过)。**谁来登记**:建站是用户的人工动作,决策书交付后各阶段 skill 已经停了;用户建完站告知,由用户或任一 skill 代为执行这一条 `transition --to built --by <执行者>`。建议带 reason 记一句站点落地情况(registrar 不强制,但 built 之后账本上不可 `checked`、不可 `amend`,不写就没地方补) |
| built→tracking | reason(升级理由)+ 新 expiry;**若原 G3=`veto_window_bet`,本次须带 G3=pass**(重跑 G3;快道降级结论不可继承) |
| 非终态→withdrawn | reason |
| 非终态/disqualified/no_site→superseded | superseded_by(账本中已存在的其他 slug);disqualified/no_site 的唯一出边;rejected/expired/superseded/withdrawn/built 不可走此边 |
| checked(非转移) | ≥1 证据;更新 last_checked_at、追加证据、写一条 from==to 的 history 条目(记 by 与本次观察),不改状态。**同一自然日不重复复查**:registrar 比对本次与已登记的 `-track` 观察的 `observed_at` 日期,撞车即拒——SERP 在几小时内不会变,再跑一遍是空烧。边界按**观察日**划、不按 run 划,所以同一天的两次运行同样受限;一天之内补录两份不同观察日的 `-track` 则不受影响。确需当日重测(典型是上次复查时浏览器处于登录态、G1 结论不成立)时传 `--same-day-reason`,理由写进 history |
| amend(非转移) | 观察性字段修订,限 expiry 续期、追加 aliases/invalidation,以及 **`captured` 候选补记闸门结论**(`--gates`)。补记 gates 是排队位/挂起位在账本上**唯一的** gates 写入口——`captured→captured` 不是转移,transition 写不了它,而上轮已注册的排队候选本轮才跑出的结论(典型是还债深审判出 `G3=veto_window_bet`)不补记就只剩在观察文件里,账本上看不见这个挂起。限制三条:**仅限 `captured`**、**补记后必须有 expiry**、**带 gates 必须同时用 `--evidence` 提交本次 observation 且逐门一致**。reason 必填并入 history;终态不可修订。经用户确认后调用 |

证据文件除存在性外,registrar 还校验内容齐备性:必须是合法 JSON,含 slug(与候选一致)、observed_at、stage(与文件名 `-<阶段>.json` 一致)、非空 points;路径必须是数据区内相对路径(禁绝对路径与 `..`)。

## 连续运行模式(xinci-run)

用户显式启动 xinci-run 后,工作流进入连续运行,直至命中终止契约。此模式是**每次启动的选择**,不是默认;四个阶段 skill(xinci-scan / track / qualify / decide)单独调用时仍是提议-确认(xinci-status 零写入,没有转移可确认)。

**每轮 admission 策略是硬契约**：恢复/创建 run 后，由本轮实际执行者以稳定 `executor_id` 记录 `browser_preflight.py`，策略与 `begin-round` 使用同一 ID；预检同时绑定目标轮次。父任务、其他子代理和上一轮的预检都不能借用。只有 `full` 可新增正式候选；浏览器不满足可控、桌面、美区、未登录四项时为 `trigger_only`；`lane=new,state=captured` 积压 >20 或连续三轮无真实决策迁移且队列增长时为 `debt_only`；trigger pending 达 200 且仍无 G1 环境时为 `paused`。registrar 的正式 CLI 在 register 前复核 `formal_admission`。`queued` 与初次 `from=null→captured` 都不是决策推进；推进只认既有候选 `from` 非空且 `to != from` 的 history 迁移。

**触发池与候选账本分层**：法规、平台或技术变化的官方标题先写 `触发池.jsonl`，不得直接作为候选 term。trigger 只有在出现用户实际会搜索的 task query、至少一个独立搜索语言证据 URL，并补齐 payer、重复对象单元、自助交付路径、基础情景来源后才可 approve。approve 仅允许进入 G0。xinci-run 注册变化面候选必须带 `origin=trigger + trigger_ref`，registrar 核对 trigger 已批准且 candidate term 与批准 query 一致；社区/信号面则显式记 `origin=signal`。单一 source family 不得连续主导超过两轮或占本 run 新 trigger 的 40%。

**lane 边界**:`lane=new` 可由 xinci-run 推进全生命周期；`lane=mature` 在 `formation_confirmed` 前由 **xinci-mature 单步承接**(2026-08-29 起;此前无 skill 承接,只能手工照指南走),活动 run 不得操作其 captured/screened/tracking,也不把它们计入 new 道积压。mature 合法进入 `formation_confirmed` 后,xinci-run 才可调用 xinci-qualify / xinci-decide 接续。前半程若已把 mature 合法送到 `screened` 且窗口为 days,用户仍可**显式单步调用** xinci-decide 做快道决策或到期处置；这是决策 skill 的人工入口,不授权 xinci-run 自动推进 mature 前半程。**xinci-mature 本身也不在 xinci-run 的标准授权内**——它是单步形态,每次转移都要用户确认,理由是这条线累计 0/4、方法尚未验证,未验证的方法不该自动跑。

- **标准授权**:启动命令即构成对本次运行内**既定路径上的 registrar 转移**的授权,无需逐条确认;xinci-run 派出的子代理在同一授权范围内执行。唯一的转移例外是 `G3=veto_window_bet` 的 `captured→screened`,它要求用户单步接受窗口赌注风险。闸门、评分线、证据要求**原样适用,不因连续模式降低**。
  **授权边界的分界线是「执行已接受的既定路径」与「接受额外窗口赌注风险」**:G3=`pass` 的快道跳过 G6–G8 是契约内的既定减配路径,在标准授权内；决策书必须逐条做**风险披露与授权状态说明**,不得把交付后的阅读写成事前“用户已确认”。`G3=veto_window_bet` 则是 G3 的独立降级结论——不是 `pass`,也不是普通 `veto`——其出闸意味着用户接受“位置可能只空几天”的额外风险,不在标准授权内。registrar 因此要求本次活动 run_id 中存在该候选的一次性确认,没有确认即拒收 `by=xinci-run` 的出闸。
  **被拒后候选放在哪**:留在 `captured`,gates 里带着 `G3=veto_window_bet`、带 expiry,观察文件记明降级依据(数到的免费实现清单 + 收录时差实测)。这是它的合法挂起位,`validate_ledger` 认这个状态。**不许替代性处置**:转 `rejected` 是错的(它仍有待确认的快道出口),转 `screened` 是绕过拒收。运行清单 notes 记一句"有候选待用户单步确认窗口赌注",运行照常继续——它不是 blocker。
- **预算(轮次上限始终存在)**:用户启动时可附 `max_rounds=N` 和/或 `max_hours=H`;**未显式给 `max_rounds` 时仍默认 6,即使只给了 `max_hours`**。两项同时存在时谁先命中就走**正常收尾 D**;若希望主要按时长运行,须同时给足够大的 `max_rounds`,没有“轮次无限”这一档。收尾处理同 C:写运行清单、如实报告推进到哪,下次启动从账本现状继续。预算是用户主权,不属于禁止的停止理由;不因缺参数暂停,按默认值开跑。
  设默认值的理由:下条列的"正常终止"第 2 项(额度耗尽)在单次运行内几乎不可达——扫描期禁用 Semrush、形成期只允许轻探针、7 天跨度闸使单次运行**做不出新的** formation_confirmed。(账本已有 formation_confirmed/qualified 存量时,qualify/decide 确实会动用 Semrush;但那是每候选个位数的 decision-changing 查询,离烧穿额度仍差得远。)没有默认预算时"不限"实际等于跑到会话资源耗尽(收尾 C),那是操作边界而非任务边界;跨天累积应由定时任务按天驱动,而不是靠单次运行硬撑。
- **正常终止,仅两条**:
  1. **终止 A**:registrar 记录任一 go 决策(fast_grab_ready / pilot_ready / build_ready)——本次运行拿到了可交付的结论,停,交付决策书。**两类 go 的分量不同,不许混说**:build_ready / pilot_ready 过了 G6–G8 与 80 分线,是"值得建站";fast_grab_ready 是"一份标好价的窗口赌注",按闸门契约 G8 的减配说明,它不等于被验证的生意;
  2. **终止 B**:Semrush 网页版额度耗尽——必须在网页界面**实际观察到**额度耗尽提示，保存截图或其他可复核文件，并在 `finish` 传 `--evidence-ref <数据区相对路径>`；只写提示要点、假设、推断或报错猜测都不构成额度耗尽。
- **正常收尾 C——会话资源耗尽**:执行者的上下文/会话资源接近极限时,完成当前动作、写运行清单、如实报告"会话资源耗尽,任务未完成、额度未耗尽"后停。这是操作边界,不是任务终点:不得伪装成终止 A 或 B;已完成的转移与清单保持有效,下次启动从账本现状继续。
- **正常收尾 D——预算命中**:上面「预算」一条中的轮次上限或时长上限先用完(轮次上限始终存在,未显式指定时为 6)。处理同收尾 C:完成当前动作、写运行清单、如实报告推进到哪与预算命中,下次启动从账本现状继续。
- **异常中止**:认证、CAPTCHA、支付、浏览器封锁等 blocker 使所有可行工作停摆时,停止并如实报告 blocker。blocker 不是额度耗尽,不是完成,不得伪装成任何正常终止。
- **禁止的停止理由**:扫描空轮、候选池为空、"看起来找不到"、运行时间长、轮次多。按运行策略换来源、维护触发池或还债；只有契约化预算、校准、资源或 blocker 才收尾。
- **screen_unsatisfiable**:拒绝原因收敛到少数结构性模式时,写一份假设报告入运行清单并继续运行——它是发现,不是终止理由。
- **收尾 E——连续三轮无真实决策迁移且队列增长**：`run_policy.py` 的 `consecutive_decision_stall_rounds >= 3` 时停止新增候选，完成当前轮 record-round 后转入闸门、来源与容量校准。这里不把 queued 当成功：它只证明又登记了新债。校准记录必须分别回答筛子是否过紧、浏览器是否阻断 G1、source family 是否单一、还债容量是否不足。
- **反空烧**:Semrush 纪律仍为 decision-changing only。额度是终止条件,不是消耗目标;为触发终止而空烧额度是禁止的。
- **去重**:**每轮**都要去重,时点是本轮提取出方向之后、花任何筛选成本之前——用 `screen_index.py check` 批量查(一次覆盖淘汰索引与账本)。它算开局纪律(先看见过什么,再花成本),但执行位置在提取之后,因为待查方向要先有(同 xinci-scan 第 0 层「执行时点」);已弃候选与已记录的淘汰方向不重复评估。索引本身不进上下文。命中的方向**不计入 funnel 的 `extracted`**——它们上一次已经有归宿了,再要求一次归宿,加总等式必然算不平。
- **如实说明**:形成期以周计,单次运行无法压缩。运行把存量候选推进到当下证据允许的最远处(tracking 复查、formation→qualify、qualified→decide),同时持续扫描新候选;单次运行内最可能先出现的 go 决策是快道(fast_grab_ready)。

## 时间字段:只记录,不调度

- 三个时间事实:`first_observed_at`(首见)、`last_checked_at`(上次复查)、`expiry`(失效日,附推理于证据)。
- **没有** next_check_at、默认复查间隔、调紧/放宽规则等任何调度机制。
- skill 被调用时只汇报时间事实("该候选 12 天未复查,expiry 还剩 5 天"),不据此自动做任何事。
- expiry 过期不自动转 expired:skill 提议,用户确认后 registrar 才执行。
- 复查哪些候选、何时复查、何时推进阶段,全部由用户决定。

**上面两条描述的是默认的单步形态,连续运行模式下授权时点前移、其余不变。** xinci-run 的启动命令授予本次运行的标准授权(见上「连续运行模式」),运行循环里的 `captured→expired`、`tracking→expired` 由它直接执行,不再逐条回头问；这表示用户授权执行既定路径,**不等于用户事前读过每个候选或逐条确认过风险**。本节禁止的始终是那件事:没有任何时间字段会**自己**触发转移,也没有 next_check_at 之类的调度机制;哪些候选进入本次运行、要不要启动连续运行,仍然全部由用户决定。

## 证据与命名约定

- 观察文件:`证据/<slug>/<YYYY-MM-DD>-<阶段>.json`,阶段 ∈ {scan, track, qualify, decide};schema 见 `数据结构/observation.schema.json`。其中 `-decide` 是**可选**的:决策阶段的产出是决策书,只有为补缺口做了新审计时才落一份 `-decide` 观察,没有新观察就不写(数据极简)。窗口期 `scan` 与形成期 `track` 用 `g6_tentative_lines` 记 `tentative_pass|tentative_veto|N/A`,确认期 `qualify` 才用 `g6_lines` 记 `pass|veto|N/A`;两者不得并存,暂定结论也不得写入 gates 冒充 G6。**凡 register/transition/amend 提交 gates,本次 `--evidence` 中的 observation.gates 必须逐门给出相同结论,且支撑观察的 source_urls 非空**;不能拿无关文件充数。`G3=veto_window_bet` 还必须填写结构化 `window_bet`(免费实现 URL、上一个同类对象页面、实测 lag_days、判断理由),所有 URL 都必须列入 source_urls。
- 观察文件可以记录由本次证据直接支撑的闸门结论(`gates`、`g6_tentative_lines`、`g6_lines`),但不登记候选状态转移、go/no-go 或其他生命周期裁决;这些只在账本。
- **观察也不得创造通用判据。** 它只写本次证据支撑的**这个候选**的结论,不写"以后都该怎么筛"。新判据必须落到契约文件或 [陷阱类别.md](陷阱类别.md)——那里才有出处、反例与后续复核;写进观察等于让一条未经验证的规则绕过契约层直接生效。
  出处(2026-08-29):一份 scan 观察在做自我修正时,顺手写下"自动补全只能用于筛掉需求侧未形成的方向(零建议即弃)"。该修正对的那一半(不能用自动补全推断供给侧占位)有实测支撑,多写的那半句既没验证,又与数据采集指南「自动补全出现与否是形成信号证据,不是资格证据」直接抵触;但后续运行读到观察即当判据执行,共否决 10 个方向,其中 5 个纯靠它成立。反测见数据采集指南「自动补全:有建议是正证据,零建议不是否决」:契约与账本自己的 9 个正面样例里 7 个返回零建议。
  **分层是硬的:观察是证据层,判据是契约层,两层不能互串。** 读观察的一方同理——observation 里出现的通用性说法只是当时执行者的推理,不构成判据,除非它已被写进契约文件。
- **数据极简原则**:只写简单清晰、服务于决策的内容——不写仪式性字段、不写过程流水账、不为"显得完整"而填充。观察写要点,不写转录。
- 运行清单:`运行/<YYYY-MM-DD>-<skill>.json`,每次运行一个小 JSON。连续模式的批量扫描另用 `运行状态/阶段/` 保存可恢复检查点：开始时登记本批正式 term，每条只可追加一个归宿，全部完成并 `finish` 后才允许 `record-round`；检查点不替代账本/索引/manifest。manifest 字段约定见 `数据结构/run-manifest.schema.json`，唯一校验实现是 `scripts/run_manifest.py`。`funnel.carryover_audited` 不参与提取归宿等式，`queued` 不计决策推进。正式候选归宿只有四格:`rejected_zero_cost` / `rejected_g1` / `deep_audited` / `queued`。`pooled` 只供读取 2026-08-31 前的历史清单，新检查点和新 `record-round` 均拒绝写入。
- **淘汰方向索引**:`<数据区>/淘汰方向.jsonl`,每行一条 JSON，`date` 是必填的实际观察日 `YYYY-MM-DD`。由 `scripts/screen_index.py` 读写，**不要手工编辑**。历史空日期只能根据运行清单/观察证据用 `repair-date` 写入追加式 `淘汰方向修订.jsonl`；不得用当前日期猜补或覆盖旧行。`[疑似重复·须快审]` 必须用 `resolve` 闭环；错误裁决只可 `--supersedes` 追加修订。
- **触发池**:`<数据区>/触发池.jsonl` 是官方变化原料的事件日志，状态为 pending/approved/discarded；它不是候选账本，不产生正式结论。raw trigger 只进入独立 `trigger_funnel`，不混入正式候选 funnel；注册成候选之后才按 `deep_audited` / `queued` 等归格。`discarded` 是终态,不可重开或覆盖;`approved` 保留**唯一一条** discard 出边——批准只表示可进 G0,方向随后被闸门否决(典型是 G1 实测 veto)时要能作废,reason 写明失败的闸门与现场结论,否则死方向会永远挂在 approved 上被下一次运行反复提取。

raw trigger 用独立 `stage=trigger` 检查点，结果只能是 `trigger_discarded / trigger_pending / trigger_approved`；`record-round` 按触发池中绑定 run_id+round 的事件自动生成 `trigger_funnel`。正式候选 `funnel.extracted` 只统计已进入候选筛选的 query。只读复核写 `candidates_reviewed`，只有账本 history 实际写入才算 `candidates_touched`。`finish` 将最终状态、中文展示、理由、结束时间、轮次预算、GO 候选与结束证据固化进 manifest 的 `termination`。

**G6 结构性入口否决出口（rejected 边第⑧种）**：已注册候选若确认“付费者不逐对象重复 / 官方不计该主体类别 / 不存在自助法律效果”，本次 scan/track observation 写 `g6_entry_veto` 和实际来源，当轮走 `captured/tracking→rejected`。它不写 `gates.G6`，不写 `g6_tentative_lines`，也不等待 expiry；registrar 将其视为 rejected 边的独立结构证据。tracking 阶段只在新证据暴露该结构事实时触发，不把它扩张成每轮重跑正式 G6。

**留痕分界**——分界线是「这一条的现场证据值不值得单独留档」。两种情况值得,其余都只配一行索引:

1. **它还有下一步**(深审存活、排队待审);
2. **它的结论来自 G2/G3 深审**——哪怕结论是出局。深审是全流程最贵的动作、每轮配额 ≤5,它数到的免费实现清单、结构阅读要点、footprint 观察都是**这一个方向独有的**证据,索引的一行 reason 装不下;而正因为每轮只有 ≤5 条,注册成本也不构成问题。

反过来说,只配一行索引的是**成本低到不值得留档、且数量大到留档会淹没账本**的那些:批量秒弃、G1 否决、已归并的陷阱类别命中——它们的死因是类别级的,单个方向没有独立留档价值。

**再补一条收口规则:上面两条判的是「要不要注册」,而一旦注册过,后续处置就只在账本一侧。** 已经在账本里的候选,此后的一切结论都走账本——包括排队位候选(见下面「具体分派」的注册进账本一项)补跑 G1 被否,走 `captured→rejected`(见上表第⑤种情形)。上面那条「G1 否决走索引」说的是本轮首次见到、尚未注册的方向;索引管不着已注册的候选,而账本里多出的这几条不会淹没它——排队每轮进 10–20、出 ≤5,其中**缺 G1 的只是一部分**(只有超 G1 上限没搜的那些缺),被 G1 否的又只是这一部分里的一半,**每轮个位数**,不是每轮 18 条。

具体分派:

- **只追加一行进本索引,不注册**:零成本秒弃(G0 / G4 / G6–G7 预筛 / 无任务)、**未注册方向的 G1 否决**、陷阱类别命中(含当场跑 G3 验证判 `veto` 的;纯品牌名即陷阱类别二,归在这一项,不另列)。这些方向都已终结,永不复活。G1 否决走索引是 2026-08-19 定的:按漏斗目标量它每轮约 18 条,逐条写观察文件 + register + transition 是每轮 36 次脚本调用、每周 100+ 条 rejected 塞满账本,写入成本压过了本轮真正值钱的 5 次深审;而它需要留下的只有"这个方向见过、死在 G1",索引一行(`gate=G1`,reason 带首屏证据要点:是 featured snippet 还是原生组件把任务做完了)完整承载了这件事。**这一条只管未注册的方向**:已经注册进账本的排队候选(①的 b 类与②)下轮补跑 G1 被否时,走 `captured→rejected`(见上表第⑤种情形),不是追加一行索引。
- **注册进账本**:①走到 G2/G3 深审**且存活**的候选,按「下一步是不是就出闸」分两类——**a 类:本轮已走完 G0–G5 全程、下一步就出闸**(register 只带证据,闸门结论与 `window_estimate` 随紧接着的出闸 `captured→screened` 一起提交——`register` 没有 `--window-estimate` 参数,而带 `--gates` 就会被强制要 `--expiry`,那是排队位的字段,一个下一步就出闸的候选不该有);**b 类:深审存活但前面的门还缺**(典型是 G5 陷阱验证取得有效 `pass`,或历史兼容候选已有合法 `veto_window_bet`,而 G1/G2 尚未跑),**注册时**它还没走完全程,所以按②的排队位注册:`captured` + gates(含已得的 G3 结论)+ expiry(带 `--gates` 就被强制要 `--expiry`)。注册之后它**回正常序列、在本轮继续补 G1/G2**——G3 那笔全流程最贵的钱已经花了,没有理由让它白等一轮;只有本轮没排上(超 G1 上限或超深审配额)才留在 `captured` 到下轮。funnel 归格随之定:本轮走完就是 `deep_audited`,没排上才是 `queued`;②超配额排队的存活方向(`captured` + gates + expiry);③**走到 G2/G3 深审但被否决的候选**——G2 结构阅读判否、或在占位否决生效前提下 G3 判 `veto`,同样先 register 再走 `captured→rejected`,reason 写清失败闸门与现场证据要点(数到的免费实现、结构阅读结论)。订阅线暂定可行时,占位事实只进入竞争记录,G3 有效门结论写 pass,不属于③。
- **陷阱类别的一个例外**:命中陷阱类别、当场跑 G3 验证且占位否决**确实生效**时,判 `veto` 的方向留在索引一侧(订阅线暂定可行时,同样的占位事实只记作竞争输入,G3 有效门结论写 `pass`,按上一条①的 b 类注册进账本;该模式已是正式类别,单个方向没有独立留档价值,这一次数到的免费实现清单按陷阱类别.md 的追加规则写进该类别节里——证据落在规则文档,不落在候选证据区);**但若在否决生效前提下判出的是 `veto_window_bet` 而不是 `veto`,它就有了 go 出口(快道),必须注册进账本**——按上一条走,索引不再记它。扫描与连续运行的开局去重用 `screen_index.py check` 一次覆盖索引与账本,不必翻历史运行清单,也不必把任何一方读进上下文。**归并纪律**:**每当认出一个新的结构性模式,就按陷阱类别.md 的追加规则把它归并成正式类别**(附实际观察;发现即建类,不必凑满三次——"≥3 次观察、跨日期、跨来源家族"是 SERP 陷阱型**改标直接筛除型**的门槛,不是建类门槛。改档计数时索引一侧的秒弃 + 账本一侧的深审否决**合并计数**——类别三的三例全在账本一侧,只数索引这一侧会永远数不到三),并在索引补一条归并记录——**term 写模式名本身**,不是任何一个具体方向(写成具体方向会被 `append` 的 term 去重静默跳过,那条记录根本落不下去),`gate` 记 G5,`reason` 以 `[已归并]` 开头并指向类别号,`pattern` 填该模式名:
  `printf '%s\n' "厂商已占位的 B2B 强制任务|G5|[已归并] 见陷阱类别.md 类别三|厂商已占位的 B2B 强制任务" | python3 xinci-workflow/xinci-core/scripts/screen_index.py append --date <YYYY-MM-DD>`
  (`screen_index.py stats` 会在某 `pattern` 累计 ≥3 次时提示该归并了——那是**漏归并的兜底提醒**,不是建类门槛;且**它只看索引一侧**:账本没有 `pattern` 字段,`stats` 只读 `淘汰方向.jsonl`,深审否决的模式它数不到。那一侧靠人:深审判否时若死因看起来是一个结构性模式,把模式名记进本次运行清单的 notes,改标直接筛除型前把两侧的次数合起来核一遍);此后命中该模式的方向由 G5 **按该类别自带的处置档**处理——标「直接筛除型」的零成本弃,标「验证型」的仍要跑 G3 验证(新类别的处置档按死因型定:SERP 陷阱型默认验证型、前置筛除型一律直接筛除型,见陷阱类别.md)。**改标直接筛除型省掉的是"第四次验证同一个死因";归并本身不省验证(验证型类别照常跑 G3),更不省留痕**:秒弃照常追加一行索引(gate 记 G5),否则下轮 `screen_index.py check` 认不出它,同一方向每轮都要重新提取评估。索引不会因此线性膨胀——`screen_index.py append` 按归一化 term 跳过重复,每行始终是一个独立方向,而不是一次命中。

## registrar 用法

### 中文交付与机器码边界

账本、schema 与 Python API 中的状态值是稳定机器码，不做破坏性迁移。面向用户的状态汇报、终止原因、错误解释与最终交付必须使用中文展示名；不得把 `budget_reached`、`active`、`captured` 等机器码直接当作自然语言结论。命令行控制器默认输出中文，只有机器解析时才显式使用 `--json`。

### `--by` 取值:按**运行模式**定,不按命令所在的文档定

`--by` 记执行者;连续运行授权还必须由活动 `run_id` 证明,不再相信调用者自报身份:

| 运行模式 | `--by` 取值 | 含义 |
| --- | --- | --- |
| 单步调用某个阶段 skill | 该 skill 名(`xinci-scan` / `xinci-track` / `xinci-qualify` / `xinci-decide` / `xinci-mature`) | 用户逐条确认过这次转移。`xinci-mature` 另受 registrar 硬校验:它只能写 `lane=mature` |
| xinci-run 连续运行(含它派出的子代理) | `xinci-run` + `--run-id <活动会话>` | 标准授权;会话必须已 begin-round |
| 用户亲自手工执行(无 skill 承接的单步操作:`built` 登记、闸门重算后的出清、`reconcile` 裁决) | `user` | 用户本人决定并执行这次写入,不再有另一层确认 |

**各阶段 SKILL.md 里的命令模板是单步形态。连续运行时必须同时传 `--by xinci-run --run-id <run_id>`。** 活动会话存在时 registrar 拒绝任何单步写入,因此漏传或伪造阶段名不再能静默绕过授权边界。

窗口赌注在连续模式下先挂起。必须先把候选以 `captured`、`G3=veto_window_bet` 和 expiry 写进账本,用户明确接受后才由 `run_controller.py confirm-window-bet` 写入候选级一次性确认,registrar 成功出闸后消费它;确认不可预埋、覆盖或消费后重新激活,没有确认记录不得出闸。

窗口赌注出闸同时修改 session confirmation 与候选账本,使用 `运行状态/事务/` 的 v2 前滚日志。每次载入会严格校验字段白名单、文件名/ID 关系、状态与时间顺序,并核对 `candidate_after_sha256`;快照被改写即 fail-closed。若中途崩溃,pending 事务会阻止所有后续写入及会话推进/结束;先执行 `run_controller.py recover [--run-id ...]`。检测到第三方改写时拒绝覆盖,由用户显式执行 `reconcile --tx-id ... --decision keep_current|apply_after --reason ... --by user|xinci-run --confirmation-ref <引用>`。`keep_current` 会作废已消费确认;若仍要出闸必须重新明确确认。

session 每次载入都会校验字段白名单、run_id/文件名、状态组合、轮次上下界、时间顺序与 confirmation 历史;手改出矛盾状态会立即停止授权。连续模式下 registrar 把 `run_id` 与活动 `round` 一起写入每条 history。每轮必须由 `record-round` 收尾:它按轮号自动归集候选,并反查 `funnel.queued` 是否确有同轮新注册、带 gates+expiry、尚未深审的排队候选；然后原子追加 manifest、推进 session。在两次写入之间中断时,`recover` 不处理这个写入点,用相同 `record-round` 参数重试可幂等完成。启动前用 `list` 获取 active run_id。`finish` 对零轮运行自动建空清单,其余情况要求**恰好一份**相同 run_id 的 manifest 并执行完整共享校验。

```bash
python3 xinci-workflow/xinci-core/scripts/registrar.py register \
  --slug <slug> --term "<精确措辞>" --source-url <URL> --task "<任务>" \
  --evidence "证据/<slug>/<日期>-scan.json" --by <skill名> \
  [--source-note "<现场摘要>"] [--aliases "别名1,别名2"] \
  [--gates G0=pass,G4=pass,G5=pass,G1=pass] [--expiry YYYY-MM-DD]
  # 排队位注册:带 --gates 就必须带 --expiry,且 observation.gates 必须支撑同一组结论

python3 xinci-workflow/xinci-core/scripts/registrar.py transition \
  --slug <slug> --to <状态> --by <skill名> [--gates G0=pass,G1=pass,...] \
  [--window-estimate <days|weeks|months>] [--expiry YYYY-MM-DD] \
  [--expiry-trigger <date|invalidation|window_closed>] \
  [--invalidation "条件1;条件2"] [--score N] [--income-score 1-20] \
  [--g6-passed-lines subscription,advertising] [--decision-ref 决策书/<slug>.md] \
  [--play ...] [--reason "..."] [--evidence <路径>] [--superseded-by <slug>]
  # 带 --gates 时,本次 --evidence 必填且 observation.gates 必须逐门一致
  # --window-estimate 是 captured→screened 的必填项;--superseded-by 是合法来源态→superseded 的必填项
  # --expiry-trigger 只在 →expired 时必填,并按来源态限制；date 会校验账本 expiry 已到
  # formation_confirmed→qualified 还必须带 --score、--income-score 与 --g6-passed-lines
  # (两者上表都列为硬要求,别因为这里是方括号就当成可省)

python3 xinci-workflow/xinci-core/scripts/registrar.py checked \
  --slug <slug> --evidence "证据/<slug>/<日期>-track.json" --by <skill名>

python3 xinci-workflow/xinci-core/scripts/registrar.py amend \
  --slug <slug> --by <skill名> --reason "<用户确认的修订理由>" \
  [--expiry YYYY-MM-DD] [--add-alias <别名>] [--add-invalidation "条件1;条件2"] \
  [--gates G3=veto_window_bet --evidence "证据/<slug>/<日期>-scan.json"]
  # --gates 仅 captured:补记本轮跑出的闸门结论(排队位/挂起位唯一的 gates 写入口),
  # 补记后必须有 expiry;出闸之后的 gates 只能由 transition 写
```
